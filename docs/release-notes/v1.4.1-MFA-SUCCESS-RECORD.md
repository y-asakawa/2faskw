## 変更内容

- GraphicalMatrix／TOTP／WebAuthnの共通完了検査で最新成功日時を記録する。
- 画像の単独照合とTOTP登録から日時代入だけを外す。カウンター・登録状態・世代進行は維持する。
- 日時保存と成功監査の独立ON/OFFを追加する。いずれも既定ON。
- 共通イベント`MFA_COMPLETE/OK`を既存の監査ファイルへ追加する。
- Dashboardの認証カテゴリへ追加し、方式・scope・保存結果の内訳を表示する。
- 公式TOTPが返す`TOTPPrincipal`を完了検査で読み取れるよう修正。TOTP検証成功後の誤拒否と、それに伴う成功日時の未記録を防ぐ。利用者・flow・世代の一致検査は維持する。
- 公式WebAuthn 1.4.2の第二要素結果でUsernamePrincipalが欠落する場合、同一Subjectへ束縛された成功時の正規化名だけを許可する。過去結果・無関係なSubjectや名前の矛盾は拒否し、公式プラグインは改変しない。

## 対象とする成功日時

| 項目 | 意味 |
| --- | --- |
| DBの`last_success_at`／CLI表示の`last_success` | 共通MFA完了検査に合格し、条件付き保存に成功した最新日時。全件の履歴ではない。 |
| DBの`updated_at`／CLI表示の`updated` | 日時保存で必要な場合だけ単調に進める。他の設定変更等でも更新されるため、認証専用の日時ではない。 |
| `MFA_COMPLETE/OK`の日時 | その要求の共通MFA完了検査日時。日時保存がOFF・失敗・競合skipでも、必須検査に合格し監査がONなら出力する。 |

通常SSOと自己管理再認証を対象とする。SP/IP方針によるMFA bypass、単独の画像照合や登録処理、
共通CompletionStrategyを通らない認証を一律に集約する機能ではない。
完了後のSP認可・属性アクセス制御・自己管理handoffが拒否されても、既に記録した完了は取り消さない。
`last_success`は設定変更履歴、SPへのアクセス許可日時、今回の新しいfactor操作の証拠ではない。

## 設定と互換性

```properties
graphicalmatrix.mfa.successRecord.enabled = true
graphicalmatrix.mfa.successRecord.queryTimeoutSeconds = 1
graphicalmatrix.mfa.completionAudit.enabled = true
```

| 設定 | 省略時 | 対象 |
| --- | --- | --- |
| `successRecord.enabled` | `true` | 共通完了時の成功日時保存。 |
| `successRecord.queryTimeoutSeconds` | `1` | 付加SQL UPDATEの期限。範囲は1～5秒。認証全体・必須SELECT・LDAPのtimeoutではない。 |
| `completionAudit.enabled` | `true` | 共通成功イベント`MFA_COMPLETE/OK`。既存のVERIFY等やCLI監査を一括停止する設定ではない。 |

上表のキーはすべて`graphicalmatrix.mfa.`を先頭に付ける。2つのON/OFFは独立している。
両方OFFでも登録状態の必須SELECT、照合・登録に必要な既存UPDATE、本人・方式・世代の検査は残る。
LDAPはLDAP接続のtimeout設定を使う。設定の不正値はconfig検査で拒否する。CLIの引数・列名、APIの`lastSuccessAt`、
DB credential形式、TOTP window、WebAuthn鍵、MFA方針は変更しない。

旧日時は変換せず、日時保存OFF期間の認証をDBへ自動補完しない。監査ONの場合も、ログからDBへ
自動反映する処理は追加しない。保存失敗時はDBの最終値と監査イベントの日時が異なり得る。

## 保存・障害・認可

必須状態lookupの接続を共用し、通常最大1回の条件付きUPDATE／LDAP modifyを試みる。
`last_success_at`と必要に応じた`updated_at`だけを進め、登録世代`state_version`は進めない。
現在値が完了日時と同じか新しければ更新せず、未来の保存値も自動で修正しない。
LDAPはraw値の一致・属性不在を含むcritical assertionを使用し、非対応時に無条件更新へ逃げない。
0件更新／assertion競合は最大1回再確認し、管理変更を観測したら拒否、新しい日時は保持する。
再確認後も状態は有効だが日時が進んでいない場合は、追加の書込みretryをせず競合skipとする。

| `store` | 意味 |
| --- | --- |
| `UPDATED` | 条件付き書込み成功。 |
| `UNCHANGED` | 保存値が今回と同じか新しく、巻戻し不要。 |
| `DISABLED` | 日時保存OFF。 |
| `SKIPPED_CONTENDED` | 競合後も必須状態は有効だが日時保存をskip。 |
| `FAILED` | 日時metadataの検証・保存・接続close等で失敗。必須状態が有効なら認証は継続する。close失敗等では既に更新済みの可能性もあり、rollbackを意味しない。 |

`NOT_ATTEMPTED`は内部の未実行状態であり、認証拒否を成功監査として出すための値ではない。

必須lookup失敗や状態不一致は認証拒否。日時だけの保存障害はWARNと`store=FAILED`で知らせて
認証を継続する。監査障害も認証の成功を取り消さず、相関UUID付き代替WARNを試みる。
自己管理の証跡、一回消費Handoff、期待世代による保存は維持する。記録済みcontextや成功日時を
認可根拠にせず、Strategy再評価でも必須状態検査を繰り返す。
この要求内の初回記録でのみ付加書込みと監査を試み、再評価を無制限の書込みretryにしない。

## 監査とDashboard

出力先はIdP側の`logs/graphicalmatrix-audit.log`であり、新しい認証履歴テーブルは作らない。
版付き`mfa1:` detailはUTF-8 formを標準Base64で包む。フィールドは
`method,flow,scope,sp,completedAt,store,eventId,stateVersion`。
長さ上限16KiB、未知／重複／欠落キー、方式とflowの不一致、時刻不一致をDashboardのparserで拒否する。
`completedAt`はepoch milliseconds。SP/Requester識別子`sp`は原本detailには含むが、Dashboardの
正規化転送前に捨てる。ユーザー／IPの既存privacy設定を維持し、Base64を秘匿化とは見なさない。
相関UUID`eventId`で従来の取込主キーを置換しない。

Dashboard索引schema 6へnullable列を追加する。認証DBの列追加は不要。
旧イベントは保持するが不足する方式情報を推測しない。旧Agentが情報を落としたイベントは
必要に応じて原本から再取り込みする。`VERIFY`と`MFA_COMPLETE`を合算しない。

### v1.4.2のログ仕様との関係

v1.4.1の監査`ts`はUTC。v1.4.2では実行環境のシステムタイムゾーンに合わせ、`Z`または数値offsetを
付ける。表記だけの変更であり、`completedAt`、DBのepoch値、TOTP計算は変更しない。
Dashboardは旧UTC行と新offset行を同じ絶対時刻へ正規化するため、この表記変更だけで再取込みは不要。
JVM/TZによる上書きとOS timezone変更後の再起動は[ログ日時の共通ルール](../LOG-REFERENCE.md#log-timezone)を参照する。

v1.4.2の管理CLI操作監査は別機能で、既定出力先は`/var/log/2faskw/admin-audit.log`である。
本書の`completionAudit.enabled=false`で停止せず、日時metadataや共通成功監査の障害時に認証を
継続する方針を、CLIの必須監査へ適用してはならない。CLIの`op_id`とMFAの`eventId`も別の識別子である。
詳細は[v1.4.2管理CLI監査設計](./v1.4.2-CLI-ADMIN-AUDIT-DESIGN.md)と
[開発者向けログ設計](../development/LOGGING.md)を参照する。

## 導入と切戻し

v1.4.0以前からは、修正版JARとMFA完了遷移の両方を確認する。既存XMLを全置換せず、
`authn/External`、`authn/TOTP`、`authn/WebAuthn`の共通CompletionStrategy接続、bean定義、
拒否イベント、`idp.authn.MFA.reuseCondition = shibboleth.Conditions.FALSE`を統合する。
全認証ノードの更新・旧フローの終了を確認する。Dashboard利用時はDashboard／Agentを先に更新し、
機能を段階導入する間は2フラグを明示的にOFFにする。省略時は両方ONのため、設定の未追加をOFF扱いしない。
旧版の日時代入は新フラグで止まらない。ノード新旧混在中の意味の違いも考慮する。
索引更新前に停止backupを取り、旧Dashboardへの切戻しはbackup復元か別索引へ原本再取込みを行う。
既に対応済みのv1.4.1からv1.4.2へ更新する場合、この機能のためだけのDB列追加や
TOTP／WebAuthnの再登録は不要である。CLI監査の準備はv1.4.2の更新手順に従う。
手順は[UPGRADE.md](../UPGRADE.md#mfa-completion-recording)、
仕様は[development/MFA-SUCCESS-RECORD.md](../development/MFA-SUCCESS-RECORD.md)を参照する。
