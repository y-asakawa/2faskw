# 2FAS-KW v1.3.0 SP別LDAP属性アクセス制御・属性カタログCLI 詳細設計

## 1. 文書の目的

本書は、2FAS-KW v1.3.0で次の2機能を実装するための詳細設計である。

1. SPごとに、IdP Attribute Resolverが解決したLDAP属性を使ってアクセス可否を判定する。
2. IdPで利用可能な属性を検出・分類し、承認済み属性だけでSP向けattribute profileを管理する。

どちらも既存のSP管理CLIである
`/opt/shibboleth-idp/bin/graphicalmatrix-sp.sh`へ統合する。新しい管理APIや外部公開listenerは
追加しない。

本書はv1.3.0で実装したSP別LDAP属性アクセス制御と属性カタログCLIの設計、
セキュリティ境界、運用手順を記録するリリースノートである。確定した導入・更新手順は
INSTALL、UPGRADE、FAQにも反映する。

## 2. 結論

v1.3.0では、次の3つを明確に分離する。

| 項目 | 目的 | SPへ送信するか |
| --- | --- | --- |
| 属性カタログ | IdPで解決できる属性と、その利用可否を管理する | これだけでは送信しない |
| attribute profile | 特定SPへ送信する属性の組合せを管理する | SPへ送信する |
| access policy | IdP内部でSPへのアクセス可否を判定する | 判定属性を送信する必要はない |

例えば`businessCategory=AA`をアクセス条件に使うだけなら、`businessCategory`は
`internal-only`としてカタログへ承認し、SP向けattribute profileには含めない。

認可判定はShibboleth IdP標準の`context-check` post-authentication interceptorから呼び出す。
認証と属性解決の後、SAML Responseを作成する前に、2FAS-KWのJava判定クラスがSP entityIDと
未filterのIdP属性を照合する。

## 3. 対象範囲

### 3.1 v1.3.0で実装する範囲

- `graphicalmatrix-sp.sh access ...`によるSP別アクセス条件の管理。
- `graphicalmatrix-sp.sh attributes ...`による属性候補の検出、分類、承認。
- 承認済み属性からattribute profileを作成・変更・削除するCLI。
- 作成したprofileを既存の`set-attributes`でSPへ適用する処理。
- Shibboleth IdP `ContextCheck`との初期連携。
- access policyと属性カタログの原子的更新、backup、revision、rollback。
- 既存v1.2.7 SP registryの互換読込とschema移行。
- CLI操作と認可結果の監査ログ。
- 設定検査、unit test、integration test、package regression test。

### 3.2 v1.3.0で実装しない範囲

- リモート管理API、Web管理画面、外部からの設定更新。
- LDAPスキーマに存在する全属性の自動公開。
- 任意JavaScript、正規表現、wildcardによる認可条件。
- LDAP groupの再帰展開や、CLI独自のLDAP検索。
- SP側のアプリケーション認可の置換。
- 属性値を含む監査ログ、属性値の常時表示。
- OIDC、CAS、Attribute Queryへの適用。初期対象はSAML 2 Browser SSOとする。
- 複数IdPノード間の自動配布。クラスタでは既存の設定配布機構で同じファイルを同期する。

## 4. 現行v1.2.7との関係

v1.2.7のSP管理CLIは、次をすでに一つのSP管理名で扱う。

- SP metadataとmanaged registry。
- `attribute-filter.xml`内の2FAS-KW管理block。
- `none`、`uid`、`uid-mail`およびproperties定義のattribute profile。
- SP別MFA policy。
- dry-run、`--apply`、backup、revision、rollback、監査。

v1.3.0はこの処理を拡張し、別の実行ファイルを作らない。既存の`add`、`adopt`、`update`、
`set-attributes`、`set-mfa`、`history`、`rollback`の動作を維持する。

既存の`sp-management.properties`にある次の定義は、v1.3.0でも読み取り可能とする。

```properties
graphicalmatrix.sp.attributeProfile.uid-business = uid,businessCategory
```

ただし、CLIがpropertiesを直接書き換えると、コメント、行順、管理者の手修正を壊す可能性がある。
新しいCLI管理profileは専用の`attribute-catalog.json`へ保存し、properties由来profileは
`source=legacy-properties`の読み取り専用profileとして扱う。

### 4.1 既存profileの互換移行

upgradeだけで既存SPの属性releaseを停止させないため、次の互換規則を採用する。

- 組込みprofileの`none`、`uid`、`uid-mail`は`source=builtin`として引き続き利用できる。
- `uid`と`mail`は組込みprofileとの互換目的でsystem approved属性としてcatalogへ初期登録する。ただし
  新規profile作成・更新と新規SPへの適用時には、現在のAttribute RegistryまたはencoderにSAML mappingが
  あることを必ず再検証する。
- properties由来custom profileを現在使用しているSPは、upgrade後も同じfilter内容を維持する。
- properties由来profileは`LEGACY_UNREVIEWED`警告を表示するが、upgrade時に自動削除しない。
- 未承認属性を含むlegacy profileを別SPへ新規適用することは拒否する。
- legacy profileを変更またはmanaged JSON profileへ移行する前に、各属性のrelease承認を要求する。
- `attributes profile import-legacy PROFILE --new-name NEW_PROFILE`のdry-runで、承認不足、
  SAML mapping、影響SPを表示する。

これにより既存動作を維持しながら、新しいSPと新しいprofileだけを厳格な承認境界へ移行する。

## 5. 用語

| 用語 | 意味 |
| --- | --- |
| SP管理名 | `graphicalmatrix-sp.sh`で使う小文字の名前。entityIDとは別。 |
| entityID | SAML metadataに記載されたSPの一意識別子。判定では完全一致する。 |
| resolved attribute | Attribute Resolverが生成したIdP内部属性。 |
| mapped attribute | Attribute RegistryまたはencoderにSAML変換定義がある属性。 |
| released attribute | Attribute Filterを通過し、対象SPへ送信される属性。 |
| catalog | 属性の検出状態、利用区分、承認状態を保存する一覧。 |
| profile | SPへreleaseする承認済み属性IDの組合せ。 |
| access policy | SPへのアクセスを許可・拒否するIdP内部条件。 |
| unfiltered attribute | SPへのrelease filter適用前のIdP属性。認可判定に使用する。 |

## 6. セキュリティ原則

1. **属性の存在は公開許可を意味しない。** 検出しただけではprofileへ追加できない。
2. **認可用属性は外部送信しない。** 必要な場合だけ別途release承認する。
3. **policy設定済みSPはfail closedとする。** 必要属性の欠損、型不明、読込不能は拒否する。
4. **policy未設定SPは従来どおり許可する。** v1.3.0導入だけで既存SPを停止させない。
5. **denyがallowより優先する。** 明示denyに一致した場合は、allow条件を満たしても拒否する。
6. **設定変更はroot限定とする。** Jetty実行ユーザーは設定を読み取るだけとする。
7. **属性値をログへ出さない。** decision、属性ID、reason code、policy revisionだけを記録する。
8. **任意コードを受け付けない。** JavaScript、SpEL、正規表現、任意Spring bean参照をCLI入力にしない。
9. **既存設定を上書きしない。** ContextCheck利用済み環境では競合を検出し、安全に停止する。
10. **SP側認可を原則とする。** IdP側認可は、SPが対応できない場合または統一拒否が必要な場合に使う。

## 7. 全体構成

```text
SAML SP
  -> Shibboleth IdP SSO profile
     -> Password / MFA authentication
     -> Attribute Resolver
        -> LDAPなど既存data connector
        -> IdPAttribute
     -> Attribute Filter
     -> postAuthenticationFlows
        -> context-check
           -> GraphicalMatrixSpAccessFunction
              -> RelyingPartyContext.entityID
              -> AttributeContext.unfilteredIdPAttributes
              -> access-policy.jsonのimmutable snapshot
              -> proceed または ContextCheckDenied
     -> SAML Response生成
        -> attribute profileで許可した属性だけを送信
```

2FAS-KWは認可判定のために追加のLDAP接続を作らない。通常のSSO処理ですでに解決された属性を
使用する。これにより、LDAP接続poolへの負荷を二重化しない。

## 8. IdPへの組込み

### 8.1 ContextCheckの採用

Shibboleth IdPの`context-check` interceptorは、`ProfileRequestContext`を受け取る
`Function<ProfileRequestContext,String>`を呼び出し、`proceed`または拒否eventを返せる。
v1.3.0はfunctional modeを使用する。

plugin側に次のクラスを追加する。

```text
io.github.yasakawa.faskw.GraphicalMatrixSpAccessFunction
io.github.yasakawa.faskw.GraphicalMatrixSpAccessPolicyStore
io.github.yasakawa.faskw.GraphicalMatrixSpAccessEvaluator
```

`GraphicalMatrixSpAccessFunction`は次を行う。

1. `RelyingPartyContext`からSP entityIDを取得する。
2. entityIDにpolicyがなければ`proceed`を返す。
3. `AttributeContext`からunfiltered IdP attributesを取得する。
4. immutable policy snapshotで評価する。
5. ALLOWなら`proceed`、DENYなら`ContextCheckDenied`を返す。
6. decisionを監査ログへ記録する。

### 8.2 初期化コマンド

```bash
sudo /opt/shibboleth-idp/bin/graphicalmatrix-sp.sh access init
sudo /opt/shibboleth-idp/bin/graphicalmatrix-sp.sh access init --apply
```

dry-runは次を確認・表示する。

- `idp.intercept.ContextCheck` moduleが有効か。
- `conf/intercept/context-check-intercept-config.xml`の現在のfunction/condition。
- `conf/relying-party.xml`の`postAuthenticationFlows`。
- 2FAS-KW管理blockの追加差分。
- IdPの再build・再起動が必要か。
- 既存ContextCheckとの競合。

`--apply`はbackupを作成した後、次を行う。

1. ContextCheck moduleが無効なら`bin/module.sh -e idp.intercept.ContextCheck`を実行する。
2. `context-check-intercept-config.xml`へ2FAS-KW管理functionを追加する。
3. SAML2 Browser SSO profileの`postAuthenticationFlows`へ`context-check`を1回だけ追加する。
4. access policyとcatalogの空ファイルを安全な権限で作成する。
5. XML、JSON、plugin設定を検査する。
6. `PENDING_RESTART`を表示し、build、restart、status確認の順序を`next`へ渡す。

interceptor設定はreloadable serviceではないため、初回組込み後はIdPのbuildと再起動を必須とする。
SPごとのpolicy変更ではXMLを変更しないため、通常は再起動しない。

### 8.3 既存ContextCheckとの競合

`shibboleth.context-check.Function`または`shibboleth.context-check.Condition`がすでに利用されている場合、
CLIは自動上書きしない。

```text
state=CONTEXT_CHECK_CONFLICT
reason=An existing non-2FAS-KW ContextCheck function is configured
result=NO_CHANGE
```

v1.3.0では、既存functionの自動renameや任意beanの自動chainは行わない。管理者が既存要件と
2FAS-KW判定を一つのfunctionへ統合し、そのbeanから
`GraphicalMatrixSpAccessEvaluator`を呼ぶ手動構成をrelease noteに示す。競合を無視する
`--force`は設けない。

### 8.4 interceptorの順序

`context-check`は既存のattribute release consentやterms-of-useより前へ置く。アクセス権がない利用者に
属性release同意画面を表示しないためである。CLIは既存flowを削除せず、重複する`context-check`だけを
検出する。

```xml
<property name="postAuthenticationFlows">
    <list>
        <value>context-check</value>
        <!-- existing flows remain in their original order -->
    </list>
</property>
```

## 9. access policyの仕様

### 9.1 保存形式

保存先は次とする。

```text
/opt/shibboleth-idp/conf/graphicalmatrix/access-policy.json
```

例を示す。

```json
{
  "schemaVersion": 1,
  "policies": [
    {
      "name": "2faskwlocaltest",
      "entityId": "https://sp.example.org/shibboleth",
      "enabled": true,
      "mode": "restrict",
      "revision": 3,
      "allow": [
        {
          "attributeId": "businessCategory",
          "values": ["AA"]
        },
        {
          "attributeId": "employeeStatus",
          "values": ["active"]
        }
      ],
      "deny": [
        {
          "attributeId": "accountStatus",
          "values": ["suspended", "disabled"]
        }
      ],
      "updatedAt": "2026-08-04T00:00:00Z"
    }
  ]
}
```

policyにはPassword、LDAP接続情報、利用者の実属性値、session情報を保存しない。ただし、比較対象となる
許可値と拒否値はpolicy定義なので保存する。

### 9.2 評価順序

評価順序は設定ファイルの行順ではなく、次の固定順序とする。

1. entityIDが取得できない要求は、2FAS-KW access policyの対象外として`proceed`とする。
2. entityIDにpolicyがない場合は`NOT_APPLICABLE`として`proceed`とする。
3. policyが`enabled=false`の場合は`POLICY_DISABLED`として`proceed`とする。
4. policyのentityIDとregistryのentityIDが一致しなければ`POLICY_IDENTITY_MISMATCH`で拒否する。
5. AttributeContextまたはunfiltered attributesが取得できなければ`ATTRIBUTE_CONTEXT_MISSING`で拒否する。
6. deny条件のどれかに一致すれば`EXPLICIT_DENY`で拒否する。
7. allow条件をすべて満たせば許可する。
8. allow属性がない、値がない、どれか不一致なら拒否する。

同一属性に複数値がある場合はOR、異なる属性はANDとする。

```text
businessCategory = AA または AB
AND
employeeStatus = active
```

IdP属性がmulti-valuedの場合、少なくとも1値がpolicy値へ完全一致すれば、その属性条件を満たす。

### 9.3 比較仕様

- 比較はUTF-8文字列の完全一致かつ大文字・小文字を区別する。
- 前後空白をCLIが暗黙に削除しない。入力に前後空白があれば拒否する。
- 正規表現、prefix一致、substring一致、`*` wildcardを許可しない。
- 改行、NUL、制御文字を拒否する。
- attribute IDは`[A-Za-z][A-Za-z0-9._-]{0,127}`とする。
- 1値は最大256文字、1属性あたり最大100値、1SPあたり最大32属性とする。
- 1ファイルは最大1 MiB、policyは最大1000 SPとする。

LDAP側のmatching ruleとIdP内部文字列の比較規則は同一とは限らない。大文字・小文字を無視した比較が
必要な場合は、Attribute Resolverで正規化済みの別属性を生成し、その属性をpolicyへ指定する。

### 9.4 fail closedの範囲

access policyが設定されたSPだけをfail closedとする。

| 状態 | policy設定済みSP | policy未設定SP |
| --- | --- | --- |
| 属性が存在しない | DENY | ALLOW |
| 属性解決に失敗 | DENY | ALLOW |
| policy構文が不正な状態でIdP起動 | 起動時検査を失敗させる | 同左 |
| 稼働中の再読込に失敗 | 直前の正常snapshotを維持 | 直前の正常snapshotを維持 |
| policy無効化済み | ALLOW | ALLOW |

運用者がpolicyを設定したSPでfail openへ変更するオプションはv1.3.0では提供しない。

## 10. policyの再読込

ContextCheckの配線は固定し、実際のルールだけをJSONへ置く。これによりpolicy変更のたびにIdPを
再起動しない。

`GraphicalMatrixSpAccessPolicyStore`は次の方式で再読込する。

- 起動時にJSONを厳密に検証し、immutable snapshotを作成する。
- 各認可要求ではsnapshotを参照し、JSONを毎回解析しない。
- `graphicalmatrix.sp.access.reloadIntervalSeconds`ごとに、1 threadだけがmtimeとfile keyを確認する。
- 変更を検出した場合だけ、新しいsnapshotを別領域で構築してからatomic swapする。
- 読込失敗時は直前の正常snapshotを維持し、ERRORと監査eventを記録する。
- symlink、regular file以外、owner/group/mode不整合を拒否する。

既定値と範囲は次とする。

```properties
graphicalmatrix.sp.access.enabled = false
graphicalmatrix.sp.access.reloadIntervalSeconds = 5
graphicalmatrix.sp.access.auditDecisions = true
```

`access init --apply`後に`enabled=true`へする。policyのCLI反映からJVMでの認識まで最大5秒かかることを
表示する。認可requestごとに追加LDAP検索を行わず、通常時のfile statも最大5秒に1回へ抑える。

`access init`がpropertiesへ値を追加する場合は、2FAS-KWの明示的なmanaged blockだけを構造的に更新し、
既存コメント、未知のproperty、行順を保持する。profile定義はこのblockへ書かず、catalog JSONへ保存する。

## 11. 属性カタログ

### 11.1 目的

カタログは「IdPに存在する属性」と「外部SPへ送ってよい属性」を分離する。LDAPスキーマを直接列挙して
送信候補にはしない。IdP Attribute Resolver、Attribute Registry、既存Attribute Filterを解析し、
IdPで実際に利用される属性だけを候補とする。

### 11.2 保存先

```text
/opt/shibboleth-idp/conf/graphicalmatrix/attribute-catalog.json
```

例を示す。

```json
{
  "schemaVersion": 1,
  "attributes": [
    {
      "id": "uid",
      "resolution": "declared",
      "samlMapping": "mapped",
      "governance": "release-approved",
      "classification": "personal",
      "purpose": "SP account correlation",
      "updatedAt": "2026-08-04T00:00:00Z"
    },
    {
      "id": "businessCategory",
      "resolution": "runtime-observed",
      "samlMapping": "unknown",
      "governance": "internal-only",
      "classification": "internal",
      "purpose": "IdP-side SP authorization",
      "updatedAt": "2026-08-04T00:00:00Z"
    }
  ],
  "profiles": [
    {
      "name": "uid-only",
      "attributes": ["uid"],
      "description": "Account correlation only",
      "revision": 1,
      "updatedAt": "2026-08-04T00:00:00Z"
    }
  ]
}
```

### 11.3 検出情報と承認状態を分離する

一つのstatusへ異なる意味を詰め込まず、技術的な検出結果と管理上の承認を分離する。

技術状態は次とする。

| 項目 | 値 | 意味 |
| --- | --- | --- |
| `resolution` | `declared` | resolver設定に出力属性として定義されている。 |
| `resolution` | `runtime-observed` | 指定利用者・SPのAACLI結果で確認できた。 |
| `resolution` | `conditional` | SPや条件により解決有無が変わる可能性がある。 |
| `resolution` | `unknown` | 静的解析だけでは判断できない。 |
| `samlMapping` | `mapped` | Attribute Registryまたはencoderに変換定義がある。 |
| `samlMapping` | `mapping-required` | IdP内部では解決できるがSAML mappingがない。 |
| `samlMapping` | `unknown` | script、custom resourceなどにより静的判定できない。 |

管理状態は次とする。

| `governance` | release profile | access policy | 意味 |
| --- | --- | --- | --- |
| `candidate` | 不可 | 不可 | 検出のみ。管理者判断前。 |
| `approval-required` | 不可 | 不可 | 個人情報・組織限定情報。承認待ち。 |
| `release-approved` | 可 | 可 | 指定目的で外部releaseを承認済み。 |
| `internal-only` | 不可 | 可 | IdP内部判定だけに使用する。 |
| `blocked` | 不可 | 不可 | credential、secret、管理用属性など。 |

`mapping-required`でも`internal-only`ならaccess policyに使用できる。SAMLへ変換しないためである。
一方、release profileへ追加するには`release-approved`かつ`samlMapping=mapped`が必要である。

### 11.4 自動blocked判定

次を既定deny listへ含める。

```text
userPassword
authPassword
unicodePwd
sambaNTPassword
pwdHistory
password
credential
secret
token
totp
webauthn
graphicalMatrixSequence
```

大文字・小文字を無視した完全一致と機微語検出を行う。ただし名前だけでは完全な分類はできないため、
組織固有deny listも`sp-management.properties`へ設定できるようにする。

```properties
graphicalmatrix.sp.attributes.blocked = employeeNumberInternal,hrPrivateCode
```

自動blockedをCLIからrelease-approvedへ変更するoverrideは設けない。必要な場合はresolverで用途を限定した
別attribute IDを作る。

## 12. 属性候補の検出

### 12.1 静的検出

```bash
sudo /opt/shibboleth-idp/bin/graphicalmatrix-sp.sh attributes discover
```

変更は行わない。次のresourceを解析する。

- `idp.service.attribute.resolver.resources`が参照するresolver resource。
- 既定の`conf/attribute-resolver.xml`。
- Attribute Registryのdefault ruleとcustom rule。
- resolver内のlegacy AttributeEncoder。
- `conf/attribute-filter.xml`で既にreleaseされているattribute ID。
- v1.2.7 properties profileとv1.3.0 managed profile。
- access policyで使用中のattribute ID。

resolver resourceは複数指定できるため、`attribute-resolver.xml`だけを固定で読む実装にしない。
XML parserではDTD、外部entity、XIncludeを無効化し、symlinkと過大ファイルを拒否する。

ScriptedAttribute、custom bean、property replacement、activation conditionにより静的に確定できない場合は、
推測せず`conditional`または`unknown`と表示する。

### 12.2 利用者を使ったruntime確認

属性解決はrequesterとなるSPによって変わり得るため、利用者を指定する場合はSP管理名も必須とする。

```bash
sudo /opt/shibboleth-idp/bin/graphicalmatrix-sp.sh attributes discover \
  --sp 2faskwlocaltest \
  --user user001
```

CLIは独自にLDAPを検索せず、IdPのresolver test/AACLI相当処理を使う。内部的な入力は次である。

### 14.1 作成

## 18. registry schemaとrevision

v1.3.0ではSP registryをschemaVersion 2へ拡張する。

```json
{
  "schemaVersion": 2,
  "entries": [
    {
      "name": "2faskwlocaltest",
      "entityId": "https://sp.example.org/shibboleth",
      "attributeProfile": "uid-only",
      "attributeProfileRevision": 1,
      "accessPolicyEnabled": true,
      "accessPolicyRevision": 3
    }
  ]
}
```

実際のentryにはv1.2.7のmetadata、MFA、legacy情報も維持する。

- schemaVersion 1は読み取り可能とし、access policyなしとして扱う。
- 最初のv1.3.0 apply前に全ファイルbackupを作成する。
- schemaVersion 2への保存はapply成功transaction内だけで行う。
- migration後もv1.2.7 revisionを読み取れるようにする。
- 未知のschemaVersionは推測して読まず、変更なしで停止する。

`history NAME`にはmetadata、attribute profile、MFAに加え、access policy revisionを表示する。
`rollback NAME --revision N`は4要素を一つのSP transactionとして戻す。

attribute catalog/profileの変更は複数SPへ影響する可能性があるため、SP単位revisionとは別に
catalog revisionを保存する。profile更新時は、影響する各SPにも新しいrevisionを作成する。

## 19. 更新transaction

### 19.1 access policy更新

```text
CLI入力検証
  -> SP registryとentityIDの照合
  -> catalogでattribute usage承認を確認
  -> 現在policyとの差分表示
  -> --confirmの完全一致確認
  -> transaction backup
  -> access-policy.jsonをtemporary fileへ生成
  -> JSON schema、owner、mode、参照整合性を検査
  -> atomic rename
  -> registry revision更新
  -> plugin config checker
  -> 管理監査ログ
  -> 期限切れbackup cleanup
```

policy fileは同じfilesystem内でatomic renameする。途中失敗時はbackupを戻し、registryとpolicyの
revisionを一致させる。

### 19.2 profile更新

```text
CLI入力検証
  -> catalog承認とSAML mapping確認
  -> 影響SP一覧とAttributeFilter差分表示
  -> transaction backup
  -> attribute-catalog.json更新
  -> attribute-filter.xmlの2FAS-KW管理block再生成
  -> registry更新
  -> AttributeFilterService reload
  -> AACLIによる対象SP出力確認
  -> plugin config checker
  -> revisionと監査ログ
```

reloadまたは検査に失敗した場合は、catalog、filter、registryをすべて戻して再reloadする。一部だけを
成功として扱わない。

## 20. JSON parserと入力安全性

v1.2.7のregistry parserへ複雑なnested JSON処理を追加しない。v1.3.0では標準準拠のJSON parserを
使用し、IdP 5.2.x runtimeとのdependency整合をMaven dependency treeと実機JARで確認する。

実装要件は次とする。

- duplicate keyを拒否する。
- trailing token、comment、NaN、過大nestingを拒否する。
- 最大文字列長、配列数、object数、file sizeを制限する。
- schemaVersionと必須fieldを明示検証する。
- unknown fieldは初期v1.3.0では拒否し、設定typoを見逃さない。
- path traversal、symlink、hard linkによる別ファイル上書きを防ぐ。
- JSON出力はUTF-8、改行はLF、安定したfield順とする。

使用するJSON libraryをpluginへ重複同梱する場合はclass conflictが起こり得る。実装時にIdP提供版へ
`provided`で合わせるか、plugin private classloaderで安全に同梱できることを確認し、package regressionへ
重複JAR検査を追加する。

## 22. エラー画面

`ContextCheckDenied`ではHTTP処理を停止し、SAML ResponseをSPへ送らずIdPのlocal errorを表示する。
画面は「このサービスを利用する権限を確認できませんでした」のような一般的な文言とし、必要属性名や

SP別の問い合わせ先が必要な場合は、policyへ外部URLを直接入れず、SP管理名から固定のsupport referenceを

## 23. 設定検査

既存のplugin config checkerへ次を追加する。

- access機能有効時にContextCheck moduleとmanaged functionが存在すること。
- `postAuthenticationFlows`に`context-check`が1回だけ含まれること。
- 既存non-managed ContextCheckとの競合がないこと。
- access policyとcatalogがregular fileであり、Jettyが読めること。
- owner、group、modeが安全であること。
- JSON schemaと全上限値が正しいこと。
- policyのSP管理名とentityIDがregistryへ一致すること。
- policy属性がcatalogでaccess承認済みであること。
- profile属性がrelease承認済みかつSAML mappedであること。
- 使用中profileが存在すること。
- registry revisionとpolicy/profile revisionが一致すること。
- blocked属性がprofile/policyに含まれないこと。

access無効時に空policyがなくても既存認証を失敗させない。access有効時の不整合はfailとして扱う。

```bash
  2faskwlocaltest --allow 'businessCategory=AA' \

# 4. 許可利用者と拒否利用者を管理試験する。
sudo /opt/shibboleth-idp/bin/graphicalmatrix-sp.sh access test \
  2faskwlocaltest --user allowed-user
sudo /opt/shibboleth-idp/bin/graphicalmatrix-sp.sh access test \
  2faskwlocaltest --user denied-user

# 5. SPの保護URLから実際のPassword、MFA、認可、SAML応答を試験する。
```

この例では`businessCategory`をattribute profileへ追加しないため、SPへ値は送信されない。

### 26.3 属性をSPへ送信する

```bash
# 1. release用途で承認する。
sudo /opt/shibboleth-idp/bin/graphicalmatrix-sp.sh attributes approve \
  uid --usage release --classification personal \
  --purpose 'SP account correlation' \
  --apply --confirm uid

# 2. profileを作る。
sudo /opt/shibboleth-idp/bin/graphicalmatrix-sp.sh attributes profile create \
  uid-only-managed --attributes uid \
  --description 'Account correlation only' \
  --apply --confirm uid-only-managed

# 3. 対象SPへprofileを反映する。
sudo /opt/shibboleth-idp/bin/graphicalmatrix-sp.sh \
  set-attributes 2faskwlocaltest uid-only-managed
sudo /opt/shibboleth-idp/bin/graphicalmatrix-sp.sh \
  set-attributes 2faskwlocaltest uid-only-managed --apply

# 4. AACLIと実SPでrelease結果を確認する。
```

## 27. test設計

### 27.1 unit test

- 同一属性のOR、異なる属性のAND。
- deny優先。
- multi-valued attribute。
- attribute欠損、空値、型不明。
- entityID不一致。
- 大文字・小文字、Unicode、空白、制御文字。
- 上限値と重複rule。
- policyなし、disabled policy、enabled policy。
- schemaVersion 1/2 migration。
- catalog governanceとprofile作成制約。
- blocked属性の拒否。
- duplicate JSON keyと過大JSONの拒否。

### 27.2 integration test

- ContextCheck module無効からの`access init` dry-run/apply。
- 既存ContextCheck function検出時に変更しないこと。
- 既存postAuthenticationFlowsを保持すること。
- Attribute Resolverから`businessCategory`を取得できること。
- `businessCategory=AA`利用者はSAML SSO成功。
- `businessCategory=AB`、欠損利用者は`ContextCheckDenied`。
- 別SPはpolicy未設定のため従来どおり成功。
- DENY時にSAML Responseと属性をSPへ送らないこと。
- `internal-only`属性がSAML assertionへ含まれないこと。
- profile適用後だけ承認属性が送信されること。
- policy更新をIdP再起動なしで最大reload interval内に反映すること。
- 壊れた更新を検出しlast-known-goodを維持すること。
- rollback後にruntime判定とregistry revisionが一致すること。

### 27.3 security test

- XXE、XInclude、Billion Laughs、過大XML。
- JSON nesting、duplicate key、escape sequence、過大string。
- command injection、argument injection、newline injection。
- symlink、hard link、path traversal、race condition。
- root以外によるapply拒否。
- policy/catalogのworld-readable・world-writable拒否。
- ログへ属性値、Password、credential、assertion、session IDが出ないこと。
- malicious attribute IDによるXML injectionがないこと。
- profile名、SP管理名、entityIDの厳格検証。

### 27.4 performance test

- policy 0、100、1000 SPでのlookup時間。
- 1 SPあたり32属性、各100値のworst case。
- 50、100、200同時SSOで認可追加前後を比較する。
- requestごとにLDAP接続が増えないこと。
- requestごとにJSON parse/file readが発生しないこと。
- policy reloadとSSOが同時でもpartial snapshotを見ないこと。

目標は、policy snapshot lookupと属性比較のp95追加時間を1 ms未満とする。実際のSSO全体時間とは
分けて計測する。

## 28. 受入条件

1. v1.2.7からupgradeしただけでは、既存SPの認証・MFA・属性releaseが変わらない。
2. `access init`はdry-runで差分を表示し、`--apply`なしで変更しない。
3. 既存ContextCheckを上書きしない。
4. SP管理名からentityIDを一意に解決し、完全一致でpolicyを適用する。
5. `businessCategory=AA`の利用者だけを指定SPへ許可できる。
6. policy設定済みSPで属性欠損・解決失敗をfail closedにできる。
7. policy未設定SPは従来どおり利用できる。
8. access用属性をSPへ送らずに判定できる。
9. 検出だけでは属性releaseを開始しない。
10. release-approvedかつSAML mapped属性だけでprofileを作成できる。
11. profileを`set-attributes --apply`したSPだけへ属性をreleaseする。
12. policy/profile変更がbackup、revision、rollback、監査の対象となる。
13. policy変更を通常はIdP再起動なしで反映できる。
14. 認可処理で追加LDAP検索とrequestごとのJSON parseを行わない。
15. 認可拒否画面とログから必要属性名・期待値を漏らさない。

## 31. 公式仕様との対応

- ContextCheckはIdPのcontext treeを検査し、functional modeでは`proceed`または任意eventを返せる。
  `conf/intercept/context-check-intercept-config.xml`で設定し、module
  `idp.intercept.ContextCheck`を有効化する。
- post-authentication interceptorは認証・属性処理後、outbound response生成前に実行される。
- AACLI/resolver testはprincipalとrequesterを指定してAttribute ResolverとAttribute Filterを試験でき、
  IdP 5.1以降は`--unfiltered`を利用できる。
- Attribute RegistryはIdP内部属性とSAMLなどprotocol表現の変換関係を管理する。resolverで値が取れることと
  SAML mappingが存在することは別である。

## 32. v1.3.0で確定する方針

- 独立した`graphicalmatrix-access.sh`は作らない。
- `graphicalmatrix-sp.sh`の`access`と`attributes` subcommandで完結させる。
- リモートAPIを作らない。
- access policyとattribute release profileを分離する。
- access policy未設定SPは許可、設定済みSPはfail closedとする。
- denyをallowより優先し、同一属性値はOR、異なる属性はANDとする。
- access用属性をSPへreleaseする必要はない。
- properties由来profileは互換読込し、新規CLI profileはJSONで管理する。
- profile作成前に属性の明示承認を必須とする。
- 初回ContextCheck組込みはIdP再起動を必要とし、policy変更は通常再起動不要とする。
- 既存ContextCheck設定を自動上書きしない。
- 認可requestごとのLDAP再検索、JSON再解析、設定file読込を行わない。
- runtimeとCLI testは同じpure evaluatorを使用する。
