### 1.1 list／showのWebAuthn登録サマリー

`graphicalmatrix-db.sh list`／`show USER`の末尾へ、表示専用の`webauthn_status`と
`webauthn_credential_count`を追加する。enrollmentと同じPostgreSQL DB・search pathの
`storagerecords`を読み取り、公式WebAuthn contextとcanonical usernameのStorageRecord IDで
対象を絞る。user handleや他contextから利用者を推測しない。重複credential IDは1件と数える。
共通の表示列は`locked_until`の後へ`last_success`・`created`・`updated`をまとめ、その後へ
`totp_status`・`totp_registered`・`totp_seed_set`とWebAuthnの2列を並べる。

登録があれば`REGISTERED`と件数、対象行なし・空配列・期限切れは`UNREGISTERED`と`0`、
確認不能は`UNKNOWN`とする。H2では`UNKNOWN`固定。形式不明なJSON値・配列要素はその利用者を
`UNKNOWN`とし、JSON構文不正・テーブル不在・権限不足・5秒の照会期限等でSQL全体が失敗した場合は
従来のenrollment照会へ戻り、対象一覧のWebAuthn列を全件`UNKNOWN`にする。
追加照会のDB診断にはcredential JSONが含まれ得るため、その詳細を出力せず一般的なWARNだけを表示する。

登録・認証・削除処理、DB schema、コマンド引数、API／CSVは変更しない。書込みコマンドの
結果表示へWebAuthn列は追加しない。キー詳細は追加出力しない。GraphicalMatrix／TOTP選択中も残存登録を表示する。
これは同一DBの保存スナップショットであり、別DB／LDAP／独自repositoryの自動検出や
認証可能性の検査ではない。Admin Toolsの表示も更新するには、そのshellを同じ配布物から更新する。

## 2. N1：初期パスワードの運用と現在画像列の保護

### 2.1 問題と採用する仕様

従来は、現在画像列だけの入力でも同じ値を`initial_sequence`へ平文で自動補充していた。そのため`sequence`をhash保存しても、同じ秘密が初期値欄に残る場合があった。画像IDをaliasへ変換するだけでは秘密の保護にならない。

v1.4.1では既存ユーザーの現在列から初期値への暗黙補充を廃止する。ただし、CLI add／set-sequenceで新規ユーザーを作る場合は、運用上の初期値必須方針に従い、その入力画像列を初期値にも設定する。初期パスワードは管理者による再通知が必要なため、検証・正規化済みの画像ID／aliasを既存の`initial_sequence`列へ平文保存する。初期値もhash化する当初案は採用しない。現在の`sequence`は従来の設定方式（hash／keyword／AES-GCM／plaintext）で保存する。

現在値が初期値と同じbootstrap期間やRESET後は、DB・backup読取者が画像要素を取得できる。初回変更の強制だけでこのリスクは解消しない。DB・backup・管理者権限・CLI出力のアクセス管理を前提とし、N1全体のDB秘匿性を解消したとは扱わない。初期値と異なる現在画像列へ変更した後は、初期値だけでその現在画像列を取得できるわけではない。通常のIdPログインには別途一次認証も必要となる。

### 2.2 登録・変更・RESETの契約

| 入力・操作 | v1.4.1の動作 |
| --- | --- |
| CLI add／set-sequenceによる新規作成 | 現在列を設定方式で保護し、入力列を平文初期値にも設定する。`force_sequence_change=1`。aliasがあれば`A,B,C,D`等へ正規化する。 |
| APIの新規登録で現在列のみ指定 | 現在列だけを設定方式で保存し、初期値は空とする。CLIの新規作成とは異なる。 |
| APIの新規登録で初期値のみ指定 | 明示bootstrapとして平文初期値と保護現在値を作り、初回変更を必須にする。 |
| 初期値と現在列を明示 | 個別に保存する。同じ画像列の場合は初回変更を必須にし、変更強制offとの指定競合を拒否する。順不同設定での同値も検出する。 |
| API／CLIの現在列のみ変更 | 初期値を補充・上書きしない。旧hash初期値も保持する。 |
| API／CLIの初期値のみ変更 | 初期値だけを平文で設定し、現在列は変更しない。世代を進め、現在列と同じ値なら変更を強制する。 |
| 変更強制をoffにする | 現在列が初期値と同じ場合は拒否する。旧hash初期値で同値を判定できない場合も拒否する。 |
| 初期値が空のRESET | `INITIAL_SEQUENCE_REQUIRED`で停止する。 |
| 旧hash初期値のRESET／移行 | `INITIAL_SEQUENCE_REENTRY_REQUIRED`で停止し、値を削除・推測しない。 |

RESETは初期値を画像IDへ解決・検証し、その時点の現在列の保存方式でencodeして現在列へ設定する。初期値自身は平文のまま保持する。APIは期待version・初期値を条件とした更新、CLIは行ロックを含むトランザクションを使う。変更強制と`state_version`更新、既存の方式切替・ロック解除・TOTP状態初期化等のRESET動作を維持する。初期値の再入力だけではRESETしない。初回変更画面は既存の全体設定`graphicalmatrix.force_sequence_change`に従う。CLIで既存行を更新しても初期値を上書きせず、既存`[unset]`や旧保護形式を自動補充・移行しない。

管理CLIの`USER RESET`と別名`reset-user USER`は、書込み処理を呼び出す前に対象ユーザーのYES/NO確認を行う。
YESで実行し、NOまたは空入力は終了コード0で中止する。入力EOFは非ゼロ終了し、いずれも未確認のままDBを変更しない。
末尾の`-y`／`--yes`で確認を省略できる。従来の`USER RESET`の引数変換で後続引数を捨てる処理を修正し、
`--apply`を含む未知引数は確認・書込み前に拒否する。自動化は`USER RESET -y`へ更新する。
RESET自体の保存先トランザクションやAPI／CSV、`reset-totp`／`webauthn-reset`の契約は変更しない。

CSV A／Mは従来どおり全状態を指定する登録・更新であり、API／CLIの部分更新とは異なる。空の初期値は未設定として保存し、現在列から補充しない。現在列を初期値から補うbootstrap CSVには変更強制onが必要。現在列を保ったまま初期値だけを再入力する場合は、管理CLIまたはAPIの部分更新を使う。

### 2.3 表示・CSV・診断

- `graphicalmatrix-db.sh`のshow／listと更新後の表示は、初期値を平文で、現在の`sequence`をDB保存値で表示する。現在列の`[protected]`表示を以前の保存値表示へ戻し、`hsp1:`／`kw1:`／`aesgcm1:`等を復号せずそのまま表示する。
- 旧hash初期値は`[reentry-required]`、旧keyword／AES-GCM初期値は`[migration-required]`と表示する。修正版の適用だけで既存のhash初期値が平文へ戻ることはない。
- APIの`excludeSequences`による既定の非表示を維持する。表示許可時だけ読める初期値を返し、旧hashは空配列と`initialSequenceStorage`／`initialSequenceRecoverable`で区別する。
- CSV previewは初期値もマスクする。portable CSVは現在列または旧初期値がhashなら出力を拒否する。初期値を現在列の代用品にせず、マスク値や偽の空値を再import可能な値として扱わない。
- `security-status`は平文／空の初期値を正常とし、旧hash／keyword／AES-GCM初期値を`initial_sequence_incompatible_rows`に数える。画像ID等の詳細検査には移行dry-runを併用する。

### 2.4 旧データの移行

平文初期値は正規化する。旧keyword／AES-GCM初期値は元の鍵があれば復号・検証して平文へ移行できる。鍵不足や不正値では停止する。hash初期値は復元できないため、管理者が元の初期値または新しい初期値を明示して再入力する。現在画像列からは補充しない。

DB用移行は200行単位で部分確定・再開し、元値・versionで競合を検出する。再実行は正規化済みの値を変更しない。移行によってTOTP seed／WebAuthn登録鍵は変更しない。外部管理しているLDAP初期値属性の自動移行は対象外となる。

## 3. N2：管理者RESET後の自己管理権限失効

### 3.1 問題と認証世代の束縛

従来は自己管理の引継ぎが認証時の世代を保持せず、変更画面で最新versionを再取得していた。旧認証の後にRESETが行われても、新世代のversionで変更権限を作れることが問題だった。

```text
Password＋選択した第二要素
  → MFA完了時に利用者・方式・世代vを照合
  → 同じ認証要求に完了証跡(v)を保持
  → 証跡を一回消費してHandoff(v)を発行
  → Handoffを一回消費し、現在の登録世代 == vを確認
  → 変更セッションの期待世代をvに固定
  → 保存先で現在世代 == vの場合だけ原子的に更新
```

最新DB値の再取得で旧権限を新世代へ昇格させない。画面表示後にRESETされた場合も、保存時の条件付き更新で拒否する。通常SSOや既存SPセッション全体の一括ログアウトは追加しない。

### 3.2 完了証跡と正規認証自身の更新

公式TOTPプラグイン2.3.1／2.3.2は、利用者情報を`UsernamePrincipal`ではなく`TOTPPrincipal`で返す。
初期の完了検査が前者だけを読んでいたため、TOTP検証成功後に`MFA factor subject binding failed`で
拒否される不具合を修正した。`authn/TOTP`の結果に限り一意の`TOTPPrincipal`を読み取り、
カスタムvalidatorの従来の`UsernamePrincipal`形式も維持する。両方ある場合は一致を必須とし、
複数利用者・別flow・Passwordとの不一致・世代不一致は引き続き拒否する。DBの利用者名や可変な
SubjectContextで本人の紐付けを補完せず、guardやMFA強制を無効にしない。seed／登録情報の変更は不要。

公式WebAuthnプラグイン1.4.2の第二要素モードでも、`UsernamePrincipal`が付かない成功結果を
扱えるよう修正した。`authn/WebAuthn`に限り、公式の成功結果生成処理が設定した
`SubjectCanonicalizationContext`の正規化名を、そのSubjectが選択結果のSubjectと同一オブジェクトで
あり、過去結果でなく、正規化エラーがなく、名前が空でない場合だけ使用する。username principalが
存在する場合は一意かつ正規化名との一致を必須とする。無関係・内容だけ等しい別Subject、第一認証の
名前だけ、WebAuthn user handleで代用しない。Password・guardとの一致、flow、現在登録状態・世代の
検査を維持する。公式TOTP／WebAuthnプラグイン自体・設定・登録済みキーを変更せず、追加の
運用コマンドや設定は不要。通常のパッケージ再ビルド・更新で反映する。

`GraphicalMatrixSelfServiceAuthorizationContext`は、同じ`ProfileRequestContext`直下に、利用者、`stateVersion`、期待する第二要素flow、Password／第二要素の認証結果への参照、自己管理profile IDを保持する。

MFA完了検査に成功した場合だけ証跡を生成する。通常SSO・bypassでは生成せず、開始・拒否・エラー時は旧証跡を除去する。自己管理認証ではforceAuthn、新しい認証結果、利用者・profile・非負versionと認証結果の束縛を検査し、一回消費する。証跡が欠落した場合にDBの現在値や残存guardで補完しない。

認証中の強制画像列変更やLDAP検証時のカウンター更新など、正規フロー自身の世代進行は、その試行の条件付き更新成功に基づく旧→新versionだけをguardへ反映する。`GraphicalMatrixVerifyResult`の`beforeVersion`／`afterVersion`を使い、更新後の再検索で取得した無関係な世代へ付け替えない。LDAPの誤選択後の正規再試行は可能とし、第二要素の成否自体は従来どおり判定する。

### 3.3 一回限りのHandoffと変更セッション

| サーバー側属性 | 必須条件 |
| --- | --- |
| `graphicalmatrixSelfService.authorizationFormat` | Integerの`2` |
| `graphicalmatrixSelfService.user` | 検証済みの空でないString |
| `graphicalmatrixSelfService.stateVersion` | 非負のLong |
| `graphicalmatrixSelfService.expiresAt` | Long、`now < expiresAt` |
| `graphicalmatrixSelfService.nonce` | 発行ごとの推測困難な空でないString |
| `graphicalmatrixSelfService.profile` | 固定の自己管理profile ID |

発行・消費・クリアを同一HTTPセッションの排他区間で処理する。消費時は全属性をコピーして除去し、不正・期限切れでも再利用させない。期限加算はオーバーフローを検査する。

変更画面では登録の存在・ACTIVE・ロック状態と、Handoffのversion一致を確認する。変更セッションにも`graphicalmatrixChange.authorizationFormat=2`と期待versionを明示し、旧形式を現在値で補完しない。互換用LDAP入口にも同じ形式を付ける。

画像列保存、方式変更、TOTP登録開始、WebAuthn開始前の照合等で期待versionを維持する。不一致・期限切れ・保存先確認不能では権限をクリアし、再認証を要求する。WebAuthn登録開始後の別引継ぎに関するN5の解消は、この対応には含めない。

### 3.4 RESET競合・監査・構成上の限界

| RESETのタイミング | 旧操作の扱い |
| --- | --- |
| 第二要素完了前 | guard照合で拒否し、完了証跡を作らない。 |
| MFA完了後・Handoff消費前 | 旧versionを保持し、消費時の不一致で拒否する。 |
| 消費時の読取り後・画面表示後 | 保存・方式変更等の条件付き更新で拒否する。 |
| 保存と同時 | 保存先の原子的更新順に従う。RESETが先なら旧保存を成功させない。 |

`SELF_SERVICE_AUTH`、`SELF_SERVICE_HANDOFF`、`CHANGE_SAVE`、`CHANGE_METHOD_SAVE`等の既存監査イベントを使用する。実機では旧フォームの方式更新に対して`CHANGE_METHOD_SAVE result=ENROLL_REQUIRED detail=state_changed_after_verification`を確認した。Handoff拒否のHTTP 403はローカルServlet試験で確認しており、実機の全拒否経路が同じHTTPステータスになるとは扱わない。

JVM内のセッション同期だけで、複数ノードが同じセッションを同時処理する構成の一回性は保証しない。共有ストアの原子的take等が必要となる。直接SQL／LDAP編集でのversion巻戻し、古いDBの稼働中復元、削除・再作成によるversion再利用は別途セッション失効が必要となる。

## 4. N3：SP adopt時の属性値制限保全

### 4.1 問題と自動移行の範囲

従来は`AttributeRule`の属性名だけから組込みprofileを推定し、元の値フィルターを削除してRequester＋ANYを生成していた。たとえば`uid`の`ValueRegex ^staff-.*$`が失われ、送信範囲が全値へ広がり得た。

`AdoptionAttributePlan`でprofile、元XMLのhash、policy ID、元fragmentを固定し、次の範囲だけを自動変換する。

1. 対象policyと削除対象が一意である。
2. 要求条件は、対象entity IDと完全一致する単一Requesterである。
3. 各AttributeRuleは`uid`、または重複のない`uid`と`mail`である。
4. 各属性は単一のPermitValueRule ANYだけを持ち、deny・追加条件・参照・未知要素を持たない。
5. namespaceと`xsi:type`のQNameが既知の型へ解決される。
6. 元の送信条件と生成後の条件が、この対応範囲で同等である。

`none`は属性名を抽出できない場合のfallbackにしない。対象の属性規則がなく、保持する規則へ影響しないと確認できる場合だけ使用する。

### 4.2 拒否と変更検知

Value／ValueRegex、DenyValueRule、複合条件、RequesterRegex、条件参照、未知の型、複数policy、解析不能な構成は自動変換しない。共通policyや複数resourceを単一policyへ無条件にまとめず、無関係な共通policyも変更しない。

値制限の実際の拒否診断は`ERROR: ATTRIBUTE_VALUE_RESTRICTION`と非ゼロ終了である。未解決・曖昧・非対応profileには`ATTRIBUTE_POLICY_UNRESOLVED`、`ATTRIBUTE_POLICY_AMBIGUOUS`、`ATTRIBUTE_PROFILE_UNSUPPORTED`等を使用する。旧設計案にあった`ADOPT_BLOCKED`等を実装済みの出力とは扱わない。

dry-runとapplyで同じ検査を使い、applyの書込み前に元XML等を再確認する。変更があれば`CONFIG_CHANGED`で停止し、計画で固定したpolicyだけを削除する。`--apply --confirm ENTITY`は対象確認であり、値制限喪失の許可ではない。

拒否時はmetadata provider、metadataファイル、Attribute Filter、MFA設定、registryを保全する。途中失敗時は退避した原本を復元し、復元失敗を成功表示しない。複数ファイル全体の原子性や外部エディターまでの共通lockは保証しない。

### 4.3 旧adopt済みSPの扱い

旧版で失われた値制限は新版の適用だけでは戻らない。adopt前backup、legacy XML、revisionと現在のANY設定を比較し、必要な制限を復旧する。旧policyと管理ANYを両方有効にしただけでは、ANY側から送信が続く可能性がある。

同等性の確認ではfiltered AACLIとSP受信を使い、一致・不一致・属性なし・複数値混在を比較する。SPでの権限昇格や追加属性受信を実証したとは扱わず、2026-10-30の検証結果は第6章の範囲に限定する。

## 5. N4：アクセス初期化時の既存制限保全

### 5.1 問題と初期化の許可条件

従来の`stockCondition()`はRelyingPartyId、SimpleAttribute、`eppn`等から標準例に似たConditionを削除可能と判断していた。代替policyがない場合、既存の許可値制限が失われ得た。v1.4.1ではこの判定とCondition削除経路を廃止する。

| ContextCheckの状態 | `access init`／`--apply`の結果 |
| --- | --- |
| Conditionなし・Functionなし・対応するローカル構成 | 管理functionの追加を計画／適用できる。 |
| Conditionなし・既知の管理functionのみ | 再実行可能。functionやflowを重複追加しない。 |
| Conditionあり | 標準例、ワイルドカード、実値allowlist、複合条件を問わず競合として保持する。 |
| 管理functionとConditionが併存、または独自Functionあり | 条件削除・上書き・自動chainをせず停止する。 |
| 重複定義、import／alias、未対応profile条件等 | 判定不能な構成を未設定扱いせず停止する。 |
| ContextCheck設定ファイルなし | moduleの別途有効化・設定確認を案内し、自動作成・有効化しない。 |

コメント内の例は有効なConditionと扱わない。namespace、`id`／`name`の予約名、重複等を検査し、既知管理functionはBean ID・class・単一constructor引数`%{idp.home}`等で確認する。class名や識別コメントだけを所有権の根拠にしない。Spring式や任意コードを実行して既存条件の意味を推定しない。

### 5.2 計画・適用・復元

1. ContextCheck、relying-party、properties、policy、catalogの変更をメモリー上で計画する。
2. 既存条件・独自function・未知構成・未対応flowを検出したら、dry-run／applyとも書込み前に停止する。
3. apply直前に対象の存在状態とbytesを再照合し、差分があれば`CONFIG_CHANGED`で停止する。
4. 原本bytes、存在状態、所有者・group・modeを退避する。
5. 管理functionと接続を適用し、policy／catalogは存在しない場合だけ作る。既存のルール・値を初期値で上書きしない。
6. 関連propertiesと権限を反映し、整合性確認の成功後だけ`APPLY_OK`を表示する。
7. 途中失敗では今回書いたファイルを退避状態へ戻し、今回新規作成したものだけを削除する。復元直前に第三者の変更があれば上書きせず`RECOVERY_REQUIRED`で停止する。

単一ファイルの置換は既存のatomicWriteを使う。複数ファイル全体の原子性は保証しない。管理作業は同時実行せず、全検査が終わるまでbuild／reload／restartを行わない。

`postAuthenticationFlows`は既存内容と順序を維持し、`context-check`がなければ末尾へ一回追加する。既に一回ある場合は位置を維持する。重複・動的式・参照・未知list要素を無確認で単純化しない。

### 5.3 CLI診断と既存認可の移行

| 状態 | 診断 |
| --- | --- |
| 既存Condition／独自Functionと競合 | `state=CONTEXT_CHECK_CONFLICT`、`result=NO_CHANGE`、非ゼロ終了 |
| ContextCheck module未準備 | `state=CONTEXT_CHECK_MODULE_REQUIRED`、`result=NO_CHANGE`、非ゼロ終了 |
| 正常適用 | `state=ACCESS_PENDING_RESTART`、`result=APPLY_OK`。build・restart・status確認が別途必要 |

`context_condition_stock`を廃止し、`context_condition_action=PRESERVE`を使用する。条件を無条件に捨てるforceオプションは追加しない。

既存条件は、その意図、対象SP、属性・許可値、関連XMLと現在の許可／拒否例を退避し、隔離構成で同等のpolicyまたは手動統合functionを設計する。表現できない条件は既存構成を継続する。許可値・不一致・属性欠落・複数値・対象外SP・deny優先・例外時を確認してから切り替える。条件だけ削除して初期化を通さない。

`GraphicalMatrixSpAccessFunction`／`GraphicalMatrixSpAccessEvaluator`の実行時policy判定は変更しない。policy未設定SPの従来の扱いも維持する。旧初期化で削除済みの条件はbackup等から別途復旧する。初期化成功だけで認可の同等性や稼働中の反映完了を保証しない。

## 7. 更新・移行・切戻し

### 7.1 更新手順

1. 設定、DB／LDAPの必要な保存先、storage secret、policy、catalog、registry、metadataを同一世代でbackupする。過去に失われた制限はbackupと比較して別途復旧する。
2. 複数ノードでは自己管理経路を一旦停止し、旧ノードがリクエストを受けない状態で、Pluginと実際に使用するAdmin Toolsを同じ修正版へ更新する。
3. 通常のPlugin更新・build・restart手順を実施する。旧形式の引継ぎ・変更画面は再利用せず、再認証する。
4. 初期値の再入力や移行が必要なら、管理書込・自己管理操作を停止した状態で実施する。現在列から初期値へ補充しない。
5. 隔離した検証利用者でRESET後の旧権限拒否と新しい認証を確認する。通常ログイン、SP設定verify、監査、サービス状態を確認して自己管理を再開する。
6. SP adopt／アクセス初期化が必要な場合だけdry-runを行い、既存条件と競合したら停止する。N4の正常適用後はbuild・restartと実際の許可／拒否確認が必要となる。

旧Admin Toolsの`adopt`／`access init --apply`を継続しない。旧候補版と修正版がともにv1.4.1である場合、version文字列だけでなく、使用する配布物とチェックサムを確認する。

自動化で管理CLIのRESETを呼び出す場合は`USER RESET -y`または`reset-user USER --yes`へ変更する。
確認なしの実行は明示オプションが必要となり、旧例の`USER RESET --apply`は拒否される。

### 7.2 初期値の再入力・移行コマンド

旧hash初期値は元の値または新しい初期値を標準入力で明示する。次はコマンド形式であり、利用者名・実際の初期値は管理者が指定する。

```bash
sudo /opt/shibboleth-idp/bin/graphicalmatrix-db.sh set-initial-sequence USER --stdin
```

画像IDまたはaliasのカンマ区切りを1行入力し、改行後にCtrl+Dで入力を終了する。端末入力は表示されるため画面共有・記録も管理する。この操作だけでは現在画像列を変更しない。RESETは必要な場合に別途実施する。

```bash
sudo /opt/shibboleth-idp/bin/graphicalmatrix-db.sh security-status
sudo /opt/shibboleth-idp/bin/graphicalmatrix-db.sh migrate-sequence-storage --dry-run
sudo /opt/shibboleth-idp/bin/graphicalmatrix-db.sh migrate-sequence-storage --apply
sudo /opt/shibboleth-idp/bin/graphicalmatrix-db.sh migrate-sequence-storage --dry-run
```

applyはdry-runの内容とbackupを確認してから実施する。200行単位の部分確定を考慮し、後続batchの失敗を全体取消しと誤認しない。旧backup・CSV・履歴の秘密はDB行の移行だけで消えないため、保管・廃棄と必要な画像列変更を別途管理する。

### 7.3 切戻し

DDL変更がなくても、旧版への切戻しでN2〜N4の旧動作が再び可能になる。自己管理・管理初期化の対象経路を停止し、必要な操作セッションを失効させて復旧する。認証エラーを解消するためにDBのversionを旧値へ巻き戻さない。

XML等は同じ退避世代の関連設定を使い、既存制限を復旧して許可／拒否を確認する。policyだけ空、Conditionだけ削除した状態で再開しない。旧hash初期値を復元可能な平文と見なした切戻しも行わない。

## 8. 性能・影響範囲・配布物

### 8.1 性能とTOTP／WebAuthnへの影響

- N1の変更は主に登録・管理・RESET・移行時の処理であり、現在画像列の通常認証方式を変更しない。移行時はbatch更新・世代進行が発生するためメンテナンス中に実施する。

共通buildにより、固定名／version付きのPlugin、Admin Tools、Dashboard、SP Import Toolsをv1.4.1として生成し、アーカイブ内容・manifest version・SHA256SUMSを検査した。生成アーカイブは未署名であり、リリース鍵による署名・公開は行っていない。テスト環境への適用済みという状態と、一般公開済みという状態は区別する。
