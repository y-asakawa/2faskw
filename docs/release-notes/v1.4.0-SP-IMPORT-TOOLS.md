# v1.4.0: SP Import Tools　[Beta]

## 変更概要

一般的なShibboleth IdP、または既存2FAS-KW IdPの設定から既存SPを調査し、別の2FAS-KW IdPへ既存CLIで登録する
独立したJava 21移行支援ツールを追加する。ユーザーの入口は`graphicalmatrix-sp-import.sh`の1本。
定期同期、既存IdP内のadopt、MFA enrollmentや秘密鍵の移行ではない。

## 実装構成

- `sp-import-tools/`: 独立Maven project。既存pluginのJAR/classpathへ依存しない。
- `SourceAnalyzer`: service resource、静的list/ref/import、property/path、provider、属性条件を追跡する。
- `ManagedSourceAnalyzer` / `ManagedData`: registry schema 1/2とcatalog/access policy schema 1を実XML/MFA設定と照合する。
- `StrictJson`: Jackson coreによる型・重複キー・未知項目・深さ/件数制限付き読込。任意classの生成は行わない。
- `ManagedAccessWiring`: source ContextCheckの既知functionとSAML2.SSO接続を静的確認する。
- `SecureXml`: namespace・行/列付きSAX解析。DTD/外部entity/schema取得と過大入力を拒否する。
- `MigrationBundle`: TXT閲覧資料とhash付き内部manifestを生成。metadataは単一SPの元bytesを保持する。
- `ExistingCli`: 引数配列で既存CLIを直列実行。承認/profile/add/verifyと段階結果を記録する。
- `ManagedMigration`: 管理modeの前提比較、共有profile、属性承認、add/access set/disable、実状態照合、段階再開を扱う。
- `SpImportMain`: 引数mode、番号選択、source確認、最終確認、bundle再照合、再実行を扱う。

## 登録・失敗モデル

解析・exportだけなら元/新IdPを変更しない。新IdP更新は既存CLIの通常の管理動作として行う。
属性同時移行modeでは元属性集合とtarget profileを照合し、resolver/mapping不足をnoneで迂回しない。
明示的な属性後設定modeは後述のとおり、未完了を残す別の登録方式とする。
必要な属性承認はclassification/purposeを管理者が明示し、既存CLIで行う。
適用前に対象・方針を表示し、`REGISTER 件数`を要求する。

全SP一括transactionは設けない。途中失敗時は以後の処理を停止し、成功済みSPや承認/profileは保持する。
再実行では前回計画とbundle hashを比較し、既存SPの実状態をverifyする。無確認update/removeはしない。
元IdPを変更しないこと、CLI verify成功とSP側SSO切替が別であることを結果へ記録する。

## 2FAS-KW間移行の追加設計・実装

`--source-type auto|shibboleth|2faskw`を追加する。autoはregistry存在で管理modeを選び、
破損・未知schemaではfallbackしない。旧一般bundle v1の読取を維持し、管理bundle v2へ必要最小限の
管理intentと全体MFA比較値を格納する。ユーザーが読む結果は従来どおりTXTである。

ACTIVE管理SPの管理名、entityID/metadata、属性profile/description、SP別MFA/CIDRs、
release/access属性承認、allow/denyとenabled状態を移す。schema 1の欠落access状態はpolicy実体から読む。
台帳hash/ACS/証明書、実filter/profile、MFA、policy revisionの不一致、孤立policy、未知ContextCheckは保留する。
管理台帳の`acsUrls`では、同じURLを使う複数のACS要素を本体が配列へ保存する場合がある。
この正規の本体出力を`duplicate values: acsUrls`で拒否していた読取互換性を修正した。
ACS配列だけを読取時に重複整理し、metadataとのURL集合比較、hash、その他の重複検査は維持する。
元IdPの台帳・XML、既存本体の登録処理には変更を加えない。
DISABLED/REMOVED、未管理SP、history/revision/legacy XML、ユーザー/credential/秘密鍵は自動移行しない。

適用前にtargetの管理初期化、drift、ACS許可、resolver/mapping、profile/名前/entityID衝突を確認する。
全体MFAの6項目はコピーせず一致を要求する。差分があれば別途変更を判断して新計画を作る。
access移行時はtargetの全体access有効化とContextCheck初期化・反映を事前に完了する。
既存承認・descriptionの差は明示確認でtarget保持し、releaseをaccess承認で格下げしない。

書込順序は承認、共有profile、SP add/verify、access set、必要時disable、最終構成照合である。
全体transactionを設けないため、適用は`--confirm-isolated-target`と`ISOLATED TARGET`対話確認を必須とする。
実際のネットワーク遮断は管理者が実施する。元disabled policyもsetで一旦enabledになるので隔離を維持する。

resumeは前回bundle/計画/target実状態を比較する。add成功・access失敗の場合はaddを繰り返さず
残ったaccess設定から再開する。disableだけ失敗した場合も既知の中間状態として復帰する。
未知のpolicy変更、SP hash/profile/MFA/CIDR/ACTIVE差分は停止し、自動update/deleteしない。
主要設定の変更検知は行うが共通CLI lockではなく、排他的な管理作業が前提となる。

追加成果物は`managed-policy-diff.txt`、`plan-sha256.txt`、`approved-actions.tsv`、
`managed-execution-state.tsv`、`managed-result.txt`である。`CONFIG_VERIFIED`は構成照合だけを示す。
結果のREADY_FOR_CUTOVER/CUTOVER_VERIFIEDはNOT_CONFIRMEDとし、browserでallow/deny/属性欠落/
MFA/NameID/署名信頼を試験した管理者だけが切替を判断する。

## 初期版の制限

静的に解釈できない条件は理由付きで保留する。MDQの全SP一覧は保証しない。
Inlineは一覧解析だけとする。ファイルaggregateは既定で保留し、一般モードの明示抽出のみ後述条件で対応する。複雑なfilter、deny/値条件、
resource factoryは登録保留する。一般モードの非空RP overridesは後述の認可分離方式で扱うが、
その設定を自動コピーしない。管理モードでは従来の保留を維持する。

sourceのXML署名・稼働中の実効設定は自動検証しない。
target CLI連携対象は1.3.5/1.4.0。全構成の移行互換性を保証するものではない。

## 標準Attribute Filter解析の互換性修正

実IdPで報告された`ATTRIBUTE_CONDITION_UNSUPPORTED`と`ATTRIBUTE_POLICY_UNRESOLVED`に対して、
standalone解析を拡張した。IdP本体・認証・既存SP CLI・元サーバ設定は変更しない。

- 子要素のない`permitAny="true"`/`1`を全値許可として解析する。不正値や子ルール併記は保留。
- `EntityAttributeExactMatch`をrequirementとpermitの両方で扱い、対象SPのentity-levelタグを照合する。
- 全値許可条件のAND・ORに対応し、`releaseAllValues`、subject-id要求の`pairwise-id OR any`等を判定する。
- literal Name/Value、明示NameFormat、raw-XML modeに限定する。変換済みAttributeRegistryを推測しない。
- タグ不一致は許可なし、判定不能は保留とする。未知の加工Provider filter、曖昧なinline/aggregate、Assertion、
  複合値・nil・非文字列型、動的式・未知条件を無条件許可へ変換しない。
- TXTへ判定結果、未解決理由、元の位置を記録する。元XML・台帳bytesとbundleの整合性を保持する。
- SP専用policyと管理profileの比較、および共通policyの追加属性比較は、次節の属性分離方式で行う。
- 旧bundleの上書きは行わない。修正版では新しい`--export-dir`で元設定を再解析する。

追加テストはstandard permit/tag forms、subject-id OR、nested AND/OR、タグ欠落/不一致、
mapped-only/dynamic/未知条件、provider filter、role/namespace境界、複合値、TXT根拠、
bundle往復、元bytes保持、管理profile driftを対象とする。
Java 21でツール全112件のテスト、独立パッケージbuild、ZIP内容・manifest検査、
梱包済み入口の`--version`確認が成功した。生成ZIPはローカル検証用の未署名成果物であり、
この修正について共通buildの本体・Dashboardテストは再実行していない。
実サーバのSSO・移行適用は、この追加検証の対象外である。

## 管理profileと共通送信属性の分離

実IdPの`uid-mail-release=uid,mail`に、標準`alwaysRelease`の`schacHomeOrganization`が
加わる構成を、管理profileの不整合と誤判定していた。standalone importerだけを修正する。

1. `2faskw-管理名`のSP専用policyのRequesterと属性集合を管理profileに照合する。
   欠落・重複・未知条件・属性差分は保留する。`none`は専用policyなしを許容する。
2. その他の適用policyの追加属性を、管理profileとの重複を除いて別の契約として記録する。
   `release_attributes`は全体集合、`managed_profile_attributes`と`additional_release_attributes`は内訳となる。
3. profile作成・承認ではSP専用属性とaccess依存属性だけを使用する。
   共通policyや共通専用属性の承認をコピー・自動作成しない。
4. 新IdPの既知・未フィルタのmanaged providerと登録予定metadataを使い、追加属性を事前解析する。
   不足・過剰は`TARGET_ADDITIONAL_RELEASE_DIFFER`、判定不能は`TARGET_ADDITIONAL_RELEASE_UNRESOLVED`、
   resolver/mapping未準備は`TARGET_ADDITIONAL_ATTRIBUTE_NOT_READY`で書込み前に停止する。
5. 読み込んだ設定のhashと追加属性の意味を、確認時・実行時・各CLI書込み前後に再照合する。
   TXTの`additional-release-check.txt`に根拠と差分を保存する。途中失敗時は新IdPの隔離を維持する。

managed manifest v2のintentに任意の`releaseContract`を追加する。旧v2は旧来の単一属性集合として
読めるが、旧HELD bundleの保留理由は解除しない。新機能には新しい出力先での再解析が必要である。
新bundleは修正版ツールで読み込む。集合の重複・和集合・承認依存関係と件数上限を検査する。
対象がすべて保留の場合、選択できない番号の入力を繰り返させず、TXTの確認を案内して停止する。

追加検証では、共通属性の分離・重複、専用policyの欠落/変更/重複、`none`、新規profile作成、
移行先の不足/過剰/未知条件/metadata filter、providerの親構成、resolver/mapping未準備、
確認後とCLI適用後の変更、別参照ファイルのhash固定、旧v2、bundleの重複集合拒否を確認した。
Java 21でツール全131件のテストが成功した。実サーバのSSO/移行適用と本体・Dashboardの
再試験はこの修正の検証対象外である。修正版ZIPはローカル検証用の未署名成果物とする。

## 一般IdPのSP登録とアクセス制御の分離

非空RP overrideを全SPへ一括して`RP_DEPENDENCY_UNRESOLVED`としていた判定を、
一般IdPモードだけ登録判定と認可判定に分ける。既存plugin・認証・SP管理CLIは変更しない。

### 解析と成果物

- `registration_state`はREVIEW/HELD、`access_control_state`はNONE_OBSERVED/
  MANUAL_REQUIRED/UNRESOLVED/LEGACY_UNASSESSEDとする。静的な未検出は制限なしの保証ではない。
- `SourceAccessAnalyzer`はliteralなRelyingPartyByNameをentityIDで照合し、一致しないoverrideを除外する。
  ref・動的selector等の範囲は推測せず、未解析として必要な確認を表示する。
- 必要時に標準ContextCheck XMLを読む。非標準の自己完結したsnapshotは
  `--context-check-config FILE`で指定する。成功した読取は元設定のhash再照合対象へ加える。
- AND/OR/NOT、literalなSP selector、SimpleAttributePredicateのmap、RegexAttributePredicateを
  静的に記述する。SPだけで決まる分岐を整理し、regexの文字列・NOT・属性参照方式を維持する。
  未指定useUnfilteredAttributesは元IdP版の既定確認が必要である。
- Function/script/SpEL/Springの実行、importの自動展開、CLI allow/denyへの変換は行わない。
  属性欠落・wildcard・scoped値・NOTの意味を保証せず、管理者の同等性確認を要求する。
- `access-control.txt`へSP別条件、位置、RPのprofile設定と未解析理由を記録する。
  NameID・暗号化・認証・独自interceptも移行先で別途確認する。
- 新一般manifest v4は候補ごとの認可記録を必須とし、欠落・重複・孤立・未知状態を拒否する。
  旧v3も読み込める。旧v1はLEGACY_UNASSESSEDとして読み、既存HELDを解除しない。管理v2は変更しない。
  制御文字は表示用にescapeし、1000根拠/候補・manifest 32 MiBを上限とする。

### 登録限定applyと再開

認可が未移行の候補を通常applyすると書込み前に停止する。隔離された新IdPで登録だけ進めるには
`--registration-only --confirm-isolated-target --apply`と`REGISTER ONLY ISOLATED`対話確認を要求する。
既存のsource確認・登録件数確認も維持する。全候補の承認状態を確認してから属性承認/profile/addを実行する。
flagsはfirewallを変更せず、隔離は管理者が実施する。認可の設定は書き込まない。

登録verify成功は`REGISTERED_ACCESS_PENDING`、既存確認は`VERIFIED_EXISTING_ACCESS_PENDING`となり、
成功した解析・dry-run・登録でも認可が未移行なら終了コード10とする。前提不足・実エラーは各失敗codeが優先する。
`access-control-status.txt`へ認可未適用・browser試験未確認を明記し、移行完了と誤認させない。
認可再構成と許可/拒否browser試験までは隔離を維持する。

一般plan-v3は移行先実パス、登録限定/隔離/metadata確認flags、bundle hashとCLI選択内容を固定する。
manifest再読取では認可根拠の一致も確認する。resumeも同一条件と再確認を必要とし、
旧plan-v1/v2を自動再開しない。管理bundleの登録限定指定は拒否し、既存の全policy移行を維持する。

### 残る制限と検証

曖昧なaggregate抽出、任意のprovider filter実行、属性値限定release、未知resourceによる登録保留は維持する。
今回の分離だけで全SP、特にfederationのaggregateを自動登録できるわけではない。
新しい出力先で再解析し、元/新host双方で修正版を使用する。同梱README、FAQ、操作manual、
コマンドreference、英語のdevelopment/historyに同じ仕様を記載する。

単体テストではSP範囲、AND/OR/NOT、fallback、nested bean ID、regex/参照方式、未知式/ref/Function、
非標準path/hash、v4/v3/旧v1、追加確認の取消、書込前の停止、登録後・既存verify後の未移行状態を検証する。
実IdPへの適用・browser SSO・Linuxのsudo適用は未実施であり、模擬CLIの合格とは区別する。
Java 21によるツール全156件のテスト、独立package build、ZIP内容・manifest検査、
梱包済み入口の`--version`/`--help`を確認する。本体・Dashboardは今回変更せず再試験対象外とする。
修正版ZIPはローカル検証用の未署名成果物であり、公開Releaseには通常の署名・検証が必要である。

管理者権限での出力はSecureDirectoryStream対応filesystemを必須とする。
macOS等でこのAPIがない場合は、権限昇格なしの解析・dry-runだけを利用できる。

## 多数SPのmanifest容量制限の修正

多数のSPと詳細な解析・認可根拠を保存すると、旧4 MiB制限によって解析結果の出力が失敗する。
これはツールの容量制限であり、元IdP設定の不正を示すものではない。

- manifest専用上限を32 MiBとし、出力・再読込・実行前hash照合へ一貫して適用する。
- 共通BLOCK/ERROR診断はDレコードへ一度だけ保存する。読込時には全候補へ復元し、
  metadata、managed intent、entityID重複の検査前に保留状態を確定する。
- 容量超過時は実byte数、上限、`--entity-id`による絞込みを表示する。
  出力先へ不完全なbundleは公開しない。
- JSON入力と再開planの4 MiB制限は変更しない。認可未移行の終了コード10や登録保留を解除しない。

検証には248候補の合成データを使用し、4 MiB超のmanifestの出力・再読込・hash照合、
属性解析根拠と認可根拠の保持、共通保留の復元、32 MiB超の拒否を確認する。

## 一般IdPの標準beanと集合メタデータの改善

### 目的と境界

### 標準内部設定の分類

- 想定された`system/conf/relying-party-system.xml`、`relying-party-mddriven.xml`、

## 原因分類とSP別移行作業の改善

### 対象と目的

同じ`ATTRIBUTE_CONDITION_UNSUPPORTED`でも、属性IDの空白・欠落と、意図された値限定/deny、
独自条件の未対応では作業が異なる。共通の親metadataの期限切れと重なる場合も、
期限更新だけで全保留が解消すると誤解しないよう、原因分類とSP固有の作業順を表示する。

### 診断と分類

- `Diagnostic.reason()`は既存の診断detail先頭から限定したreasonを読む。旧診断の理由は推測しない。
- `SourceAnalyzer.attributeHold`は元のBLOCKコードを維持し、引用した属性ID・policy・条件根拠を残す。
  ID欠落/空白/形式と条件未対応を独立して記録し、両方の問題があれば両方を表示する。
- `attributeReason`/`valueLimited`はnamespaceと既知の構造・設定を限定して、値限定/denyの
  手動移行と未解釈の追加調査を区別する。条件の評価・正しさの保証・script実行は行わない。
- `MigrationGuidance`は元設定確認、原本更新、metadata/filter確認、属性条件の手動移行、
  追加調査、抽出方式確認、管理整合性、認可別途移行、移行先試験へ分類する。
  分類件数はSP内の重複を除き、分類間は重複する。確認完了や登録可否を意味しない。

### SPごとの具体的な作業

一覧には対象ファイル位置・コード・reasonと簡潔な作業順を表示する。
`d 番号`と新しい`migration-actions.txt`には実際のentityID/管理名・policy・属性ID・
条件値・認可根拠と完了確認を表示する。元設定の意図確認・バックアップ、信頼するmetadataの
更新・署名/期限確認、共通の親原本への依存、抽出が困難な場合の別管理provider等を案内する。

値限定/denyは新IdPのfilter resourceへ同等条件を設計し、共通/管理policyとの組合せを確認する。
filtered AACLIとSP受信属性で一致値・不一致値・空値・複数値混在を試験する。
属性送信とログイン認可は区別し、許可/拒否、SP信頼/NameID/暗号化/SSO/MFAの試験まで隔離を維持する。

### 非変更事項と制約

属性IDはtrim・改名せず、値限定/denyを全値送信へ変換しない。手動移行対象はHELDを維持し、
移行先への手動設定だけでは解除しない。必要なら信頼済み単体metadata・適切なprofile・
手動filterを使う既存CLIの別手順を管理者が計画する。元条件の削除やANY置換で回避しない。

`migration-actions.txt`は任意の説明資料であり、自動実行計画・承認・検証結果ではない。
編集/削除でfingerprintや登録可否は変わらず、旧bundleにも必須化しない。
manifest schema・選択番号・隔離/承認・終了コード、既存認証・DB・SP管理CLIは変更しない。
詳しいreasonがない旧bundleは、必要に応じ新版で元IdPを未使用の出力先へ再解析する。

## SP登録と属性設定の二段階移行：追加詳細設計

### 対象と入口

一般Shibboleth bundleのtarget段階へ `--defer-attributes` を追加する。既定の属性同時移行と
2FAS-KW管理modeは保持する。管理bundleではこの指定を拒否し、元の管理意図を破棄しない。
元解析だけの指定も拒否する。認証・DB・配備済みSP管理CLIの内部コードは変更しない。

第一段階は名前・entityID・metadata・MFA/CIDRsの登録と構成照合のみ。属性profileは
builtinの `none` に固定し、targetでstatus=OK・source=builtin・空属性集合を確認する。
属性discover、classification/purpose入力、attributes approve、profile createは行わない。
第二段階のresolver/mapping・属性承認・profile・値filter・認可は管理者が既存CLI等で行う。
同じ属性の分類・用途をSPごとに無確認で上書きする問題を、この登録経路では発生させない。

### 保留の分離

`DeferredRegistration.view` はcanonical Analysisを複製する。候補個別の
`ATTRIBUTE_CONDITION_UNSUPPORTED` と `ATTRIBUTE_POLICY_UNRESOLVED` のBLOCK/ERRORだけを
登録viewでREVIEWとする。元severity/code/location/detail/remedyをfactsへ残し、
元bundle・XML・diagnostics・fingerprintは変更しない。条件を解決したと判断しない。
全体診断と一致するものは分離せず、metadata期限/不備、provider/filter、その他の保留も維持する。
snapshot bytesがない候補やentity/root不一致は実行不可とする。

未知policyが残る場合、解析済み属性集合が網羅的とは限らない。値限定・deny・不明条件を
全値送信へ変換せず、第二段階で根拠を確認して同等条件を再構成する。
通常modeの保留解除やTXT手編集による承認は行わない。

### 隔離・確認・結果

applyは `--registration-only --confirm-isolated-target` と
`DEFER ATTRIBUTES ISOLATED` の入力確認を必須とする。元の認可未移行なら既存の
`REGISTER ONLY ISOLATED`、要確認metadataなら原本確認flagと
`VERIFY SOURCE METADATA` も維持する。フラグは署名検証・firewall変更を行わない。
実行前に全planがnone/no approval/no profile creationであることを再確認し、逸脱なら書込前に停止する。

dry-run/登録段階完了の終了コードは11とし、前提不備・CLI失敗等の失敗codeが優先する。
段階結果はDRY_RUN_ATTRIBUTES_PENDING、REGISTERED_ATTRIBUTES_PENDING、
VERIFIED_EXISTING_ATTRIBUTES_PENDING。全体移行やSSO確認済みと表示しない。
run配下の0600 `attribute-migration-todo.txt` に実SP名・元属性集合・policy・診断・
元条件の根拠・未移行認可と必要な後工程を残す。next-stepsにも隔離継続を記載する。

noneは管理profile由来の追加送信がないだけで、既存共有attribute-filter policyによる
送信を禁止しない。第二段階の設定、filtered AACLIの一致/不一致/属性なし/複数値混在、
SP受信属性、認可の許可/拒否、NameID/暗号化、署名信頼、実SSO/MFAの確認まで隔離を維持する。
既存CLIのset-attributesでprofileを割り当て、必要な値条件を別途同等に設定する。

### 計画・再開

属性後設定modeはplan-v4へmode、bundle fingerprint、target実path、隔離/登録限定/metadata確認flag、
選択entity/name/none/MFA/CIDRs/metadata hashを固定する。従来属性同時移行plan-v3は変更しない。
mode変更によるresumeは計画不一致として拒否する。存在するSPは再追加せずexact verifyする。
第二段階でprofileを変更済みなら不一致で停止し、noneへ上書きしない。
成功済み操作は保持し、batch rollbackや自動削除を行わない。

### 有効期限の再検証

`MetadataValidity.check` で固定snapshotをSecureXml解析し、MD EntityDescriptor root/entityIDを
照合する。EntityDescriptor/SPSSODescriptor/RoleDescriptorのvalidUntilを現在時刻と比較する。
元aggregateの継承期限/cache制約は抽出時にrootへ反映済みであり、そこも再確認対象となる。

一般/管理modeともtarget準備開始時、対話確認後の全選択SP書込前、各SP登録時、
add dry-run後かつadd apply直前に確認する。全選択SPの一つでも期限切れなら初回書込前に止める。
処理中に期限が過ぎた場合は以後の登録を止め、先行成功を保持する。
時刻と同値は期限切れ。malformed validUntilは入力不正として拒否する。
無関係なforeign extensionのdateはmetadata期限と扱わず、未指定期限は創作しない。
