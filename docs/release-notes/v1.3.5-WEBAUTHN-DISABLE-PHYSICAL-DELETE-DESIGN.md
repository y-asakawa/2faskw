# 2FAS-KW v1.3.5 WebAuthn停止・物理削除詳細設計

実装状態: 実装・リポジトリ回帰検証済み、実IdP結合試験待ち

## 1. 文書の目的

本書は、2FAS-KW登録を`DISABLED`にしたWebAuthn利用者が、既存のWebAuthn credentialと
Password認証を使ってMFAを完了できる問題への修正方針を定義する、v1.3.5の詳細設計兼
リリースノートである。

修正はWebAuthnだけへ個別条件を追加するのではなく、GraphicalMatrix、TOTP、WebAuthnに共通する
登録状態判定へ統合する。運用コマンドは、資格情報を保持する一時停止の`disable`と、登録情報を
物理削除する`delete USER`を維持する。`deprovision`や`purge`は追加しない。

本書は実装仕様と配布前の受入条件を示す。単体・package試験に加え、実IdPと公式WebAuthn Pluginを
用いた結合試験が完了するまでは、公開リリース済みとして扱わない。

## 2. 対象バージョン

本変更の配布対象はv1.3.5とする。基準実装はv1.3.4であり、v1.3.4以前の公開済みtagや成果物は
変更しない。

v1.3.5の実装完了時に`version.ini`、Maven成果物、plugin metadata、Admin Tools、Dashboard、
文書内versionを一括更新する。設計だけの段階では、配布成果物をv1.3.5として生成しない。

## 3. 背景

現行実装では、MFA方式を決める`findMfaSettings()`が登録の`status`を取得しない。WebAuthnを
選択すると、WebAuthn成功後に2FAS-KW登録状態を再確認せずMFAが完了する。

また、`graphicalmatrix-db.sh delete USER`は登録行を物理削除する。登録なしをMFA省略対象として
許可する構成では、停止済み登録を削除すると利用者が「未登録」と判定され、BYPASS経路で
Passwordだけの認証へ戻る可能性がある。

v1.3.5では物理削除の運用を維持したうえで、登録なしを既定拒否にする。未登録者をBYPASSで許可する
既存環境だけ、互換設定を明示する。

アカウント停止と終了後の情報削除を区別する考え方は、一般的なidentity lifecycleとも整合する。
[NIST Subscriber Accounts](https://pages.nist.gov/800-63-4/sp800-63a/accounts/)も、suspensionと
termination後の情報削除を分けている。ただし2FAS-KWでは、恒久停止状態を保持する中間コマンドは
追加せず、第一認証側の停止確認と物理deleteを運用で組み合わせる。

## 4. 運用方針

### 4.1 disable

一時停止は既存コマンドを使用する。

```bash
sudo /opt/shibboleth-idp/bin/graphicalmatrix-db.sh disable USER
```

- `status=DISABLED`へ更新する。
- GraphicalMatrix sequence、initial sequence、TOTP seed、WebAuthn credentialを保持する。
- SP・IPのBYPASSより優先して認証を拒否する。
- 再開時は`enable USER`でACTIVEへ戻す。

### 4.2 enable

```bash
sudo /opt/shibboleth-idp/bin/graphicalmatrix-db.sh enable USER
```

DISABLEDの登録をACTIVEへ戻す。保持されたcredentialを再利用できる。物理削除済み利用者には行が
存在しないため、enableでは復元できない。新規provisionとcredential再登録が必要である。

### 4.3 delete

恒久的な登録情報削除は既存コマンドを維持する。

```bash
sudo /opt/shibboleth-idp/bin/graphicalmatrix-db.sh delete USER
```

このコマンドは物理削除であり、deprovision相当の論理状態へ変換しない。新しいpurgeコマンドへも
分離しない。

deleteの対象は次のとおりとする。

- `graphicalmatrix_enrollment`の対象行
- 行内のGraphicalMatrix sequenceとinitial sequence
- 行内のTOTP seedと登録状態
- 対象利用者に対応するWebAuthn StorageService credential

WebAuthn credentialが別保存先にあるため、処理順序を次のようにする。

1. 対象利用者とcredential保存先を確認する。
2. 対象行をDISABLEDへ更新してcommitし、新規認証を拒否する。
3. WebAuthn credentialを削除する。
4. credential削除結果を確認する。
5. `graphicalmatrix_enrollment`行を物理削除する。
6. 削除件数と結果を監査記録する。

WebAuthn credential削除が失敗した場合は、登録行をDISABLEDのまま保持して失敗を返す。行を先に
削除しない。再度`delete USER`を実行すると、残ったcredential削除から安全に再開できるようにする。

既存の`--with-webauthn --apply`は互換入力として当面受け付けてもよいが、v1.3.5では通常の
`delete USER`が関連WebAuthn credentialを含む完全削除を行うため、非推奨として警告する。

### 4.4 CSV provisioning

Provisioning modeのCSV action `D`は物理deleteに変更しない。従来どおり一時停止として扱う。

```text
D -> status=DISABLED
```

外部IDMの削除通知を直ちに物理削除へ変換しない。物理削除が必要な場合は、管理者が対象と第一認証側の
停止を確認して`delete USER`を実行する。

## 5. Security invariant

v1.3.5は次の条件を満たす。

1. `DISABLED`はSP・IPのBYPASSより優先して拒否する。
2. 登録なしを、停止されていない利用者と暗黙にみなさない。
3. MFA必須時は、方式選択前と第二要素成功後に最新の登録状態を読み取る。
4. MFA全体の過去の認証結果だけで、今回の状態判定を省略しない。
5. Passwordと第二要素が同一利用者に結び付くことを証明できない場合は拒否する。
6. 保存先障害、欠落status、多値status、不正方式を認証成功へ変換しない。
7. deleteは関連WebAuthn credentialを含む物理削除として完了する。
8. deleteの部分失敗時はDISABLED行を保持し、認証可能なmissing状態へしない。
9. delete後のmissingは既定のmissing policyで拒否する。
10. 失敗理由やcredential情報を利用者向け画面または通常ログへ露出しない。

## 6. 状態とBYPASS

### 6.1 登録状態

| 状態 | 意味 | 認証 | credential |
|---|---|---|---|
| `ACTIVE` | 通常利用中 | ポリシーと方式に従って許可 | 使用可能 |
| `DISABLED` | 一時停止またはdelete途中失敗 | 常に拒否 | 保持または削除途中 |
| missing | 未登録または物理削除済み | 既定拒否 | 原則なし |

### 6.2 missing policy

新しい設定を追加する。

```properties
graphicalmatrix.mfa.missingEnrollmentPolicy = deny
```

値は次の2種類だけを受け付ける。

| 値 | 動作 |
|---|---|
| `deny` | REQUIRE、BYPASSの両方で登録なしを拒否する。既定値。 |
| `allow-on-bypass` | 既存MFAポリシーがBYPASSを返した場合だけ登録なしを許可する。 |

空値、未知値は設定エラーとしてfail closedにする。`allow-on-bypass`は移行用互換設定であり、設定検査と
起動ログで警告する。

`allow-on-bypass`環境でdeleteすると、対象利用者はmissingとなり、第一認証だけでBYPASS認証できる
可能性がある。このためCLIと管理APIは、互換設定が有効な場合にdeleteを拒否する。管理者は次の
どちらかを完了してから実行する。

1. `missingEnrollmentPolicy=deny`へ変更する。
2. LDAP等の第一認証アカウントを停止し、運用確認を完了する。

第一認証停止を2FAS-KWが機械的に検証できない構成では、設定をdenyへ変更する方法だけを自動deleteの
許可条件とする。

### 6.3 判定表

| 保存先の結果 | REQUIRE | BYPASS |
|---|---|---|
| ACTIVE、対応方式 | 第二要素へ進む | 状態確認後に省略可能 |
| DISABLED | 拒否 | 拒否 |
| missing、policy=deny | 拒否 | 拒否 |
| missing、policy=allow-on-bypass | 拒否 | 許可 |
| status欠落・空・未知・多値 | 拒否 | 拒否 |
| ACTIVE、方式欠落・未対応 | 拒否 | 拒否 |
| 保存先障害・検索結果不正 | 拒否 | 拒否 |

## 7. 認証フロー

### 7.1 開始判定

Password成功後に次を実行する。

1. `authn/Password`の成功Subjectから利用者を一意に確定する。
2. SP・IPのMFAポリシーを評価する。
3. DBまたはLDAPからstatus、MFA方式、方式固有の準備状態を取得する。
4. 第6.3節の判定表を評価する。
5. 拒否時はカスタム失敗イベントを設定してMFAを終了する。
6. 明示的なmissing+BYPASSだけは監査後に第二要素を省略する。
7. REQUIREでは利用者、方式、選択flow、追跡IDを認証処理単位のGuardContextへ保存する。

利用者不明、保存先障害、方式不明をGraphicalMatrixへfallbackさせない。

### 7.2 完了判定

GraphicalMatrix、TOTP、WebAuthnの成功遷移に共通CompletionStrategyを接続する。

- GuardContextがPRECHECK_PASSEDであることを確認する。
- Password利用者が開始時と一致することを確認する。
- 実行された第二要素flowが開始時の選択と一致することを確認する。
- 第二要素結果が同じ利用者に結び付くことを検証する。
- 保存先から最新状態を再取得する。
- ACTIVE、方式一致、方式固有準備完了の場合だけMFAを成功させる。
- DISABLED、missing、方式変更、保存先障害は拒否する。

第二要素SubjectにUsernamePrincipalがない場合、方式別SubjectBindingValidatorで同一利用者との結び付きを
証明する。検証方法がない場合は拒否し、単に比較を省略しない。

### 7.3 SSO結果再利用

トップレベルMFA結果の再利用で状態判定を飛ばさないため、実効設定を次とする。

```properties
idp.authn.MFA.reuseCondition = shibboleth.Conditions.FALSE
```

PasswordやWebAuthn等の下位flow結果は各flowのreuse conditionに従って再利用できる。ただし再利用された
第二要素もCompletionStrategyによる利用者結合と最新状態確認を通す。

### 7.4 失敗イベント

| イベント | 対象 |
|---|---|
| `GraphicalMatrixAccessDenied` | DISABLED、登録なし、方式・利用者不整合 |
| `GraphicalMatrixServiceUnavailable` | 保存先障害、timeout、処理context異常 |

`conf/authn/authn-events-flow.xml`へend-stateとglobal transitionを追加する。ローカルエラー画面を
表示する構成では、`conf/errors.xml`の`shibboleth.LocalEventMap`と
`messages/messages.properties`も同時に更新する。

## 8. 保存先設計

### 8.1 DB

既存`status VARCHAR(32)`とstatus indexを利用する。本件のための新しい状態列は追加しない。

MFA設定取得はstatus、mfa_method、totp_status、totp_seedの有無を同じSELECTで取得する。開始と完了は
別の読み取りを行い、ACTIVE結果をsessionまたはTTL cacheへ保存しない。

deleteは対象行をDISABLEDへ変更した後、WebAuthn credential削除成功を確認してから行をDELETEする。
途中失敗時はstatus=DISABLEDの行を保持する。

### 8.2 LDAP

LDAPではstatus属性の欠落、空値、単一値、複数値、読み取り例外を区別する。現在の`attr()`のように
欠落と例外を空文字へ統合するhelperはstatus判定に使用しない。

LDAP保存の物理削除では、enrollment entryとWebAuthn credential保存先の両方を処理する。credential
保存先を特定できない場合は、enrollment entryを先に削除せずDISABLEDで停止する。DB用CLIを実行して
LDAP登録も削除されたとみなさない。

## 9. 管理操作

### 9.1 CLI

予定するCLI契約は次のとおりである。

```bash
# 一時停止する。credentialは保持する。
sudo /opt/shibboleth-idp/bin/graphicalmatrix-db.sh disable USER

# 一時停止を解除する。
sudo /opt/shibboleth-idp/bin/graphicalmatrix-db.sh enable USER

# enrollmentと関連credentialを物理削除する。
sudo /opt/shibboleth-idp/bin/graphicalmatrix-db.sh delete USER
```

`delete USER`は現行どおりDBを変更するコマンドとし、deprovisionやpurgeへ名称変更しない。実行前に
対象利用者、現在status、MFA方式、WebAuthn credential件数、missing policyを表示する。秘密値は
表示しない。

### 9.2 管理API

- `POST /users/{id}/disable`: DISABLEDへ遷移する。
- `POST /users/{id}/enable`: DISABLEDからACTIVEへ遷移する。
- `DELETE /users/{id}`: enrollmentと関連credentialを物理削除する。

DELETEは先に対象行をDISABLEDへ更新する。関連credential削除に失敗した場合は5xxを返し、DISABLED行を
残す。成功時だけ行を削除し、`deleted=true`を返す。

### 9.3 CSV provisioning

Provisioning modeの`D`は従来どおりDISABLEDへの一時停止とし、物理削除しない。大量の物理削除は
CSV自動取込の対象にしない。

## 10. 監査

次を監査イベントとして記録する。

```text
MFA_ACCESS_DENIED
MFA_SERVICE_UNAVAILABLE
ENROLLMENT_DISABLED
ENROLLMENT_ENABLED
ENROLLMENT_DELETE_STARTED
ENROLLMENT_DELETE_CREDENTIAL_REMOVED
ENROLLMENT_DELETE_COMPLETED
ENROLLMENT_DELETE_FAILED
ENROLLMENT_DELETE_UNSAFE
```

記録項目は時刻、操作主体、対象利用者、SP、認証方式、変更前後status、`state_version`、理由コード、
credential削除件数、correlation IDとする。sequence、initial sequence、TOTP seed、WebAuthn credential、
Password、session cookieは記録しない。

## 11. 設定診断

`graphicalmatrix-plugin-check.sh --config-only`で次を確認する。

- MFA DecisionStrategyがstatusを読む実装である。
- 全第二要素成功経路にCompletionStrategyがある。
- カスタム失敗イベントが定義されている。
- ローカルエラー表示時はLocalEventMapとmessageが定義されている。
- `idp.authn.MFA.reuseCondition`が所定の値である。
- `missingEnrollmentPolicy`が既知値である。
- `allow-on-bypass`使用時は警告する。
- LDAP status属性とcredential保存先が設定されている。
- MFAを通らない成功経路は自動確認不能として手動確認を要求する。

## 12. 移行

### 12.1 配備前調査

1. ACTIVE、DISABLED、不正status、status欠落の件数を確認する。
2. BYPASS対象で2FAS-KW未登録の利用者数と業務影響を確認する。
3. 管理APIまたはCLIのdeleteを呼び出す外部処理を確認する。
4. WebAuthn StorageServiceの種類と対象利用者credential削除方法を確認する。
5. LDAP保存時はstatus属性のACLと多値有無を確認する。
6. IdPクラスタ全nodeの設定と保存先整合性を確認する。

### 12.2 missing policy移行

未登録+BYPASSを現在利用している環境は、初回更新時だけ`allow-on-bypass`を明示して互換動作を維持できる。
対象利用者をprovisionした後、`deny`へ変更する。新規環境は常に`deny`から開始する。

互換設定を使用している期間は、物理deleteを行わない。第一認証停止を外部手順で確認してdeleteする
必要がある場合は、作業中だけmissingをdenyにできるかを先に確認する。

### 12.3 既存deleteオプション

現行の`delete USER --with-webauthn --apply`を使用する自動処理は、v1.3.5で`delete USER`へ移行する。
互換オプションを受け付ける期間も、処理結果は同じ完全物理削除とする。

## 13. 試験

### 13.1 認証試験

- ACTIVEのGraphicalMatrix、TOTP、WebAuthnが正常に認証できる。
- DISABLEDの3方式がREQUIRE／BYPASSとも拒否される。
- missing+denyがREQUIRE／BYPASSとも拒否される。
- missing+allow-on-bypassがBYPASSだけ成功する。
- WebAuthn開始後にdisableしても、完了判定で拒否される。
- 既存MFA SSO結果がある状態でdisableし、次の要求が拒否される。
- 第二要素Subjectの利用者欠落、複数、不一致が拒否される。
- DB／LDAP障害がExternalまたはPassword成功へfallbackしない。
- カスタムイベントが設定方針どおりの一般エラーになる。

### 13.2 delete試験

- `delete USER`がenrollment行と関連WebAuthn credentialを物理削除する。
- TOTP seedとGraphicalMatrix credentialが行とともに残らない。
- WebAuthn削除失敗時にDISABLED行が残り、認証を拒否する。
- 失敗後の`delete USER`再実行で削除を完了できる。
- missing policyがdenyの場合、delete後にBYPASS認証できない。
- allow-on-bypassの場合、安全条件未確認のdeleteを拒否する。
- API DELETEもCLIと同じ順序と結果になる。
- CSV provisioningのDは物理削除せずDISABLEDにする。
- delete済み利用者のenableは失敗し、新規provisionが必要になる。
- 監査ログにcredential値が残らない。

### 13.3 配布・回帰試験

- 旧v1.3.4データを保持したまま更新できる。
- LDAP保存とDB保存の両方で同じ状態判定になる。
- Admin Tools、Dashboard、CSV importの表示が状態を正しく認識する。
- API curl test、CLI regression、package regression、Maven testが成功する。
- 実際のShibboleth WebAuthn Pluginを用いた結合試験を行う。
- 複数IdP nodeでdisableが全nodeの新規認証へ反映される。

## 14. 受入条件

次をすべて満たした場合だけv1.3.5のF-01対応を完了とする。

1. DISABLEDのWebAuthn利用者が、新規認証、処理途中の停止、SSO再利用の全ケースで拒否される。
2. GraphicalMatrixとTOTPも同じ状態判定を通る。
3. BYPASSがDISABLEDを上書きしない。
4. 登録なしの既定動作がdenyである。
5. `delete USER`が関連credentialを含む物理削除として動作する。
6. deleteの部分失敗がDISABLEDを保持してfail closedになる。
7. DB構成で実機試験が完了し、LDAP保存では状態guardの試験とdirectory側削除手順が確認されている。
8. 全IdP nodeへJARと設定が一組で配備されている。
9. 未登録BYPASS利用者の移行または互換設定が完了している。
10. 利用者向け表示と監査ログに秘密情報が含まれない。

## 15. ロールバック

旧版へ戻すとF-01と、物理delete後のmissing+BYPASS復帰リスクが再発する。JARだけ、またはMFA遷移だけを
部分的に戻さない。

緊急切戻し時は、対象利用者をLDAP等の第一認証側でも停止し、WebAuthn認証経路または対象SPを
制限してから、v1.3.4のJARと対応設定へ一組で戻す。物理削除済みcredentialは復元しない。

本件では新しいDB列を追加しないため、schema rollbackは不要である。
