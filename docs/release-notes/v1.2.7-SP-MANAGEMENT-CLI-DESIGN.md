# 2FAS-KW v1.2.7 SP管理CLI 詳細設計

## 1. 目的

新しいSAML Service Provider（SP）を追加する際に、IdP側で必要となるSP metadataの
登録、属性リリース、2FAS-KW MFA方針の設定を、一つの管理CLIで一貫して実施する。

対象はShibboleth IdP 5.2系と2FAS-KWであり、CLIはIdPサーバ上でroot権限により実行する。
利用者やSP管理者がWeb画面から直接登録する機能は含めない。

SP管理用のHTTP API、管理Web UI、Webhook、リモート実行agentはv1.2.7では実装しない。SPの
追加・更新・停止・復元を行える入口は、IdPサーバへログインした管理者が`sudo`で実行する
`graphicalmatrix-sp.sh`だけとする。API endpoint、listener port、管理用token、API credentialは
配布物・設定・Jetty webappのいずれにも追加しない。

本書はv1.2.7で実装したSP管理CLIの設計、セキュリティ境界、運用手順を記録する
リリースノートである。

## 2. 結論

実現可能である。現在の手作業は、SPごとに次の3箇所を更新している。

1. `conf/metadata-providers.xml`と`metadata/*.xml`へSP metadataを登録する。
2. `conf/attribute-filter.xml`へSP entityIDに完全一致する属性リリース方針を追加する。
3. `conf/graphicalmatrix/mfa-policy.properties`へSP単位のMFA方針を追加する。

ただし、SPサーバそのものの構築、TLS証明書の発行、SP秘密鍵の生成・保管、SP側への
IdP metadata設定は、製品や運用主体ごとに異なる。そのためv1.2.7のCLIはそれらを遠隔で
操作しない。SPがHTTPSで公開するmetadata、またはSP管理者が提供するmetadataファイルを
受け取り、IdP側の信頼設定を作る範囲に限定する。

この境界により、IdPからSPの秘密鍵を扱わず、SSH接続情報やSP管理者権限も不要になる。

## 3. 現行の連携構造

```text
利用者
  -> SPの保護ページ
  -> SPが署名付きAuthnRequestをIdPへ送信
  -> IdPがSP metadataから entityID / ACS / SAML署名鍵を解決
  -> 2FAS-KWが entityID と送信元IPでMFA要否を判定
  -> IdPが属性フィルタを entityID に適用
  -> IdPが署名済みResponseをmetadata記載のACSへ返す
  -> SPがIdP署名を検証し、アプリケーションsessionを作成
```

現在の手順は[INSTALL_NEW_SP.md](../INSTALL_NEW_SP.md)にある。
SPを識別する正本は利用者向けURLやACS URLではなく、metadata内の`EntityDescriptor/@entityID`
である。MFA方針もこの文字列の完全一致で判定する。

## 4. 採用する方式

### 4.1 SP metadata

新規SPごとに`FilesystemMetadataProvider`を`metadata-providers.xml`へ追加する現方式は、
数件なら単純だが、SP数に比例してXML編集・再起動・ロールバックが増える。

v1.2.7では、初期化時に1回だけ`LocalDynamicMetadataProvider`を導入する。
以後のSP追加・更新・停止は、専用directory内のmetadataファイルだけで行う。

```xml
<MetadataProvider id="GraphicalMatrixManagedSPMetadata"
    xsi:type="LocalDynamicMetadataProvider"
    sourceDirectory="%{idp.home}/metadata/2faskw-managed-sp"
    refreshDelayFactor="0.02"
    maxCacheDuration="PT8H"
    maxIdleEntityData="PT30M"/>
```

`LocalDynamicMetadataProvider`は、SPのentityIDに対応するmetadataを必要時にdirectoryから
解決する。新規metadataは初回のAuthnRequest時に自動認識されるため、SP追加ごとのJetty
再起動は不要である。削除・置換時は、CLIが`reload-metadata.sh -id GraphicalMatrixManagedSPMetadata`
を実行してresolverのキャッシュを明示的に無効化する。

標準reload scriptの接続先はShibbolethの`IDP_BASE_URL`に従う。通常は空の
`graphicalmatrix.sp.reload.baseUrl`を維持してShibboleth既定の`http://localhost/idp`を使う。
localhost:80でIdPを公開しない同居検証環境では`http://127.0.0.1:8080/idp`のようなloopback URLを
設定し、CLI wrapperが子processへ`IDP_BASE_URL`として渡す。管理flowを外部へ公開しない。

MetadataProviderの`id`はXMLの`NCName`でなければならず、数字で始めてはならない。初期版で使用した
`2FAS-KWManagedSPMetadata`は無効であるため、現行実装は`GraphicalMatrixManagedSPMetadata`を正とし、
`init --apply`時に旧IDを検出した場合は同じproviderのIDだけを自動移行する。旧IDでresolverの
初期化が失敗したIdPは、移行後にJettyを再起動して復旧する。

標準のファイル名はentityIDのSHA-1を小文字16進数化して`.xml`を付けたものになる。これは
IdPの仕様であるため、CLIが算出する。運用者がファイル名を手入力しない。

### 4.2 属性リリース

属性リリースはSPのmetadata登録とは別の認可であり、metadataに要求属性が書かれていても
自動releaseしてはならない。既定値は`none`とし、追加直後のSPには属性を渡さない。

CLIは管理対象だけを含む`attribute-filter-managed-sp.xml`を生成する。初期化時に、この
ファイルを既存のAttribute Filter service resourceへ1回だけ追加する。更新後は
`reload-service.sh -id shibboleth.AttributeFilterService`で反映する。

v1.2.7で提供する属性profileは以下に限定する。

| profile | releaseする属性 | 用途 |
| --- | --- | --- |
| `none` | なし | 追加直後の既定。属性を使わないSP、または要件確認中。 |
| `uid` | `uid` | 内部アカウント照合だけが必要なSP。 |
| `uid-mail` | `uid`, `mail` | メール通知など明確な用途があるSP。 |
| `custom` | 指定した事前定義profile | 組織が承認したprofileだけを選択可能にする。 |

`custom`は任意XML入力を受け付けない。`sp-management.properties`で定義したprofile名と、
許可済みattribute IDの組合せだけを使う。LDAP password、GraphicalMatrix sequence、TOTP seed、
WebAuthn credential、管理ロールはprofile候補に含めない。

### 4.3 MFA方針

現在の`mfa-policy.properties`は単一ファイルから毎回読み込まれる。別propertiesを追加しても
2FAS-KWは自動で読まないため、v1.2.7のCLIは既存ファイルの`forceSPs`、`bypassSPs`、
`requiredSPs`、`bypassSpCidrs`を構造化して更新する。registryで管理していない既存のSP値は
保持し、CLI管理SPの値だけを追加・更新・除去する。同じpropertyが複数行ある設定は安全に
統合できないため拒否する。

初期化時に、手管理の既存値をこのブロックへ移行するか、手管理のままにするかを明示的に選ぶ。
両方を同じpropertyへ重ねることはできないため、移行前にCLIが重複と既存値を表示し、
`--apply`なしでは変更しない。

標準profileと対応する方針は以下とする。

| MFA profile | 更新先 | 意味 |
| --- | --- | --- |
| `inherit` | 更新しない | `default`、既存のnetwork rule、required ruleに従う。 |
| `force` | `forceSPs` | 送信元CIDRのbypassより優先してMFAを要求する。 |
| `bypass` | `bypassSPs` | 常にMFAを省略する。明示承認が必要。 |
| `sp-cidr-bypass` | `bypassSpCidrs` | 指定SPかつ指定IPv4 CIDRだけMFAを省略する。 |

`requiredSPs`は「列挙したSP以外をMFA不要にする」性質を持つため、新規SP追加の標準profileに
は使わない。運用者が既にallow-list方式を採用している場合だけ、`--mfa required`を明示して
追加できる。

### 4.4 既存の手作業登録SPの検出

`status`はregistryに存在するCLI管理SPだけでなく、現在のIdP metadata設定を読み取り、
手作業で登録済みのSPを検出する。これは読み取り専用であり、既存のmetadata、attribute filter、
MFA方針を変更しない。

検出対象と表示内容は以下とする。

| metadata source | `status`での扱い |
| --- | --- |
| `FilesystemMetadataProvider` | `metadataFile`を安全に解析し、各`EntityDescriptor/@entityID`、ACS、署名鍵fingerprintを表示する。 |
| `LocalDynamicMetadataProvider` | `sourceDirectory`を走査し、entityIDと標準SHA-1 file nameの整合性を確認する。 |
| `InlineMetadataProvider` | 設定内のentityIDを表示する。 |
| `FileBackedHTTPMetadataProvider` | provider ID、metadata URL、backing file、最終更新時刻を表示する。backing fileが読める場合だけentity数を表示する。 |
| `DynamicHTTPMetadataProvider` | provider IDとURL templateを表示する。実体のSP一覧は外部metadata serviceへ問い合わせず`UNKNOWN_REMOTE`とする。 |
| `ChainingMetadataProvider` | 子providerを設定順のまま展開して表示する。 |

出力の各SPには、`MANAGED`、`EXISTING_LOCAL`、`REMOTE_SOURCE`、`DUPLICATE_ENTITY_ID`、
`INVALID_METADATA`、`UNRESOLVED`のいずれかの状態を付与する。

```text
SOURCE                         ENTITY ID                                      STATUS
GraphicalMatrixManagedSPMetadata https://library.example.org/shibboleth         MANAGED
LegacyPartnerMetadata          https://legacy.example.org/shibboleth          EXISTING_LOCAL
FederationAggregate            https://federation.example/metadata            REMOTE_SOURCE
```

`status`はmetadata sourceを読み取り、同じentityIDが複数sourceに存在する場合を
`DUPLICATE_ENTITY_ID`として警告する。属性releaseとMFA方針の安全な解釈は、対応している
`FilesystemMetadataProvider`を`adopt`する際に実施する。

既存SPをCLI管理へ取り込む`adopt`は、`status`で一意に検出できた
`FilesystemMetadataProvider`だけを対象とする。
`adopt`はmetadata digest、現行属性release、MFA方針を表示し、`--apply`とentityIDの再入力が
なければregistryへ記録しない。最初の`adopt`は設定を書き換えず、元のファイル内容と設定断片を
revision `legacy-original`として保存する。

adopt後は、以下の二種類の復元を使い分ける。

- `rollback`: CLIで行った直前または指定revisionの変更を戻す。管理対象の現在状態を以前のrevisionへ戻す。
- `restore-legacy`: adopt前の手作業登録状態へ戻し、CLIが導入したmetadata、属性profile、MFA ruleを除去する。

この二つを分けることで、「最新版を一つ前へ戻す」と「CLI管理化そのものを取り消す」を混同しない。

## 5. CLIの構成

配布物へ次を追加する。

```text
/opt/shibboleth-idp/bin/graphicalmatrix-sp.sh
/opt/shibboleth-idp/conf/graphicalmatrix/sp-management.properties
```

シェルscriptは権限・外部command・IdP pathの確認だけを担当する。metadata XML解析、JSON
registry、propertiesの行保存編集、原子的書込みはJava 21の
`GraphicalMatrixSpManagementTool`が担当する。このクラスは既存の2FAS-KW plugin JARに含め、
SP管理専用のHTTP APIや別listenerは追加しない。

XMLを文字列置換で処理しない。XML parserではDTDと外部entityを無効化してXXEを防ぎ、
metadataの解析では最大サイズ、要素数、証明書数、URL長を制限する。

### 5.1 コマンド

```bash
# IdP metadata sourceを読み取り、既存の手作業登録SPも含めたinventoryを表示する。
# 変更しない。
sudo /opt/shibboleth-idp/bin/graphicalmatrix-sp.sh status

# CLIが作成・adoptしたSPだけを表示する。
sudo /opt/shibboleth-idp/bin/graphicalmatrix-sp.sh list

# statusと同じ全inventoryを機械可読JSONで出力する。
sudo /opt/shibboleth-idp/bin/graphicalmatrix-sp.sh list --all --format json

# 現在のIdP状態から、次に実行する安全なcommandを表示する。変更しない。
sudo /opt/shibboleth-idp/bin/graphicalmatrix-sp.sh next

# LocalDynamicMetadataProviderと管理用attribute filter/MFA blockを導入する。
# 初回はdry-run、内容を確認した後だけ--applyを付ける。
sudo /opt/shibboleth-idp/bin/graphicalmatrix-sp.sh init
sudo /opt/shibboleth-idp/bin/graphicalmatrix-sp.sh init --apply

# metadataを取得・検証し、追加予定を表示する。
sudo /opt/shibboleth-idp/bin/graphicalmatrix-sp.sh add \
  --name library \
  --entity-id https://library.example.org/shibboleth \
  --metadata-url https://library.example.org/Shibboleth.sso/Metadata \
  --attribute-profile uid \
  --mfa force

# dry-runで表示されたSHA-256を確認してから適用する。
sudo /opt/shibboleth-idp/bin/graphicalmatrix-sp.sh add ... \
  --approve-sha256 <metadata-sha256> \
  --apply

# ローカルで受領したmetadataを使う場合。
sudo /opt/shibboleth-idp/bin/graphicalmatrix-sp.sh add \
  --name library \
  --entity-id https://library.example.org/shibboleth \
  --metadata-file /secure/incoming/library-metadata.xml \
  --attribute-profile uid \
  --mfa force \
  --approve-sha256 <metadata-sha256> \
  --apply

# metadata、属性profile、MFA方針を更新する。更新前に現在値との差分を出す。
sudo /opt/shibboleth-idp/bin/graphicalmatrix-sp.sh update library --metadata-url ...
sudo /opt/shibboleth-idp/bin/graphicalmatrix-sp.sh set-attributes library uid-mail --apply
sudo /opt/shibboleth-idp/bin/graphicalmatrix-sp.sh set-mfa library sp-cidr-bypass \
  --cidrs 192.168.10.0/24 --apply

# SPごとの変更履歴を確認し、直前または指定revisionへ戻す。
sudo /opt/shibboleth-idp/bin/graphicalmatrix-sp.sh history library
sudo /opt/shibboleth-idp/bin/graphicalmatrix-sp.sh rollback library --revision 3
sudo /opt/shibboleth-idp/bin/graphicalmatrix-sp.sh rollback library --revision 3 --apply \
  --confirm https://library.example.org/shibboleth

# IdPから一時的に利用不能にする。metadataを削除せずregistryへ停止状態を記録する。
sudo /opt/shibboleth-idp/bin/graphicalmatrix-sp.sh disable library --apply

# 再有効化する。
sudo /opt/shibboleth-idp/bin/graphicalmatrix-sp.sh enable library --apply

# registry、metadata、属性方針、MFA方針を一括削除する。二重確認を必要とする。
sudo /opt/shibboleth-idp/bin/graphicalmatrix-sp.sh remove library --apply --confirm library

# IdPの現在の反映状態と、指定metadataの差分だけを確認する。
sudo /opt/shibboleth-idp/bin/graphicalmatrix-sp.sh verify library
sudo /opt/shibboleth-idp/bin/graphicalmatrix-sp.sh check-update library --metadata-url ...

# 手作業登録SPを検出後、CLI registryへ取り込む。設定は表示・承認後だけ更新する。
sudo /opt/shibboleth-idp/bin/graphicalmatrix-sp.sh adopt legacy-partner \
  --entity-id https://legacy.example.org/shibboleth
sudo /opt/shibboleth-idp/bin/graphicalmatrix-sp.sh adopt legacy-partner \
  --entity-id https://legacy.example.org/shibboleth \
  --apply --confirm https://legacy.example.org/shibboleth

# adopt前の手作業設定へ完全に戻す。対象entityIDの再入力を必須にする。
sudo /opt/shibboleth-idp/bin/graphicalmatrix-sp.sh restore-legacy legacy-partner \
  --apply --confirm https://legacy.example.org/shibboleth
```

更新系の既定はdry-runとし、`--apply`がなければIdP設定、metadata、registryを一切変更しない。
`remove`と`bypass`は追加の明示確認を要求する。

### 5.2 次の操作を案内する`next`

`next`は現在のIdP設定とSP登録状態を確認し、次に実行すべき操作を順番に表示する。
このコマンド自体は設定を変更しない。SP管理機能の有効状態、managed metadata provider、
managed属性filter、registry、metadata sourceおよびMFA policyを確認対象とする。

出力は、最初に`state`と`reason`を示し、その後に`[現在の手順/全手順]`形式で操作を表示する。
補足説明と実行コマンドを分離し、実行コマンドは字下げして表示する。

```text
$ sudo /opt/shibboleth-idp/bin/graphicalmatrix-sp.sh next
state=NOT_INITIALIZED
reason=The managed metadata provider or attribute filter is not initialized

============================================================
Next Steps
============================================================

[1/4] Review the planned initialization changes
      This command does not modify any configuration.

  sudo /opt/shibboleth-idp/bin/graphicalmatrix-sp.sh init

[2/4] Apply the reviewed changes
      Run this command only after confirming the output from step 1.

  sudo /opt/shibboleth-idp/bin/graphicalmatrix-sp.sh init --apply

[3/4] Restart Jetty to load the new IdP configuration
      The metadata provider is not active until Jetty reloads its configuration.

  sudo systemctl restart jetty-idp.service

[4/4] Verify the initialization result

  sudo /opt/shibboleth-idp/bin/graphicalmatrix-sp.sh status
```

`next`が状態と案内を正常に表示した場合の終了コードは0とする。`REVIEW_REQUIRED`も、
確認手順を正常に表示できた場合は0である。引数不正は2、設定ファイルの読込み失敗などの
実行時エラーは1を返す。

| 状態 | 意味 | 表示する次の操作 |
| --- | --- | --- |
| `DISABLED` | SP管理機能全体が無効。 | 設定ファイルで機能を有効化し、`next`を再実行する。 |
| `NOT_INITIALIZED` | managed metadata providerまたはmanaged blockが未導入。 | `init`のdry-run、`init --apply`、Jetty再起動、`status`の順に表示する。 |
| `INITIALIZED_EMPTY` | CLI基盤は導入済み、管理SPがない。 | allowlistの編集、`add`のdry-run、SHA-256承認付きの`add --apply`を表示する。 |
| `EXISTING_SP_DISCOVERED` | 手作業登録SPを検出し、registryには未登録。 | 既存SPの確認、`adopt`のdry-run、反映、検証を表示する。 |
| `ACTIVE` | 管理対象SPが整合している。 | SP名指定時は`verify NAME`とSSO試験、全体表示時はSP一覧と各SPのSSO試験を案内する。 |
| `DISABLED` | `next NAME`で指定したSPが無効。 | `enable NAME`のdry-run、反映、検証を表示する。無効のままSSO試験は案内しない。 |
| `NOT_FOUND` | `next NAME`のSP名がregistryにない。 | `list`で正しい名前を確認し、再指定または新規追加するよう案内する。 |
| `REVIEW_REQUIRED` | duplicate entityIDまたは不正なmetadataを検出。 | `status`による確認と手動修正だけを案内し、自動変更コマンドは表示しない。 |

SP名を指定しない`next`は、SP管理機能の無効、未初期化、要確認、既存手作業SP、管理SPなし、
正常の順に判定し、最初に該当した状態を表示する。`next NAME`は指定したmanaged SPだけを表示する。
`next --all`は、検出したすべての手作業SPとmanaged SPについて個別の状態と操作を表示する。
`next --all`とSP名は同時に指定できない。

### 5.3 運用者が実行する順序

#### 初めてCLIを導入する場合

```bash
# 1. 現在の手作業登録SPと設定差異を確認する。
sudo /opt/shibboleth-idp/bin/graphicalmatrix-sp.sh status
sudo /opt/shibboleth-idp/bin/graphicalmatrix-sp.sh next

# 2. 予定されるIdP設定差分を確認する。ここでは何も変更しない。
sudo /opt/shibboleth-idp/bin/graphicalmatrix-sp.sh init

# 3. 内容を確認した後にだけ反映する。
sudo /opt/shibboleth-idp/bin/graphicalmatrix-sp.sh init --apply

# 4. provider、属性filter、MFA policyの反映を確認する。
sudo /opt/shibboleth-idp/bin/graphicalmatrix-sp.sh status
sudo /opt/shibboleth-idp/bin/graphicalmatrix-sp.sh next
```

`init`が`REVIEW_REQUIRED`となった場合は、表示された既存XMLの競合を確認する。強制上書き
optionは提供しない。

#### 新しいSPを追加する場合

```bash
# 1. SP管理者からentityID、metadata URLまたはmetadataファイル、必要属性、MFA要件を受け取る。
# 2. 追加予定を検証し、metadata digest、ACS、鍵fingerprint、属性/MFA差分を確認する。
sudo /opt/shibboleth-idp/bin/graphicalmatrix-sp.sh add \
  --name library \
  --entity-id https://library.example.org/shibboleth \
  --metadata-url https://library.example.org/Shibboleth.sso/Metadata \
  --attribute-profile uid \
  --mfa force

# 3. 表示されたSHA-256をSP管理者から別経路で受け取った値と照合する。
# 4. 一致した場合だけ、表示された値を指定して反映する。
sudo /opt/shibboleth-idp/bin/graphicalmatrix-sp.sh add \
  --name library \
  --entity-id https://library.example.org/shibboleth \
  --metadata-url https://library.example.org/Shibboleth.sso/Metadata \
  --attribute-profile uid \
  --mfa force \
  --approve-sha256 <metadata-sha256> \
  --apply

# 5. IdP側の設定を確認し、SPの保護ページから実際のSSOを開始して試験する。
sudo /opt/shibboleth-idp/bin/graphicalmatrix-sp.sh verify library
sudo /opt/shibboleth-idp/bin/graphicalmatrix-sp.sh next library
```

#### 既存の手作業登録SPを書き換えて管理する場合

```bash
# 1. 対象entityIDと、metadata・属性・MFA方針の現状を確認する。
sudo /opt/shibboleth-idp/bin/graphicalmatrix-sp.sh status --entity-id https://legacy.example.org/shibboleth

# 2. adoptの予定を確認する。最初のadoptは設定を書き換えない。
sudo /opt/shibboleth-idp/bin/graphicalmatrix-sp.sh adopt legacy-partner \
  --entity-id https://legacy.example.org/shibboleth

# 3. legacy-original revisionを保存してCLI管理へ登録する。
sudo /opt/shibboleth-idp/bin/graphicalmatrix-sp.sh adopt legacy-partner \
  --entity-id https://legacy.example.org/shibboleth \
  --apply --confirm https://legacy.example.org/shibboleth

# 4. 以後は通常のupdate/set-attributes/set-mfaで変更する。必ず最初にdry-runを行う。
sudo /opt/shibboleth-idp/bin/graphicalmatrix-sp.sh update legacy-partner --metadata-file /secure/incoming/legacy-new.xml
sudo /opt/shibboleth-idp/bin/graphicalmatrix-sp.sh history legacy-partner
```

#### 書換えを戻す場合

```bash
# 1. 変更履歴と、戻す対象の差分を確認する。
sudo /opt/shibboleth-idp/bin/graphicalmatrix-sp.sh history library
sudo /opt/shibboleth-idp/bin/graphicalmatrix-sp.sh rollback library --revision 3

# 2. 直前のCLI変更だけを戻す。
sudo /opt/shibboleth-idp/bin/graphicalmatrix-sp.sh rollback library --revision 3 --apply \
  --confirm https://library.example.org/shibboleth

# 3. 手作業登録から取り込んだSPを、adopt前の状態へ完全に戻す場合だけ使う。
sudo /opt/shibboleth-idp/bin/graphicalmatrix-sp.sh restore-legacy legacy-partner
sudo /opt/shibboleth-idp/bin/graphicalmatrix-sp.sh restore-legacy legacy-partner --apply \
  --confirm https://legacy.example.org/shibboleth

# 4. 復元結果をCLI管理外のSPとして確認してから、SP側SSO試験を行う。
sudo /opt/shibboleth-idp/bin/graphicalmatrix-sp.sh status \
  --entity-id https://legacy.example.org/shibboleth
```

`rollback`と`restore-legacy`は、dry-runの出力に表示したentityID、metadata fingerprint、属性profile、
MFA方針が意図どおりであることを確認してから`--apply`する。

## 6. 必要な入力と検証

| 入力 | 必須 | 検証 |
| --- | --- | --- |
| `--name` | 必須 | `[a-z0-9][a-z0-9-]{0,62}`。registry上で一意。 |
| `--entity-id` | 必須 | metadataの`EntityDescriptor/@entityID`と完全一致。空白、制御文字を拒否。 |
| `--metadata-url`または`--metadata-file` | いずれか | URLはHTTPSだけ。fileはregular file、最大1 MiB。両方指定不可。 |
| `--approve-sha256` | apply時必須 | dry-runで表示したmetadataのSHA-256と完全一致。 |
| `--attribute-profile` | 任意 | 既定`none`。許可済みprofileだけ。 |
| `--mfa` | 任意 | 既定`inherit`。`bypass`は`--confirm-bypass`も必要。 |
| `--cidrs` | 条件付き | `sp-cidr-bypass`のときだけ必須。IPv4 CIDRを厳密に検証。 |

metadata URLを使う場合、初期設定で`graphicalmatrix.sp.metadata.allowedHosts`に登録したFQDNだけを
許可する。HTTP、redirect、user-info付きURL、IP literal、link-local/loopback/multicast宛は既定で
拒否する。閉域SPを使う場合は管理者がFQDNをallow-listへ追加する。

CLIはmetadata取得時に以下を検査する。

1. XMLがwell-formedで、DTD、外部entity、XIncludeを含まないこと。
2. `EntityDescriptor`が1件だけで、entityIDが入力値と一致すること。
3. `SPSSODescriptor`とHTTPSの`AssertionConsumerService`が少なくとも1件あること。
4. ACSのhostがmetadata URLのhostまたは明示allow-listに一致すること。
5. SAML署名用の`KeyDescriptor`を表示し、X.509 SHA-256 fingerprintをregistryへ記録すること。
6. 同じentityIDが管理registryに存在しないこと。更新時は明示的な`update`だけを許可すること。
7. metadataの有効期限、署名の有無、`AuthnRequestsSigned`、証明書の有無を警告として表示すること。

CLIはXML署名の有無を表示するが、v1.2.7では署名を信頼anchorへ連鎖させる暗号学的検証は行わない。
署名の有無にかかわらず、SP管理者から別経路で取得したSHA-256および証明書fingerprintを確認し、
表示されたmetadata digestを`--approve-sha256`へ指定して登録する。URLを知っているだけでは
更新・鍵変更を自動承認しない。

## 7. IdP上のファイル配置

```text
/opt/shibboleth-idp/
  metadata/
    2faskw-managed-sp/
      <sha1(entityID)>.xml
  conf/
    graphicalmatrix/
      sp-management.properties
      sp-management-registry.json
      mfa-policy.properties
  credentials/
    graphicalmatrix/
      sp-management-revisions/
      sp-management-backups/
  logs/
    graphicalmatrix-sp-management-audit.log
```

active metadata directoryは`0755`、metadataは`0644`とし、Jettyは読み取りだけを行えるようにする。
SAML metadataは公開情報であり、秘密鍵やcredentialは含まない。disabled metadata、revision、
transaction backupはroot専用の`0700` directoryへ保存する。backupは既定30日、revisionは既定180日で、
次回の更新操作時に期限切れを削除する。

revisionとtransaction backupを`conf/`配下へ置いてはならない。IdPは起動時に`conf/`を再帰走査して
propertiesを自動検出するため、root専用directoryがあると`AccessDeniedException`で起動に失敗し、
backup内のpropertiesが読み込まれると現在の設定を上書きする危険がある。v1.2.7のCLIは、旧配置の
`conf/graphicalmatrix/sp-management-revisions/`および`sp-management-backups/`を検出した場合、
新配置へ自動移動する。旧配置と新配置の両方が存在する場合は自動統合せず、管理者の確認を要求する。

registryは`root:<IdP実行グループ>`、`0640`とする。CLIの更新はrootだけに許可し、IdP実行ユーザーには
設定検査に必要な読み取りだけを許可する。registryのグループは`conf/graphicalmatrix` directoryから
継承し、原子的な置換後にも毎回補正する。

registryはJSONで保存し、少なくとも以下を記録する。SP秘密鍵、LDAP credential、SAML assertion、
利用者属性は保存しない。

```json
{
  "schemaVersion": 1,
  "name": "library",
  "entityId": "https://library.example.org/shibboleth",
  "status": "ACTIVE",
  "metadata": {
    "source": "https://library.example.org/Shibboleth.sso/Metadata",
    "sha256": "...",
    "file": "metadata/2faskw-managed-sp/<sha1>.xml",
    "certificateFingerprints": ["..."]
  },
  "attributeProfile": "uid",
  "mfaProfile": "force",
  "createdAt": "2026-08-03T00:00:00Z",
  "updatedAt": "2026-08-03T00:00:00Z",
  "currentRevision": 3,
  "legacyOriginalRevision": "legacy-original"
}
```

各revisionはregistryとは別のroot専用directoryへ保存する。保存内容はmetadata原本、現在の
registry entry、変更eventとし、adopt時のregistry entryにはlegacy provider、attribute filter断片、
MFA profileも記録する。`metadata-providers.xml`、`attribute-filter.xml`、`mfa-policy.properties`全体の
backupはtransaction失敗時の即時復元にだけ使い、SP単位のrevision復元には使わない。

## 8. 更新処理と整合性

### 8.1 追加・更新の順序

```text
入力検証
  -> metadata取得または読込
  -> XML/SAML検証と差分表示
  -> SHA-256承認確認
  -> backup作成
  -> metadata / attribute policy / MFA policy / registryを同一directoryの一時ファイルからatomic rename
  -> metadata resolver reload
  -> attribute filter service reload
  -> 2FAS-KW config check
  -> 監査ログ記録
```

反映途中に失敗した場合は、同一command内でbackupから復元して再度reloadする。
自動ロールバックにも失敗した場合は、更新失敗とrollback失敗の両方を表示して非0で終了する。

metadataだけでなく属性/MFA設定も一つのtransactionとして扱う。設定の一部だけが反映された
状態を成功として扱わない。

### 8.2 履歴とrollback

`add`、`update`、`set-attributes`、`set-mfa`、`disable`、`enable`、`adopt`、`rollback`、
`restore-legacy`の成功ごとに、反映後の状態をrevisionとして保存する。revision番号はSPごとに
単調増加とし、`history`は時刻、状態、属性profile、MFA profile、eventを表示する。

`rollback NAME --revision N --apply --confirm ENTITY_ID`は、N番revisionのSP単位の状態へ戻す。
適用前に、現在状態との差分、復元するmetadata fingerprint、属性release、MFA方針を表示する。
entityID、metadata source、legacy source fileのいずれかが現在のregistryと一致しない場合は、
意図しない上書きを避けるため拒否する。

rollback後も新しいrevisionを作成する。過去revisionを削除・上書きしないため、誤ったrollbackにも
さらにrollbackできる。revisionは既定30日ではなく、SP metadata鍵の更新履歴を追跡できるよう
既定180日保持する。保持数の上限はSPごとに50 revisionとする。

### 8.3 無効化、削除、手作業状態への復元

`disable`はmetadataファイルをactive source directoryから隔離し、属性profileとMFA ruleも
除外する。registryとbackupは残す。これにより、SPからのAuthnRequestはmetadata未登録として
拒否される。

`remove`はdisable後にのみ可能とし、SP管理名を再入力する`--confirm`を要求する。metadata鍵の
ローテーションでは`remove`+`add`を使わず、`update`で旧鍵と新鍵を含むmetadataを検証して
切替期間を設ける。

#### SPを完全に削除する手順

削除は、対象SPを2FAS-KW管理から完全に外す操作である。managed metadata、registry、対象SPの
managed attribute filter、MFA policyを削除する。削除後は`enable`や`rollback`で元に戻せないため、
再登録に使う承認済みmetadataと、必要な属性/MFA設定を別途保管してから実施する。

```bash
# 1. 対象SPの名前、entityID、現在の状態と履歴を確認する。
sudo /opt/shibboleth-idp/bin/graphicalmatrix-sp.sh list
sudo /opt/shibboleth-idp/bin/graphicalmatrix-sp.sh verify library
sudo /opt/shibboleth-idp/bin/graphicalmatrix-sp.sh history library

# 2. まず無効化の予定を確認し、内容に問題がなければ反映する。
sudo /opt/shibboleth-idp/bin/graphicalmatrix-sp.sh disable library
sudo /opt/shibboleth-idp/bin/graphicalmatrix-sp.sh disable library --apply

# 3. metadataが無効側へ移動し、対象SPが停止状態になったことを確認する。
sudo /opt/shibboleth-idp/bin/graphicalmatrix-sp.sh verify library
sudo /opt/shibboleth-idp/bin/graphicalmatrix-sp.sh next library

# 4. 削除対象をdry-runで確認する。ここでは設定は変更されない。
sudo /opt/shibboleth-idp/bin/graphicalmatrix-sp.sh remove library

# 5. SP管理名を--confirmへ正確に再入力して削除を反映する。
sudo /opt/shibboleth-idp/bin/graphicalmatrix-sp.sh remove library --apply --confirm library

# 6. registryから削除済みであることを確認する。
sudo /opt/shibboleth-idp/bin/graphicalmatrix-sp.sh list
sudo /opt/shibboleth-idp/bin/graphicalmatrix-sp.sh status --entity-id https://library.example.org/shibboleth
```

`disable --apply`と`remove --apply`は、それぞれmetadata resolverとattribute filterのreload、
2FAS-KW設定検査を実行する。いずれかが失敗した場合は当該command内で反映前の状態へ復元して
非0で終了する。削除対象が手作業登録SPの場合は`remove`を使わず、先に`adopt`して管理対象にするか、
既存のmetadata provider設定を手作業で変更する。

`sp-management.properties`の`graphicalmatrix.sp.metadata.allowedHosts`および
`graphicalmatrix.sp.metadata.allowedAcsHosts`は、将来CLIがmetadataを取得・検証してよいホストの
許可リストであり、SP登録そのものではない。そのため`remove`では自動削除しない。許可リストに対象SPの
FQDNが残っていても、metadata provider、registry、属性/MFA設定を復元したり、認証を許可したりはしない。
将来の再登録可能性がある場合は残す。完全廃止してmetadataを今後受け入れる必要もない場合だけ、他の
FQDNを残したまま管理者が手動で削除する。

```properties
# 例: new-sp.example.orgを削除し、new-sp2.example.orgだけを残す。
graphicalmatrix.sp.metadata.allowedHosts = new-sp2.example.org
graphicalmatrix.sp.metadata.allowedAcsHosts = new-sp2.example.org
```

このproperties変更は次回の`graphicalmatrix-sp.sh`実行時に読み直されるため、許可リストの編集だけでは
Jetty再起動を必要としない。

#### 手作業状態への復元

`restore-legacy`はSP削除ではなく、`adopt`で取り込んだ既存SPをCLI導入前の手作業登録へ戻す操作である。
対象は、取り込み時に一意に検出できた`FilesystemMetadataProvider`だけとする。CLIで新規追加したSPは
元の手作業設定を持たないため、この操作は使えない。その場合は前述の`disable`と`remove`を使用する。

```text
手作業登録SP
  -> adopt
2FAS-KW管理SP
  -> restore-legacy
手作業登録SPへ復元
```

`adopt`時に保存した`legacy-original` revisionには、元のmetadata provider XML、metadataファイルの
内容と配置先、対象SPのattribute filter XML断片、MFA profileとCIDR設定を保持する。
`restore-legacy`はこれらをSP単位で復元し、2FAS-KW管理directoryのmetadata、managed attribute filter、
managed MFA rule、registry entryを取り除く。他のmanaged SPや、対象外のIdP設定は変更しない。

```bash
# 1. CLI管理下での履歴を確認する。
sudo /opt/shibboleth-idp/bin/graphicalmatrix-sp.sh history legacy-partner

# 2. 復元するentityID、旧provider名、旧metadataファイルの配置先を確認する。
#    このdry-runでは設定を変更しない。
sudo /opt/shibboleth-idp/bin/graphicalmatrix-sp.sh restore-legacy legacy-partner

# 3. 表示内容が意図どおりであることを確認してから復元する。
sudo /opt/shibboleth-idp/bin/graphicalmatrix-sp.sh restore-legacy legacy-partner \
  --apply \
  --confirm https://legacy.example.org/shibboleth

# 4. registryから外れ、手作業登録SPとしてmetadataが読まれることを確認する。
sudo /opt/shibboleth-idp/bin/graphicalmatrix-sp.sh status \
  --entity-id https://legacy.example.org/shibboleth
```

復元後はregistry entryが削除されるため、`verify legacy-partner`、`enable legacy-partner`、
`rollback legacy-partner`などのCLI管理SP専用commandは使えない。metadata resolverとattribute filterの
reload、2FAS-KW設定検査は復元command内で実行される。失敗した場合はcommand開始時のsnapshotへ戻し、
非0で終了する。

元のprovider IDがすでに存在する場合、または`legacy-original`のmetadata revisionが失われている場合は
復元を拒否する。取り込み後に対象SPのattribute filterやMFA設定を手作業で変更していた場合、保存した
断片との重複や意図しない上書きを避けるため、実行前に`metadata-providers.xml`、`attribute-filter.xml`、
`mfa-policy.properties`をバックアップし、dry-run出力を確認する。

## 9. 監査と権限

すべての更新系commandを`graphicalmatrix-sp-management-audit.log`へ記録する。

```text
ts=<UTC> event=SP_ADD actor=<sudo-user> name=library entity_id=<...> result=OK detail=
```

metadata URLにはquery stringやcredentialを許可しないため、ログに秘密値が残らない。
URLを記録する場合もfragmentは保存しない。証明書fingerprintとmetadata digestは記録してよい。

v1.2.7のwrapperは全commandでrootを要求する。`sudoers`で引数単位の委譲は行わず、CLI実行権限を
持つ管理者を限定する。読み取り専用の参照権限を別ロールへ委譲する必要がある場合は、rootが取得した
機微情報を含まない出力を別途配布する。

この権限分離はCLIに限る。HTTP APIを後から追加して同じ権限を公開してはならない。将来APIが
必要になった場合は、ネットワーク境界、強い管理者認証、認可、監査、レート制限、CSRF対策、
秘密情報の取扱いを含む別設計・別バージョンとして審査する。

## 10. 2FAS-KW本体への変更範囲

| 対象 | 変更 |
| --- | --- |
| 新規Java | `GraphicalMatrixSpManagementTool`、安全なmetadata parser、既存metadata source scanner、registry、transaction、properties/XML renderer。 |
| 新規shell | `graphicalmatrix-sp.sh`。root確認、IdP path検出、`reload-metadata.sh`/`reload-service.sh`呼出。 |
| 配布設定 | `sp-management.properties.idpnew`、managed metadata provider/attribute filterテンプレート。既定は`enabled=false`。 |
| 配布 | plugin ZIP/TARへIdP側CLIを同梱。Admin Tools ZIPには同梱しない。 |
| Config check | 有効時に`LocalDynamicMetadataProvider`、管理用attribute filter block、registry、active metadata directoryを検査。 |
| テスト | metadata parser、XXE・entityID・ACS拒否、SHA-1標準ファイル名、registry JSON、dry-run、追加、検証、無効化、再有効化を追加。 |
| 文書 | `INSTALL_NEW_SP.md`をCLI中心へ更新し、手動手順は障害時の復旧手順として残す。 |

GraphicalMatrixの認証Servlet、sequence保存形式、DB schema、LDAP schema、既存利用者の認証フローは
変更しない。SPの追加は既存の`authn/External`と2FAS-KW MFA判断へそのまま入る。

## 11. 初期化時の扱い

既存のIdP設定は運用ごとの差異が大きいため、`init --apply`は次の条件を満たす場合だけ自動で
変更する。

1. `metadata-providers.xml`に`GraphicalMatrixManagedSPMetadata`が存在しない。ただし、無効な旧ID
   `2FAS-KWManagedSPMetadata`だけが存在する場合は、同じproviderのIDを現行IDへ移行できる。
2. XMLを安全に解析でき、追加先の`ChainingMetadataProvider`が一意に決まる。
3. `attribute-filter.xml`に管理用markerが存在しない、または既存managed blockが正常に読める。
4. `mfa-policy.properties`の管理対象propertyが重複していない。
5. 変更前backupと生成後のXML構文が正常である。

上記を満たさない独自構成では、CLIは変更を拒否し、生成予定の差分と手動導入手順を出力する。
無理に設定ファイルを正規化・上書きしない。

metadata provider自体の初回導入はIdPのreloadまたはJetty再起動が必要になる可能性がある。
一方、provider導入後のSP追加・更新ではmetadata resolverとattribute filter serviceのreloadだけで
反映できる。認証処理中の既存sessionを強制終了しない。

## 12. 採用しない方式

| 方式 | 採用しない理由 |
| --- | --- |
| SPサーバへのSSH自動構築 | 製品差、秘密鍵、証明書、Firewall、アプリ設定の責任境界が広すぎる。 |
| metadata URLの定期自動上書き | ACS・鍵変更を無承認で受け入れることになり、SSRFとmetadata改ざんのリスクが高い。 |
| 任意のattribute XML入力 | 属性の過剰releaseを防げず、設定のレビュー不能性が高い。 |
| SP追加ごとの`metadata-providers.xml`追記 | SP数に比例してXML編集・再起動・rollbackが増える。 |
| metadata未登録SPを許容する設定 | 未検証のACSや鍵へSAML Responseを返す危険がある。 |

## 13. 実装範囲と導入順序

v1.2.7では次を実装する。

1. `status`、`list`、`next`、`verify`、`check-update`による読み取りと次commandの案内。
2. `init`、`add`、`update`、`set-attributes`、`set-mfa`による初期化と管理。
3. `disable`、`enable`、`remove`、`history`、`rollback`による停止・復元。
4. 対応する既存`FilesystemMetadataProvider`の`adopt`と`restore-legacy`。
5. 承認済みcustom attribute profileと、remote metadata sourceのread-only表示。

導入は、読み取り専用inventory、初期化dry-run、初期化適用、Jetty再起動、新規SP dry-run、
digest承認付き適用、SSO試験の順で行う。検証用IdPでreload失敗時のrollback、metadata鍵
ローテーション、属性profile変更、disable後の拒否を確認してから本番利用する。

DashboardへのSP管理監査イベント取込みはv1.2.7の対象外とし、別のログsource拡張として扱う。

## 14. 受入条件

1. `add`のdry-runではIdP設定・registry・metadataに変更がない。
2. `--apply --approve-sha256`後、IdP再起動なしで新SPのSSOが開始できる。
3. metadataのentityIDまたはACSが設定条件と不一致なら拒否し、承認したSHA-256と取得値が不一致なら追加を拒否する。
4. 新SPへは選択したattribute profile以外の属性をreleaseしない。
5. `force` SPでは`bypassNetwork`に一致する送信元からもMFAが要求される。
6. `disable`後、SPからのAuthnRequestはmetadata未登録として拒否される。
7. update/reload失敗時、metadata・属性・MFA方針・registryが開始前の状態に戻る。
8. 既存SP、自己管理フロー、GraphicalMatrix/TOTP/WebAuthn認証が回帰しない。
9. `status`が既存のFilesystem/LocalDynamic/Inline metadataからentityIDを検出し、管理対象外を
   `EXISTING_LOCAL`として表示する。
10. remote metadata sourceは許可なく取得せず、`REMOTE_SOURCE`としてprovider情報だけを表示する。
11. `rollback`が指定SPだけを指定revisionへ戻し、他SPのmetadata・属性release・MFA方針を変更しない。
12. `restore-legacy`がadopt前の手作業設定を復元し、構造不一致時は設定を変更せずに失敗する。
13. SPの追加・更新・停止・削除・復元を実行できるHTTP endpoint、管理Web UI、listener port、
    remote agentが配布物・IdP webapp・設定に存在しない。変更操作はIdPホスト上で許可された
    管理者が`sudo /opt/shibboleth-idp/bin/graphicalmatrix-sp.sh`を実行した場合だけ可能である。

## 15. 調査根拠

- [IdP 5 Metadata Management Best Practices](https://shibboleth.atlassian.net/wiki/spaces/IDP5/pages/3199507429/MetadataManagementBestPractices): 少数のローカルSPにはfilesystem、増加するローカルSPには`LocalDynamicMetadataProvider`を推奨している。
- [IdP 5 LocalDynamicMetadataProvider](https://shibboleth.atlassian.net/wiki/spaces/IDP5/pages/3199506968/LocalDynamicMetadataProvider): source directory、entityID SHA-1の標準file naming、初回要求時の自動解決を定義している。
- [IdP 5 Metadata Configuration](https://shibboleth.atlassian.net/wiki/spaces/IDP5/pages/3199506698/MetadataConfiguration): metadata sourceがSPの技術情報・鍵を提供し、source順序が重複entityIDの解決に影響することを示している。
- [IdP 5 Metadata Reload](https://shibboleth.atlassian.net/wiki/spaces/IDP5/pages/3199511489/MetadataReload): resolver IDを指定した`reload-metadata.sh`と、dynamic resolverのcache clearを定義している。
- [IdP 5 Reloadable Services](https://shibboleth.atlassian.net/wiki/spaces/IDP5/pages/3199507931/ReloadableServices): attribute filter serviceなどをCLIでreloadできることを定義している。
- [IdP 5 Attribute Filter](https://shibboleth.atlassian.net/wiki/spaces/IDP5/pages/3199511838): attribute releaseはentityIDを含むcontextに対する明示的なfilter policyで制御される。
- [INSTALL_NEW_SP.md](../INSTALL_NEW_SP.md): 本プロジェクトのCLIおよび手動SP追加手順。
