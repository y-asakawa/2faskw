# v1.4.2 管理CLI操作監査ログ 詳細設計

状態: **実装済み・ローカル検証・未公開**。作成日: 2026-11-02。
対象は`graphicalmatrix-db.sh`と同じ更新処理を呼ぶAdmin Tools／CSV runnerである。
v1.4.1を基準にした設計と、v1.4.2の実装記録を併記する。導入時は監査先の準備が必要である。
以下の「現行」は設計時のv1.4.1を指し、実装・試験の到達点は15節に記す。

## 1. 目的と採用方針

管理者が「いつ、どの利用者に、どの設定操作を行い、実際にどうなったか」をログで追跡できるようにする。
DBに履歴テーブルを追加せず、最新状態は既存DB、操作履歴は専用監査ログという役割分担を採用する。

採用する要件:

- IdP上とStandalone Admin Tools上で、同じCLIに同じ監査仕様を適用する。
- 既存のコマンド名、引数、RESETのYES/NOと`-y`、dry-run／`--apply`を維持する。
- 変更処理より前の開始記録と、確定結果の記録を区別する。
- 対象利用者を記録し、秘密値を記録しない。操作の前後で秘密のHashを採る方式も使わない。
- ログ保存不能を黙って無視しない。更新前の障害は更新を止め、更新後の障害は更新済みと明示する。
- DBとファイルの原子的な同時commitや、全変更の完全な変更前後スナップショットは保証しない。

例えば`graphicalmatrix-db.sh user001 RESET -y`では、対象`user001`、操作`RESET`、実行主体、
確定した結果を記録する。画像列が何であったかを記録する機能ではない。

## 2. 現行コードで確認した状態

| 経路 | 現行実装 | v1.4.2での扱い |
| --- | --- | --- |
| 自己管理画面 | `GraphicalMatrixAuditLogger`が変更・登録eventを`graphicalmatrix-audit.log`へ追記する | 出力仕様と認証処理を維持する |
| 管理HTTP API | 操作event、対象利用者、結果を同じ監査ログへ記録する | APIへのCLI監査の重複追加はしない |
| `graphicalmatrix-db.sh`直接実行 | SQL結果・診断を端末へ出すが、ユーザー管理の専用操作監査はない | 本設計で追加する |
| Java内部更新tool | `GraphicalMatrixInitialSequenceTool`等がDBを更新する。成功監査はない | CLI向けの型付き操作結果を返す内部経路を追加する |
| CSV runner | `csv-import.log`に計画とファイル単位の適用成否がある | 既存ログを維持し、同じCLIの監査へファイルと利用者を関連付ける |
| SP管理CLI | SP管理用の別監査ログがある | 今回は変更せず、ユーザー管理ログと区別する |
| OSのsudoログ | 環境次第で実行者・コマンドが残る | 補助情報として扱う。DB変更成功の証拠にしない |

現行の`GraphicalMatrixAuditLogger`はファイル書込み失敗でも認証を止めない。
そのbest-effort実装をCLIの必須監査へ流用しない。認証用監査と管理CLI監査の障害方針は別とする。
`ADMIN-TOOLS.md`の従来の`admin-audit.log`記述は設計説明であり、CLIへの実装済み仕様ではなかった。

## 3. 対象範囲

### 3.1 監査対象のコマンド

| CLI・別名 | 正規化したaction | 記録する安全な変更内容 |
| --- | --- | --- |
| `add`／`set-sequence` | `SET_SEQUENCE` | 新規作成か更新か、画像列の変更有無、初期値を設定したか、変更強制の結果 |
| `set-initial-sequence` | `SET_INITIAL_SEQUENCE` | 初期値を変更した事実、変更強制の結果。初期画像列自体は出さない |
| `USER RESET`／`reset-user` | `RESET` | 初期値へ戻した事実、方式・状態・ロック・TOTPの変更結果 |
| `set-method` | `SET_METHOD` | 変更先の`GraphicalMatrix`／`TOTP`／`WebAuthn` |
| `require-change` | `SET_REQUIRE_CHANGE` | ON／OFF |
| `enable`／`disable` | `ENABLE`／`DISABLE` | `ACTIVE`／`DISABLED` |
| `unlock`／`reset-failures` | `UNLOCK` | 失敗回数・ロック解除の事実 |
| `lock` | `LOCK` | 指定時間、確定したロック期限 |
| `set-totp-seed` | `SET_TOTP_SEED` | seed設定の事実、TOTP状態。seed自体は出さない |
| `clear-totp-seed`／`reset-totp` | `RESET_TOTP` | seed消去、登録状態の変更 |
| `webauthn-reset` | `RESET_WEBAUTHN` | 削除した件数、任意の方式変更。dry-runを区別する |
| `webauthn-delete` | `DELETE_WEBAUTHN_CREDENTIAL` | 削除件数、credential IDのSHA-256 fingerprintのみ |
| `delete` | `DELETE_USER` | 無効化・キー整理・行削除それぞれの確定結果 |
| `csv`／`provisioning-csv` | `IMPORT_CSV` | ファイル識別子、行番号、対象利用者、A／M／D、方式・状態など |
| `migrate-sequence-storage` | `MIGRATE_SEQUENCE_STORAGE` | 対象利用者、保存方式名、初期値移行の事実、batch結果 |
| `migrate-totp-seed-storage` | `MIGRATE_TOTP_STORAGE` | 対象利用者、保存方式名、確定結果 |
| `invalidate-pending-totp` | `INVALIDATE_PENDING_TOTP` | 対象利用者、PENDING取消し、方式・状態の結果 |
| `csv-export`／`export-csv` | `EXPORT_CSV` | DB更新ではないが機微情報を外へ出す操作として、件数と成否を記録する |

変更系コマンドのdry-run、RESETのNO／空入力／EOF、検証段階の拒否も対象とする。
通常の`list`／`show`／`webauthn-list`／設定help／保存方式の照会は、既定では専用監査の対象外とする。
未知コマンド・不正な引数は、安全に分類できたaction／targetだけをbest-effortで記録し、元の入力を転記しない。

### 3.2 autoInitによる例外

現行CLIは、一部の照会やdry-runでも`db.autoInit=true`ならschema初期化SQLを実行する。
「readコマンドだからDB更新なし」と決めつけない。初期化を実行する場合は、独立した
`SCHEMA_INIT`の開始・結果監査を**DDLより前から**有効にする。DDL非transactionalな経路の失敗は、
すべて未変更と断定せず`UNKNOWN`／`PARTIAL`に分類する。
本番での既定`autoInit=false`と、PoCで明示的に有効化する運用は変更しない。
SCHEMA_INITは独立したopとし、呼出し元op IDと関連付ける。dry-runのPLANNEDは利用者情報の
適用が未実施という意味であり、その前に実施したschema処理の記録を打ち消さない。

### 3.3 対象外と保証の境界

- SQLクライアントによる直接更新、別スクリプト、DB管理者、LDAP管理ツールの操作は捕捉しない。
- `graphicalmatrix-db-migration.sh`によるDB全体の復元・任意SQL適用は本設計の利用者単位監査の対象外。
  別途、DB運用の作業記録・DB監査で管理する。全CLIを網羅したとは記載しない。
- 公式WebAuthn管理画面でのキー追加・削除は公式プラグインの監査設定による。公式プラグインを改変しない。
- 同じDB資格情報で内部Java toolを直接呼ぶ行為も、公開CLI入口だけの監査では完全には捕捉できない。
- root、DB管理者、監査ファイルへの書込み権限を持つ主体による改変耐性・否認防止は別問題である。

## 4. 配置と設定

### 4.1 ログの保存先

同一ホスト上のIdP／Admin Toolsで、次を既定にする。

```text
/var/log/2faskw/admin-audit.log
/var/log/2faskw/admin-audit.lock
```

認証ログ、CSV runnerログ、SP管理ログとは分離する。`GRAPHICALMATRIX_HOME`が違っても
同一ホストの既定の監査先は共通であり、eventにdeployment識別子を付けて区別する。
Jettyが書換え可能なIdPの`logs/`を必須監査の既定保存先にはしない。

`conf/graphicalmatrix/admin-audit.properties`をIdP／Admin Toolsの両パッケージで配布する。
既存ファイルは上書きせず、`.idpnew`／`.adminnew`として差分確認できるようにする。

```properties
graphicalmatrix.admin.audit.logFile = /var/log/2faskw/admin-audit.log
graphicalmatrix.admin.audit.lockFile = /var/log/2faskw/admin-audit.lock
graphicalmatrix.admin.audit.lockTimeoutMillis = 3000
graphicalmatrix.admin.audit.mirrorSyslog = false
```

設定ファイル省略時も同じ既定値で動く。ただしログの配置・権限準備は必要である。
変更系監査を無効化する設定や`--no-audit`は追加しない。既存の`admin.enabled`と連動して、
IdP側の通常CLIが監査対象外になる実装にはしない。出力先を未検証の環境変数で上書きしない。

### 4.2 所有者・権限

| パス | 所有者・mode | 方針 |
| --- | --- | --- |
| `/var/log/2faskw` | `root:graphicalmatrix-admin`、`0750` | 一般利用者・Jettyによるファイル差替えを防ぐ |
| `admin-audit.log` | `root:graphicalmatrix-admin`、`0660` | rootと許可されたCLI／CSV実行主体だけが追記する |
| `admin-audit.lock` | 同上 | rotationで削除・再作成しない固定lock file |
| `admin-audit.properties` | `root:root`、`0644` | 秘密値は含めず、書換えは管理者だけに限定する |

IdP上でrootがCLIを実行する場合も、必要なgroupを導入時に準備する。既存groupのGIDは変更しない。
CSV serviceの`graphicalmatrix-admin`、およびsudoなしでCLIを書込み実行する既存の許可利用者は、
このログの書込みgroupへ明示的に所属させる。一般利用者やJettyを便宜的に追加しない。

group-writeは許可された管理主体を信頼する設計であり、その主体による内容改変・truncateは防げない。
改変耐性が必要な環境は、別権限の集中ログ基盤へ転送し、そこでアクセス制限・保持・監視を行う。

### 4.3 installerと直接更新の扱い

- Admin Tools installerは、rootで上記のgroup・directory・空のログ／lockを準備する。
- 存在するログを`install /dev/null`等で上書き・truncateしない。既存所有者・modeは確認して調整する。
- IdP配布物には同じ処理の監査準備コマンドを同梱する。既存のJAR差替え更新では、その準備を先に行う。
- CLI自身は、書込み可能にするためのsudo・chmod・chownを自動実行しない。
- 準備がなくても通常のread操作は可能。ただし変更系操作は明確な案内を出してDB更新前に停止する。
- H2で内部Javaだけを`sudo -u jetty`実行する場合、監査ファイルを開くのは元の管理CLI側とする。
  Jettyへ監査ファイルの権限を渡さず、sudoが追加FDを閉じる環境にも依存しない。

## 5. ログ形式

UTF-8、1 event 1行の`key=value`形式とする。共通必須fieldは固定順で出力する。
`format=1`を付け、将来の形式変更と区別する。日時はシステムタイムゾーンのISO-8601とし、
`Z`または数値オフセットを必須にする。単調clockによる処理時間は表示timezoneと独立に維持する。
当初のUTC固定案は16節の共通ログ方針に更新した。

| field | 内容 |
| --- | --- |
| `ts` | event記録日時。DBの`updated_at`と必ず同時刻とは限らない |
| `event` | `ADMIN_CLI_START`、`ADMIN_CLI_CHANGE`、`ADMIN_CLI_END` |
| `format` | `1` |
| `op_id` | CLI 1回ごとに生成するランダムUUID。再実行では別IDになり、二重実行防止や整合性の保証には使わない |
| `parent_op_id` | SCHEMA_INITの子処理から親CLIへの参照。親なしは`none`。CSVのdry-runとapplyは別実行であり別opになる |
| `seq` | 親CLIの監査状態が割り当てる増加番号。schema子処理とも共有するため、1つのopで絞ると欠番になり得る。全ホスト共通の順序番号ではない |
| `host`、`deployment_id` | 実行ホスト名と導入先の実パスのSHA-256。別ホストの同じ実パスは同じdeployment IDになるため両方で識別する |
| `action`、`mode` | 正規化したaction、`APPLY`／`PLAN`／`EXPORT` |
| `target_user` | 単一対象ユーザー。batch全体のSTART／ENDは`-`、CHANGEには個別IDを記録 |
| `uid`、`euid`、`effective_user` | OSから取得する実UID・実効UIDと実効利用者名 |
| `login_uid` | Linux audit loginuid。未設定・取得不能なら`-` |
| `invoker_claim`、`invoker_source` | 任意の`SUDO_USER`等の参考情報と由来。認証済み管理者名とは断定しない |
| `db_type`、`db_target_id` | DB種別と秘密を含まない接続先識別子 |
| `stage` | `VALIDATE`、`CONFIRM`、`UPDATE_ENROLLMENT`等の固定分類 |
| `result`、`db_result` | 下記の操作結果とDB確定状態 |
| `matched_rows`、`changed_rows` | 変更statementが返した件数。取得不能は`-`で、推測値を出さない |
| `changes` | 許可した設定結果のみ。秘密値そのものや生の例外messageは含めない |
| `exit_code`、`duration_ms` | END時のCLI終了値と処理時間 |
| `operation_exit_code` | 内部更新toolの元の終了値。監査障害によるCLI終了値と区別する |
| `reason_code` | `USER_NOT_FOUND`、`AUDIT_IO_FAILED`等の固定診断コード |

`db_target_id`は設定上のDB接続先のSHA-256であり、JDBC URLやDBパスワードをそのまま出さない。
PostgreSQLではURIのhost・port・DB pathを使用し、認証情報とquery parameterを含めない。
H2では最初の`;`または`?`より前のJDBC URLを使用する。管理者が任意の配置IDを指定する方式ではない。
IP／host名、portの省略／明示で値が変わり得る一方、proxyのbackend変更や同じ接続先へのDB復元で
変わらない場合がある。DNS解決やDBサーバー固有IDの取得は行わず、未解析・欠落設定のfallbackもあるため、
実DBの一意性や接続・更新成功を保証しない。完全な生成規則と検索例は
[開発者向けログ設計](../development/LOGGING.md)を参照する。

### 5.1 実行者の解釈

実UID／EUID／kernel loginuidを一次情報とする。`SUDO_USER`、`USER`、`LOGNAME`、
`SSH_CONNECTION`は環境由来であり、値があるだけで本人確認済みと扱わない。
sudoから通常呼ばれた場合は`invoker_claim=admin01`等を補助情報にし、OSのsudo/auditログと照合する。
root直実行はroot、CSV serviceはservice accountとして記録する。CSVのアップロード担当者を
service accountやファイル名から推測しない。共有root／共有API tokenの利用から個人を特定する保証はない。

### 5.2 記録禁止情報と値の制限

記録しないもの:

- 現在／初期GraphicalMatrix画像列、入力alias列、保存済みhash・暗号文・pepper・keyword。
- TOTP seed、確認コード、AES鍵、WebAuthn公開鍵・credential JSON・user handleの全文。
- DB password、Bearer token、秘密鍵、接続URLの認証情報。
- 生のargv、`SUDO_COMMAND`、stdin、SQL本文、stdout／stderr、stack traceや例外messageの丸ごと転記。

記録可能な`changes`は、方式名、状態、変更強制ON/OFF、ロック期限、seedを設定／消去した事実、
credential削除件数、保存方式名、登録世代、画像列を変更した事実に限る。
画像列の長さ・値のfingerprintは操作追跡に必須ではないため新規監査では記録しない。
WebAuthn単一キー削除の識別だけは、高エントロピーなcredential IDのSHA-256を利用できる。

キー名は実装内のallowlistに固定する。control文字・改行・空白・`=`・`%`等を値へそのまま埋めず、
UTF-8 byte列をpercent-encodingして1行・1値を維持する。連結後に正規表現で秘密を伏せる方式は採らない。
1行上限は8 KiB。超過時は任意の参考fieldから省略し、action／target／op_id／確定結果を切り捨てない。
必須fieldを安全に記録できない場合は、更新前なら処理を止める。

## 6. 状態・成否の定義

`result`と`db_result`を別fieldにする。shell終了値0だけで`DB変更成功`を判定しない。

| result | db_resultの代表値 | 意味 |
| --- | --- | --- |
| `STARTED` | `NOT_ATTEMPTED` | 操作受付。まだ変更確定ではない |
| `PLANNED` | `NOT_ATTEMPTED` | dry-runの対象と予定。DBを変更した記録ではない |
| `CANCELLED` | `NOT_ATTEMPTED` | RESETのNO／空入力等による中止 |
| `REJECTED` | `NOT_ATTEMPTED` | 入力・権限・状態の検証段階で拒否 |
| `SUCCESS` | `COMMITTED` | 変更statementとcommitの成功を確認した |
| `NO_MATCH` | `COMMITTED` | 対象行0件。変更成功した利用者がいるとは扱わない |
| `NO_CHANGE` | `COMMITTED` | 対象はあるが設定変更が不要であると確認できた |
| `FAILED` | `NOT_ATTEMPTED`／`ROLLED_BACK` | 変更前の失敗、またはrollbackを確認した失敗 |
| `PARTIAL` | `PARTIAL` | 先行stage／batchはcommit済み、後続処理が失敗した |
| `UNKNOWN` | `UNKNOWN` | commit応答の喪失等で、成功・rollbackのいずれも証明できない |

EXPORTの成功は`result=SUCCESS db_result=NOT_ATTEMPTED`とし、DB commitと混同しない。
出力件数とファイルへの保存完了を確認し、内容を監査へ取り込まない。

同じ値を指定したUPDATEでも、現行仕様でversion・更新日時が進む場合は、その実更新を記録する。
最終DB値を別SELECTしただけで`NO_CHANGE`や`SUCCESS`を推測しない。
失敗時に元のAPI／CLIの診断を変更する必要はないが、監査には固定reasonと確認済みの状態だけを記録する。

### 6.1 基本シーケンス

```text
最小限のcommand/target分類と監査先の検証
  -> STARTをappend・同期
  -> 引数検証／RESET確認／dry-run
  -> mutation開始（ここからDB変更の可能性あり）
  -> 変更statement・commitから型付き結果を取得
  -> commit済みCHANGEをappend・同期
  -> 任意の結果表示（DB更新とは別の段階）
  -> ENDをappend・同期、終了
```

STARTを作れる前に秘密入力をargvやログへ複製しない。targetを安全に分類できない場合は`-`とする。
EXIT trapはENDの二重送信防止と未完了の診断補助に使い、`$?=0`からcommitを創作する用途には使わない。
SIGINT／SIGTERMでは確認済み状態だけを記録する。SIGKILL・電源断ではtrapが実行されないことを前提にする。

### 6.2 型付き操作結果

`GraphicalMatrixCliOperationReport`を内部の共通契約として追加する。
JSON等の構造化形式を内部通信に利用しても、管理者向けの監査ファイルは上記のTXT形式とする。

- operation ID、target、stage、commit verdict、実statementの件数、許可した変更結果を保持する。
- Java更新toolはcommit成功後にreportを返す。rollbackやclose時の障害もcommit状態と分離する。
- PostgreSQLの変更SQLは`RETURNING`等で対象・結果を取り、生成したSQLをstdinで実行する。
  mutation専用呼出しは型付きreportだけを返し、通常の結果表とは出力経路を分離する。
  `RETURNING`の行が届いただけではcommit済みとしない。commit応答と専用呼出し全体の
  正常完了を確認して確定する。応答喪失時は件数が分かっていても`UNKNOWN`とする。
- H2はJDBCの更新件数と明示的なtransaction状態からreportを作る。H2 Shellの表示を解析して成功扱いしない。
- `sudo -u jetty`の追加FD引継ぎを必須にしない。内部更新呼出しのstdoutをreport専用にし、
  小さく制限されたreportだけを親CLIが受け取る。秘密のstdinや既存の結果表を監査へteeしない。
- 外部から与えた`rows_affected`やreportをそのまま信用せず、親が生成したop ID・action・targetとの
  一致、列名allowlist、形式・件数・サイズを検査する。
- reportが壊れた場合、変更開始前なら拒否する。既に開始済みでcommit状態が不明なら`UNKNOWN`とする。
- batch toolはcommitごとのreportを逐次返せるようにする。親はreport streamの終了と子processの
  終了値を別々に回収する。pipe／process substitutionの読取り成功を子の正常終了と誤認しない。

これは監査のための結果通知・transaction境界の明確化であり、credential生成、照合、lockout、
MFA選択、登録世代、物理deleteの安全方針は変更しない。

### 6.3 更新後の結果表示エラー

DB更新と結果のSELECT／端末表示を別段階で管理する。commit後のSELECT失敗・出力先切断は、
`stage=DISPLAY result=FAILED db_result=COMMITTED`とする。変更をrollback済みと記録しない。
利用者へは「更新済みだが表示に失敗」と伝え、自動再実行を促さない。

## 7. 複数段階・一括処理

### 7.1 ユーザーの物理削除

現行の次の順序を維持し、確定した各段階を記録する。

```text
START DELETE_USER
  -> DISABLE_ENROLLMENT commit -> CHANGE
  -> DELETE_WEBAUTHN_CREDENTIALS commit -> CHANGE
  -> DELETE_ENROLLMENT commit -> CHANGE
  -> END SUCCESS
```

キー整理で止まれば、`END result=PARTIAL db_result=PARTIAL`とし、
`enrollment_status=DISABLED`、`enrollment_deleted=false`等の確認済み結果を示す。
最終的な物理削除が終わっていないのに`USER_DELETED SUCCESS`と記録しない。
H2の対応範囲、WebAuthn保存先の制約、途中失敗時にDISABLEDを保持する方針は変えない。

### 7.2 CSV import／provisioning

- runnerの`csv-import.log`は維持し、専用監査を代用させない。
- 受信ファイルを一度だけ固定化し、検証・SHA-256・実適用は同じbyte列を使う。
- 監査のSTART／ENDにはファイルSHA-256、許可したbasename、件数、modeを記録する。
  完全パスとCSV本文は記録しない。SHA-256はファイル同一性の識別子であり、送信者認証ではない。
- 行ごとの`target_user`、行番号、A／M／D、変更先方式・状態をop IDで関連付ける。
- dry-runの行記録は`PLANNED`。実適用の行記録は、そのtransactionのcommit確認後にだけ
  `ADMIN_CLI_CHANGE`として出す。事前previewを成功履歴とみなさない。
- batch rollbackでは各行を変更成功としない。commit結果不明では行結果も`UNKNOWN`とする。
- direct `csv`実行も対象にし、runnerの有無で監査を迂回できないようにする。
- runnerが渡す親IDは相関の参考情報であり、CLI自身のop IDやOS主体を上書きさせない。

安全な行metadataは必要ならmode `0600`の一時fileへ段階保存する。生CSVやSQLを新しい監査用
一時fileへ複製しない。stagingは64 MiBを上限とし、上限超過が分かったらcommit前にrollbackする。
一時fileは削除し、ログ障害時に残す場合も秘密を含まないmetadataだけを管理者専用領域へ保管する。

### 7.3 保存形式migration・PENDING取消し

画像列migrationは既存の200行単位commitを維持し、commit済みbatchごとに対象利用者のCHANGEを記録する。
後続batch失敗時に、先行batchまでrollbackしたと記録しない。TOTP seed migrationは現行の
transaction境界を維持する。PENDING一括取消しは、実際のUPDATE対象から利用者IDを取得する。
どの処理も、事前の一覧SELECTと最終件数だけで個別利用者の成功を推測しない。

## 8. ログ障害時の契約

| 発生時点 | DB操作と終了時の扱い |
| --- | --- |
| 監査先不正／権限不足／容量不足／lock timeoutでSTARTを書けない | DB更新・autoInit前に停止。新しい監査準備エラー終了値`73` |
| transaction開始前のPLANNED等の保存失敗 | DB更新を開始しない。`73` |
| commit確認済みだがCHANGE／ENDを書けない | 更新済みとstderrへ明示。新しい終了値`74`。成功やrollbackとは表示しない |
| commit確認済みの先行stageがあり、その後の更新または監査が失敗 | `PARTIAL`。確認済みstageと未完了stageを表示する |
| 接続断等でcommitを確認できない | `UNKNOWN`。自動retryしない。既存DB障害の非ゼロ終了を維持する |
| syslog mirrorだけが失敗 | primary記録は有効。警告は出すが、この理由だけでDB操作を失敗扱いにしない |

既存のRESET中止時の終了値0、EOFや不正引数の非ゼロ終了、dry-runの無変更契約は維持する。
DB更新0件を専用監査では`NO_MATCH`にするが、監査追加だけを理由に既存の通常終了値を一律変更しない。
`73`／`74`が新たに発生し得る点と、`74`では無条件再実行しない点を運用マニュアルへ明記する。
内部toolのエラー件数等が偶然`73`／`74`を返す場合、監査障害と混同しないようCLIでは一般失敗`1`へ
正規化し、元の値は`operation_exit_code`へ保存する。この詳細終了値の変更は互換性上の注意として記載する。
部分更新と監査障害が併発した場合も終了値は`74`を優先し、元処理の終了値と確定済みstageを
別の診断fieldで保持する。自動化は「非ゼロなら変更なし」と判断しない。

OS stderrへの出力・syslog mirrorはprimary失敗の補助通知であり、その通知の永続保存まで保証しない。
DBとログの間でprocessが失われれば、STARTだけ残り得る。ENDのないopを成功・失敗のどちらかへ
自動補完しない。現在のDB状態、sudoログ、元の作業記録を照合し、未確定として調査する。

## 9. ファイル書込みと保持

`GraphicalMatrixAdminAuditWriter`をJava側に新設する。新しい常駐daemonやPython実行環境は追加しない。

- 監査先／lockは通常fileであること、owner／mode、親directory、symlink・hardlink数を検査する。
- group／otherが親directoryを書換えられる配置や、symlink経由の保存先は拒否する。
- 固定lock fileの排他lockを取得し、完全な1行またはcommit済みの小さなbatchをappendする。
- `APPEND`と`NOFOLLOW_LINKS`を用い、書込み後に`FileChannel.force(true)`を行ってから成功を返す。
- lock待ちは既定3秒、設定可能範囲は100〜10000 ms。無期限待ちにしない。
- file descriptorはイベント／batchごとに閉じる。DB transaction中に監査lockを保持しない。
- CSVの各行でJava processを新規起動しない。commit済みmetadataをwriterへbatchで渡し、
  batch単位でappend／forceする。単一利用者操作もwriter起動回数を一定に抑え、実測する。
- wall clockの巻戻りに備えてop内連番と単調clockのdurationを記録する。ホスト間の完全な時間順は保証しない。

logrotateはrename＋createとし、日次180世代、圧縮、`delaycompress`を例とする。
copytruncateは監査行が失われる窓があるため、新しい必須CLI監査の推奨にはしない。
createする新fileも`root:graphicalmatrix-admin`の`0660`とし、固定lock fileはrotateしない。
rename／create間の短い不在は最大1秒の有界retryで扱う。なおも失敗した場合は第8節に従う。
既に開いた旧fileへの行はrotation後のログも含めて検索する。無期限のretryや、勝手な別file作成は行わない。

SELinuxでは`/var/log`配下の適切なラベルを確認する。AVCがある場合に対象を調査し、
SELinux全体の無効化や広いallow ruleの追加を通常手順にしない。
fileの同期はOS／filesystemへの保存要求であり、ハードウェア障害や権限保有者による改変まで防ぐものではない。

## 10. syslog・既存ログとの関係

`mirrorSyslog=true`の場合だけ、primaryと同じ安全なeventを`logger`等でローカルsyslogへ転送する。
tagは`2faskw-admin-audit`、op IDを同じにして重複と相関を識別する。raw commandは送らない。
`logger`が成功しても、遠隔サーバーでの保存完了や保持期間を保証したとは扱わない。

既存の`graphicalmatrix-audit.log`、`csv-import.log`、SP監査ログはそのまま維持する。
Dashboardへ新ログを自動投入しない。認証成功件数へ管理操作を混ぜず、別途対応する場合に
event分類・権限・個人情報範囲を設計する。ログの存在確認・容量・rotation失敗を運用監視に加える。

## 11. 記録例と確認方法

説明用に参考fieldの一部を省略した例であり、実装では共通必須fieldを出力する。

```text

ts=2026-11-02T03:00:01Z event=ADMIN_CLI_CHANGE format=1 op_id=11111111-1111-4111-8111-111111111111 seq=2 action=RESET mode=APPLY target_user=user001 stage=UPDATE_ENROLLMENT result=SUCCESS db_result=COMMITTED matched_rows=1 changed_rows=1 changes=method:GraphicalMatrix,status:ACTIVE,force_change:true,totp:UNREGISTERED
```

RESETのNOでは`result=CANCELLED db_result=NOT_ATTEMPTED`、commit不明では`result=UNKNOWN db_result=UNKNOWN`とする。

## 15. 実装記録

### 15.1 コードと実行経路

| Component | 責務 |
| --- | --- |
| `GraphicalMatrixAdminAuditTool` | 親CLIとして開始記録を永続化し、Bashの対話を維持して実行する。確定receipt、部分更新、表示故障、終了・signalを集約する。 |
| `GraphicalMatrixAdminAuditWriter` | root管理の設定とlog/lock、通常ファイル、owner/group/mode、link、先祖directoryを検証し、安定lock下でappend・force(true)・closeする。 |
| `GraphicalMatrixAdminAuditClient` | workerから親へUnix domain socketで型付き結果を送る。DB commitと通知失敗を区別し、commit応答不明をUNKNOWNのまま扱う。 |
| `GraphicalMatrixCliOperationReport` | 許可した変更項目と値のみを受け付け、資格情報や任意文字列を拒否する。 |
| `GraphicalMatrixCliSqlCommand` | CLIが生成した更新SQLをJDBCで実行し、実statement件数・RETURNING対象・同一transaction内の安全な更新後状態を保持し、commit確認後に報告する。 |
| 既存InitialSequence／migration／export tool | 既存の更新条件と保存形式を維持し、確定箇所へreportを追加する。 |

追加FDやsafe metadataファイルのsudo引継ぎではなく、短命な親プロセスとUnix domain socketを採用した。
常駐daemonは増やさない。ランダムcapabilityを子へ渡し、祖先processとの関係、OSのsocket peer主体、
私有directoryの所有者・権限を検査する。取得可能な場合は親のJava executableも確認するが、
別UIDのworkerが`/proc/PID/exe`を参照できない場合も考慮する。環境へ存在しない親を指定しても
監査なしの実行にはならない。process ancestryを秘匿するOS設定は対象環境で動作確認する。
IPCにも有界待ちを設け、応答しないpeerでworkerが無期限に停止しないようにする。
入口の元引数はNUL区切りの私有pipeから親へ渡し、画像列等を監査用JVMのargvへ複製しない。
対話用stdinはそのまま維持する。この入口用FDはH2のsudo workerへ監査FDを渡すものではない。
H2 workerへの必要情報はsudoの`env`へ明示し、Jettyに監査ファイルの書込み権限は付与しない。
DB資格情報・任意Java実行権限・監査書込権限を持つ悪意ある主体の迂回を防ぐ機構ではない。

PostgreSQLの既存照会・表示はpsqlを継続する。更新はJDBCへ分離したため、表示SELECTの故障が
更新transactionの成功を取り消したようには記録されない。H2 scalar照会もJDBCへ分離し、
人向けの見出しを値として判定しない。SQL分割には既存PostgreSQL driverのparserを使い、
quoted semicolonやDO blockを文字列の単純分割で壊さない。

### 15.2 一括処理と安全な内容

直接CSVも私有のsnapshotを一度だけ作り、SHA-256、検証、SQL生成、適用を同じbyte列へ固定する。
safeな行番号・action・対象とtransactionの実結果を保持し、全行commit後に一括で永続化する。
画像列移行の200行batch、TOTP seed移行の全件transaction、物理deleteの段階commitは維持する。
新しい一時metadataファイルは追加せず、報告はmemory内で上限検査してからcommitする。
既存CSV処理に必要な私有SQL／CSV一時ファイルは0600/0700とし、終了時にcleanupする。

`changes`は許可項目の更新後状態と操作の変更flagであり、全項目の変更前後差分ではない。
例えば状態変更時に同じtransaction内の方式や登録世代も併記するが、それらを全て変更したとは限らない。
件数は実statementから得る。利用者が0件なら変更先の予定値を実変更として転記しない。
CSVの同一利用者への複数行は行ごとに記録する。file hashは秘密列のfingerprintではなくsnapshotの相関用である。
DB targetは認証情報・URL queryを除外した接続先識別子のhashとし、raw JDBC URLを出さない。

### 15.3 導入と検証

準備script、両配布物の設定template、CLI監査用rename/create logrotate、CSV unit、package検査を追加した。
IdP側の認証起動検査にCLI監査の書込み権限を要求しない。既存公式TOTP／WebAuthnを改変せず、
認証・自己管理の監査loggerの障害契約も変更しない。Git管理外のlocal installerは、該当helperが
ある配布物で監査先を準備し、親CLIをJettyではなくrootで実行するよう追従する。

自動試験の主要項目:

- writerの注入対策、固定項目、mode/link拒否、lock待ち上限、同時追記、rotation後再open、10,000行batch。
- 型付き結果の秘密値拒否、0件と成功、取消、既知commit後の表示故障、部分確定、不明commit、監査故障73/74。
- 実Bash CLIとH2で、RESET、追加、方式、無効化、物理削除、CSV plan/apply/rollback、autoInit、偽親指定の拒否。
- JDBCで10,000件のCSV相当更新と単一commit、64MiBを超える報告のcommit前拒否。
- 既存認証・自己管理・CLI security regressionと配布物回帰。

13節の全故障条件を実機で実施済みという意味ではない。SELinuxを含むEL/Ubuntuでのroot・CSV service・
実sudoによるUID切替、実PostgreSQLへの通常適用とcommit応答喪失、disk-full／read-only filesystem、SIGKILL、
集中syslogの永続化は対象環境で追加確認する。DBとlogの原子的同時確定は引き続き保証しない。
本ブランチからの公開、署名、tag作成、commit/pushは実装作業と分けて行う。

## 16. ログ日時の統一（2026-11-05追記）

### 16.1 対象と出力

認証・自己管理、SP管理／属性ガバナンス、SPアクセス制御、管理CLI、CSV処理の各独自ログを、
実行環境のシステムタイムゾーンへ合わせる。Javaの5つの監査出力箇所は
`GraphicalMatrixLogTimestamp`を共用し、人向けのアクセス方針reload診断も同じ整形処理へ接続する。
CSV runnerはPOSIXの`date`で日時と数値offsetを取得し、同じISO-8601形式へ整える。
UTCへの暗黙fallbackは行わず、日時生成に失敗した場合は不正な`ts`を出力せず停止する。

```text
UTC: ts=2026-11-05T01:43:30.518Z
JST: ts=2026-11-05T10:43:30.518+09:00
```

Javaは元の小数秒精度を維持し、CSVは秒精度とする。夏時間のoffsetは「現在のoffset」ではなく、
記録対象のInstantに対して計算する。同じローカル時刻が2回現れる夏時間の終了時も数値offsetで区別できる。
設定項目は追加しない。Javaの`-Duser.timezone`や`TZ`、containerの設定で上書きした場合はその設定が使われる。
OSのtimezone変更後はJetty等の長時間実行JVMを再起動する。CLI／CSV runnerは次回実行時に確認する。

### 16.2 維持する契約

- DBのepoch値、`last_success`の更新条件、TOTP判定、MFA完了detailのmillisは変更しない。
- API／索引／registry／metadataの日時、metadataの署名対象byte列、移行用run ID・backup名はログ表記とは別である。
- 既存UTC行は書き換えず、新旧形式を混在させる。Dashboardは数値offsetを解釈して元のInstantへ戻す。
  MFA完了detailの時刻との一致検査も、表記文字列ではなくInstantで維持する。
- Dashboardの索引は従来どおり絶対時刻を保持し、画面はブラウザのtimezoneで表示する。
- IdPのlogback、OS journal、Apache／PHP等の第三者製品設定は上書きしない。UTC固定の独自設定は運用側で確認する。
- 監査のowner/mode/link検査、commit前後の契約、秘密値除外、rotation、認証の失敗方針は変更しない。

### 16.3 試験と更新

UTC／Asia/TokyoのJVMで共通formatterと監査writerを確認し、日付境界、小数秒、正負・非整数時間のoffset、
夏時間の重複時刻を試験する。CSV runnerはUTC、JST、Kathmandu、負offset、および不正なdate出力を確認する。
Dashboardは旧UTC行との混在、JST・他offsetの正規化、offset欠落の拒否、MFA完了epochの一致／不一致を試験する。
共有UTC fixtureは正本として維持し、出力との比較は同じInstantと残りのpayloadが一致することを確認する。
