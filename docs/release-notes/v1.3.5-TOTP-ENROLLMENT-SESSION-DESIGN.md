# 2FAS-KW v1.3.5 TOTP登録セッション束縛 詳細設計

実装状態: 実装済み、単体・回帰試験実施済み、実IdP・実LDAP結合試験は未実施

## 1. 文書の目的

本書は、TOTP自己登録の開始権限が特定の登録世代へ結び付いていない問題を修正する、
2FAS-KW v1.3.5の詳細設計兼リリースノートである。

現行実装では、認証済みの古いTOTP登録画面が有効な間に管理者がMFA方式を変更した場合、
古い画面からの取消操作で現在の方式をGraphicalMatrixへ戻せる。また、管理リセット後に別の
正規セッションがTOTP再登録を開始すると、古い画面の再試行処理が新しいPENDING seedを取得して
表示する可能性がある。

v1.3.5では、登録開始ごとに一意な登録IDを発行し、登録開始後の`state_version`と固定期限を
組み合わせたBindingを、保存先とサーバー側HTTPセッションの双方へ保持する。確認、再試行、取消は、
同じBindingに一致するPENDING登録だけを操作できるようにする。

本書でいうTOTP登録は、自己管理画面でQRコードまたはseedを表示し、確認コードを入力して
`totp_status=ACTIVE`へ遷移する処理を指す。通常ログイン時のTOTP検証アルゴリズムは対象外である。

## 2. 対象バージョンと判定

本変更の配布対象はv1.3.5とする。基準実装はv1.3.4であり、公開済みtagや成果物は変更しない。

本件は、認証済みセッション、登録key、CSRF token、および短い有効期間を必要とするため、
未認証の外部利用者が直接実行できる問題ではない。一方、管理者によるMFAリセットや方式変更を
古い登録セッションが上書きできるため、TOTP自己登録を提供する本番環境では修正を必須とする。

| 項目 | 評価 |
|---|---|
| 重要度 | Low |
| 確信度 | High |
| 影響 | 管理復旧の上書き、別登録のTOTP seed露出、登録状態の競合 |
| 主な成立条件 | 認証済み旧登録セッションと管理変更または別登録の時間的重複 |
| v1.3.5方針 | F-05として修正する |

## 3. 現行実装の問題

### 3.1 登録開始が二つの更新に分かれている

現行の方式変更処理は、最初に`updateMfaMethodIfCurrent()`で方式をTOTPへ変更し、その後に
`prepareTotpRegistration()`でseedを生成する。後半が失敗すると、方式だけがTOTPになり、
登録に必要なPENDING seedが存在しない中間状態が残る可能性がある。

### 3.2 登録セッションが登録世代を保持しない

HTTPセッションの`totpEnroll.*`には、利用者、flow key、CSRF token、期限、認可済みフラグが
保存される。しかし、登録開始時の`state_version`や登録を一意に識別するIDは保存されない。

そのため、保存先の現在値が管理操作や別登録によって置き換わっても、旧画面が同じ利用者の
操作として継続できる。

### 3.3 再試行が現在のPENDING seedを取り直す

確認コードが誤っていた場合、現行Servletは利用者IDだけを指定して
`prepareTotpRegistration()`を再実行する。保存先が別登録のPENDING状態へ変わっていると、
その別登録のseedが旧セッションへ返される可能性がある。再試行のたびに登録期限も延長される。

### 3.4 取消が現在のversionを採用する

現行の取消処理は、操作時に`findEnrollment()`で現在の行を読み、そこで得た最新の
`state_version`を`updateMfaMethodIfCurrent()`へ渡す。登録開始時のversionと比較しないため、
管理者が行った方式変更を旧登録画面がGraphicalMatrixで上書きできる。

### 3.5 管理書込経路の不整合

管理APIのリセット等は`state_version`を増加させるが、登録セッションとの対応情報を持たない。
また、現行`graphicalmatrix-db.sh set-totp-seed`はseedと状態を更新する一方、
`state_version`を増加させない。このような書込経路が残ると、登録世代を使った失効が成立しない。

## 4. 適用範囲

### 4.1 対象

- IdP-native自己管理および互換用変更画面からのTOTP登録開始
- TOTP確認コードの検証、誤コード後の再試行、登録取消
- PostgreSQLおよびH2の登録状態とトランザクション
- LDAP保存の登録状態と原子的条件更新
- 管理API、CLI、CSV、保存形式移行等の登録書込経路
- HTTPセッション、エラー応答、監査ログ、設定検査
- 既存データ移行、配備、切戻し、package regression

### 4.2 対象外

- 通常ログイン時のTOTPアルゴリズム、桁数、time step、window
- Shibboleth TOTP Plugin内部の認証処理
- TOTP確認コードの新しい試行回数制限
- 全IdPセッションの一括失効
- TOTP認証器アプリ側に既に保存されたseedの遠隔削除
- GraphicalMatrix、WebAuthnの認証方式そのもの

## 5. Security invariant

v1.3.5のTOTP登録処理は次の条件を満たす。

1. 登録開始ごとに推測困難で再利用しない`registrationId`を発行する。
2. 登録の続行は、利用者、登録ID、開始後version、固定期限の全一致を必要とする。
3. BindingはHTTPパラメータではなく、認証済みサーバー側セッションから取得する。
4. 保存先の状態確認前にseedを復号、表示、ログ出力しない。
5. 管理変更、別登録、disable、reset、削除、再作成後の旧Bindingを拒否する。
6. Binding不一致時に現在値を取り直して再試行しない。
7. 誤コード時に返せるのは、同じBindingで確認した同じseedだけとする。
8. 再試行で登録期限を延長しない。
9. 方式変更、seed生成、登録ID、期限、version更新を一つの原子的開始操作にする。
10. 確定と取消は同じBindingに対する条件付き終端操作とし、一方だけを成功させる。
11. 保存先障害やLDAP Control未対応を無条件更新へfallbackしない。
12. seed、確認コード、QR内容、完全な登録IDを監査ログへ記録しない。

## 6. 登録Binding

登録操作を次の不変値で識別する。

```text
TotpEnrollmentBinding = (
    userId,
    registrationId,
    expectedStateVersion,
    expiresAt
)
```

| 値 | 生成元 | 用途 |
|---|---|---|
| `userId` | 認証済み自己管理セッション | 別利用者への操作を拒否する |
| `registrationId` | 登録開始時のSecureRandom | 同じ利用者の別登録を区別する |
| `expectedStateVersion` | 登録開始更新後の保存先version | 管理変更や別書込を検出する |
| `expiresAt` | 登録開始時刻と固定TTL | 古い登録権限を時間で失効させる |

`registrationId`、CSRF token、flow keyは、それぞれ別のSecureRandom値を生成する。
登録IDだけを認可情報として使用しない。

## 7. 状態遷移

| 操作 | 保存先の変更 | セッション |
|---|---|---|
| 登録開始 | TOTP、PENDING、新ID、新seed、固定期限、version + 1 | 更新後Bindingを保存 |
| 誤コード | 保存先を変更しない | 同じBinding、期限のまま再試行 |
| 登録確定 | TOTP、ACTIVE、ID・期限消去、version + 1 | 終了 |
| 正規取消 | GraphicalMatrix、UNREGISTERED、PENDING seed・ID・期限消去、version + 1 | 終了 |
| 管理reset・方式変更・disable | 管理変更、ID・期限消去、version + 1 | 旧Bindingは失効 |
| 別の登録開始 | 新ID、新seed、新期限、version + 1 | 旧Bindingは失効 |
| 期限切れ | 要求では保存先を変更しない | 終了し再認証を要求 |

確定または取消済みの要求を再送しても成功扱いにしない。現在の状態を上書きせず、STALEとして
再開始を案内する。

## 8. 登録期限

TOTP登録専用の設定を追加する。

```properties
graphicalmatrix.totp.registrationTtlSeconds = 180
```

- 許容範囲は30秒から900秒とする。
- 初期値は現行の`graphicalmatrix.challenge.seconds`と同じ180秒とする。
- 登録開始時に`expiresAt`を固定し、設定変更や誤コードで延長しない。
- 現在時刻が`expiresAt`以上の場合を期限切れとする。
- 未設定時は180秒を使用し、共通challenge設定へ暗黙追従させない。

専用設定へ分離することで、GraphicalMatrix challengeの期限を変更せず、QR読取りや確認コード入力に
必要な時間だけを運用環境に合わせて調整できる。

## 9. DBデータ設計

`graphicalmatrix_enrollment`へ次の列を追加する。

| 列 | 型 | 初期値 | 意味 |
|---|---|---|---|
| `totp_registration_id` | `VARCHAR(64)`、NULL可 | NULL | 現在のPENDING自己登録ID |
| `totp_registration_expires_at` | `BIGINT NOT NULL` | 0 | 登録固定期限のepoch milliseconds |

既存の`state_version`を併用する。登録ID単独で検索するAPIは追加しないため、専用indexは必須としない。

```sql
ALTER TABLE graphicalmatrix_enrollment
  ADD COLUMN IF NOT EXISTS totp_registration_id VARCHAR(64);

ALTER TABLE graphicalmatrix_enrollment
  ADD COLUMN IF NOT EXISTS totp_registration_expires_at BIGINT NOT NULL DEFAULT 0;
```

通常のIdP実行ユーザーへDDL権限を追加しない。本番PostgreSQLでは配備前に管理用DBユーザーでDDLを
適用し、Config Checkで列の存在を確認する。H2の新規作成DDLと既存DB更新DDLも同じ列を持たせる。

## 10. LDAPデータ設計

LDAP保存では、次の単一値属性を追加する。

| 論理名 | 設定キー | 属性名の例 |
|---|---|---|
| 登録ID | `graphicalmatrix.ldap.attr.totp_registration_id` | `gmTotpRegistrationId` |
| 登録期限 | `graphicalmatrix.ldap.attr.totp_registration_expires_at` | `gmTotpRegistrationExpiresAt` |

属性名の例は既存環境に存在することを意味しない。配布LDAP schemaでは、プロジェクトが管理するOID枝から
重複しないOIDを割り当て、対象補助objectClassのMAY属性へ追加する。bind利用者には対象属性のread、
compare、write権限を付与する。

TOTP登録の開始、確定、取消にはLDAP Assertion Controlを`critical=true`で使用する。Control OIDは
`1.3.6.1.1.12`であり、Assertion不成立時は更新を実行しない。RFC 4528が定義する条件付き更新を使い、
検索後に別操作が競合しても同一Modify内で条件を再確認する。

導入前にroot DSEの`supportedControl`、ACL、schema、単一値制約、成立時と不成立時の実Modifyを確認する。
Control未対応、権限不足、属性欠落の場合はLDAP保存での新規TOTP自己登録を有効にしない。

参考: [RFC 4528 LDAP Assertion Control](https://www.rfc-editor.org/rfc/rfc4528.html)、
[RFC 4511 Modify Operation](https://www.rfc-editor.org/rfc/rfc4511.html#section-4.6)

## 11. Repository API

利用者IDだけで現在のPENDING seedを取得・確定するAPIをTOTP自己登録経路から除去し、Bindingを必要とする
APIへ置き換えた。結果は`GraphicalMatrixTotpEnrollmentResult`へ集約する。

```java
GraphicalMatrixTotpEnrollmentResult beginTotpRegistration(
    String user,
    long expectedPreBeginVersion,
    long now,
    long ttlMillis
);

GraphicalMatrixTotpEnrollmentResult verifyTotpRegistration(
    GraphicalMatrixTotpEnrollmentBinding binding,
    String code,
    long now
);

GraphicalMatrixTotpEnrollmentResult cancelTotpRegistration(
    GraphicalMatrixTotpEnrollmentBinding binding,
    GraphicalMatrixConfig config,
    long now
);
```

開始成功Resultは登録ID、開始後version、期限、初回表示用seedを返す。
Resultは`STARTED`、`ACTIVATED`、`RETRY`、`CANCELLED`、`STALE`、`EXPIRED`、`LOCKED`、
`UNAVAILABLE`を区別する。seedを含めてよいのは、同じBindingを保存先で確認した`RETRY`だけとする。

秘密値を含むResultへ自動生成の`toString()`を付けない。例外、監査、debug logへResult全体を出力しない。

## 12. DBトランザクション

開始、確認、取消は、対象行を`SELECT ... FOR UPDATE`で取得する短いトランザクションとする。
ブラウザの入力待ち中は行ロックやDB接続を保持しない。

### 12.1 開始

1. `expectedPreBeginVersion`と現在の行を比較する。
2. ACTIVE、非ロック、初期変更完了等の既存条件を確認する。
3. 新しい登録IDとseedを生成する。
4. 方式、PENDING状態、seed、ID、期限、versionを一度に更新する。
5. commit成功後だけBindingとseedをServletへ返す。

二つの開始要求が同じ事前versionを使用した場合、一方だけを成功させる。失敗側へseedを返さない。

### 12.2 確認

行ロック下でBinding、ACTIVE、TOTP、PENDING、非ロック、期限を照合してからseedを復号する。
誤コードでは保存先を更新せず、その処理で確認した同じseedだけを`RETRY`結果へ含める。

正しいコードの場合、同じトランザクションでACTIVE化、登録ID・期限消去、version増加を行う。
更新件数が1件の場合だけ成功とする。

### 12.3 取消

取消専用APIで同じBindingを確認し、GraphicalMatrix sequenceが現在の設定で利用可能な場合だけ、
GraphicalMatrixへ戻す。PENDING seed、登録ID、期限を同じ更新で消去する。画像列、初期画像列、
`force_sequence_change`は変更しない。

管理者がすでに方式を変更していた場合はSTALEとし、現在の方式を変更しない。

## 13. LDAP原子的更新

LDAPでは検索とModifyの間に管理操作が入る可能性があるため、単純なread-compare-modifyだけでは
受入条件を満たさない。Assertion Controlへ次の条件を含め、Modifyと一体で評価する。

```text
status = ACTIVE
AND mfa_method = TOTP
AND totp_status = PENDING
AND state_version = expectedStateVersion
AND totp_registration_id = registrationId
AND totp_registration_expires_at = expiresAt
AND locked_until = 読み取って非ロックを確認した値
```

- Filter値を文字列連結で生成せず、LDAP FilterとBERの専用encoderへ集約する。
- `assertionFailed (122)`はSTALEとして扱う。
- Control未対応、ACL不足、schema不整合、通信障害はUNAVAILABLEとする。
- Assertion失敗後に最新versionを読み直してModifyを再試行しない。
- 一時的なRequest Controlを別のLDAP操作へ持ち越さない。
- 複数書込先を使う場合は、対象利用者の更新順序を一つのauthoritative writerへ集約する。

## 14. HTTPセッション

新設する`GraphicalMatrixTotpEnrollmentSession`へ`totpEnroll.*`の管理を集約する。

| 項目 | 内容 |
|---|---|
| 利用者、flow key、CSRF | 現行の要求保護 |
| Binding | 登録ID、開始後version、固定期限 |
| 認可状態 | 正規の自己管理経路から開始したこと |
| inFlight | 同じ登録に対する二重送信を排他する状態 |

受付時に短い排他区間で`inFlight=true`へ遷移する。保存先I/O中にJava monitorを保持しない。
結果反映時に登録Bindingを再確認し、別登録が開始されていれば遅い応答からseedを表示せず409で終了する。

複数ノードではJavaの`synchronized`を分散ロックとして扱わない。HTTPセッションのsticky routing、
または共有セッションストアの原子的claim機能を使用する。保存先のBinding検査は構成にかかわらず必須とする。

## 15. HTTP応答と利用者表示

| 結果 | HTTP | 表示 |
|---|---:|---|
| 開始成功 | 200 | 当該登録のQR、seed、確認フォーム |
| 誤コード、Binding有効 | 200 | 同じ登録情報と元の期限で再試行 |
| 確定・取消成功 | 200 | 完了画面 |
| key、CSRF、Binding不正 | 400 | 秘密を含まない再開始案内 |
| 管理変更、別登録、状態不一致 | 409 | 登録状態が変更されたため再開始 |
| 期限切れ | 410 | 期限切れと再認証案内 |
| ロック中 | 既存方針 | seedを表示しないロック画面 |
| 保存先・暗号処理障害 | 503 | 一般的なサービス利用不可案内 |

既存の`Cache-Control: no-store`等を維持する。登録IDをURLやエラー本文へ追加せず、QR生成を外部サービスへ
委譲しない。失効した画面から自動で新しいseedを作成しない。

## 16. 管理操作と書込契約

保存先を書き換える全経路は、進行中の登録を明示的に維持する操作でない限り、登録IDと期限を消去し、
`state_version`を増加させる。

| 経路 | v1.3.5で必要な変更 |
|---|---|
| 管理API `totp-reset`、`reset` | ID・期限を消去し、version増加を維持 |
| 管理APIの方式変更、disable、enable | ID・期限を消去し、version増加を維持 |
| CLI `set-totp-seed` | ID・期限消去とversion増加を追加 |
| CLI `reset-totp`、`clear-totp-seed` | ID・期限消去を追加 |
| CLIの方式変更、disable、enable、reset、delete | 旧Bindingを必ず失効 |
| CSV A、M、D | PostgreSQLとH2の両分岐で旧IDを保持しない |
| WebAuthn方式変更 | ID・期限消去とversion増加 |
| seed・sequence保存形式移行 | 条件付きversion更新と登録失効 |
| LDAP管理処理 | 関連属性の変更、ID・期限消去、version増加を同一Modifyで実施 |

DBへ直接書き込む外部ツールも同じ契約を守る。PENDING seedだけを入れ替え、versionと登録IDを維持する
操作はサポートしない。新版IdPと旧Admin Toolsを混在させない。

## 17. 運用互換性

### 17.1 変更しないもの

- 既存ACTIVE TOTP利用者のseedと通常ログイン
- TOTPの6桁コード、time step、検証window
- `graphicalmatrix-db.sh`の既存コマンド名
- 管理APIの既存URLと基本request形式
- CSV provisioningの列名、A・M・D action
- GraphicalMatrixとWebAuthnの通常認証

### 17.2 意図的に変わるもの

- 管理変更後の古い登録画面は続行・取消できない。
- 誤コードを入力しても期限は延長されない。
- 同じ利用者の複数タブ登録は一つだけを有効とする。
- v1.3.4以前に開始した登録画面はBinding欠落として拒否する。
- 登録中に別の管理更新が行われた場合は最初からやり直す。

これらは利用者の再操作を発生させるが、管理者の変更と別登録の秘密を優先して保護する意図的な
fail-closed動作である。

## 18. データ移行

### 18.1 ACTIVE TOTP

既存の`totp_status=ACTIVE`利用者はseed、登録時刻、MFA方式を変更しない。新しい登録IDはNULL、期限は0の
ままとする。通常ログインに新列を要求しない。

### 18.2 旧PENDING TOTP

旧PENDINGには、どの認証済みHTTPセッションと対応するかを証明する情報がない。新しい登録IDを後付けして
継続させず、配備中に全件失効させる。

1. PENDING件数と対象者をseedを表示せず取得する。
2. 利用可能なGraphicalMatrix sequenceがある利用者は、PENDING seedを消去し、方式をGraphicalMatrix、
   TOTP状態をUNREGISTEREDへ戻し、ID・期限を消去してversionを増加させる。
3. GraphicalMatrix sequenceを利用できない利用者は自動変更せず、管理者復旧対象として一覧化する。
4. 対象利用者へTOTP登録の再実施を案内する。

旧設計のようにTOTP方式のままPENDING seedだけを消去すると、利用者が通常ログインも再登録も完了できない
可能性があるため採用しない。

### 18.3 LDAP

LDAP schemaと属性mappingを全書込先へ先に配備する。既存ACTIVE利用者には登録ID属性を追加しない。
旧PENDINGの失効はAssertion Control対応を確認した管理手順で実施する。

## 19. 配備手順

1. IdP設定、DBまたはLDAP、TOTP暗号鍵、配布物を同一世代でバックアップする。
2. TOTP PENDING件数、ACTIVE件数、保存先、全IdPノード、Admin Tools、CSV runnerを確認する。
3. TOTP自己登録と関連する管理更新を一時停止する。
4. PostgreSQL列、またはLDAP schema・属性mappingを配備する。
5. 旧PENDINGを第18章の方針で失効させる。
6. 全IdPノード、管理API、Admin Tools、CSV runnerをv1.3.5へ更新する。
7. Config Checkで列、属性、LDAP Control、設定値を確認する。
8. 旧版へトラフィックや定期ジョブが残っていないことを確認する。
9. TOTP自己登録を再開する。
10. 正常登録、誤コード再試行、取消、管理reset後の旧画面拒否を確認する。

ローリング更新中に旧版と新版が同じ登録データを書き込む構成はサポートしない。短い保守時間を設けて
一括更新する。

## 20. 切戻し

新列をDBへ残したまま旧版へ戻すことは可能だが、旧版を公開するとF-05の経路が再発する。切戻し中は
TOTP自己登録の開始、確認、取消を公開しない。管理API、Admin Tools、CSV runnerも互換が確認された版へ
同時に戻す。

切戻し前後のPENDING登録は失効させ、過去のBindingとHTTPセッションを復元しない。ACTIVE TOTP seedを
不要に再生成しない。LDAP属性を削除する場合は、新版コードが完全に停止した後の別作業とする。

## 21. 監査

既存イベントを維持し、結果と失効理由を追加する。

| event | 主なresult・detail |
|---|---|
| `TOTP_REGISTER_START` | `OK`、`STALE`、`LOCKED`、`UNAVAILABLE` |
| `TOTP_REGISTER_VERIFY` | `OK`、`FAIL`、`STALE`、`EXPIRED`、`LOCKED` |
| `TOTP_REGISTER_CANCEL` | `OK`、`STALE`、`EXPIRED`、`LOCKED` |

detailには`registration_id_mismatch`、`state_version_mismatch`、`expired`、`not_pending`、
`assertion_failed`等の固定reason codeを使用する。seed、確認コード、QR、otpauth URI、Cookie、CSRF、
flow key、完全な登録IDを記録しない。

管理変更直後のSTALEは正常な失効として扱う。UNAVAILABLE、LDAP Control未対応、属性欠落、継続的な
競合増加は運用アラートの対象とする。

## 22. 試験設計

### 22.1 F-05再現経路

| ID | 操作 | 合格条件 |
|---|---|---|
| F05-01 | Aで開始、管理者がWebAuthnへ変更、Aで取消 | STALE。WebAuthnを維持 |
| F05-02 | Aで開始、reset、Bで開始、Aで誤コード | Aの応答とログにBのseedを含まない |
| F05-03 | B開始後、AからBの正しいコードを送信 | Binding不一致。BはPENDINGを維持 |
| F05-04 | Aで開始、disable、enable、Aで確認・取消 | ACTIVEに戻っていても旧Bindingを拒否 |
| F05-05 | Aで開始、CLIでset-totp-seed、Aで再試行 | CLIでversion増加・ID消去。新seedを返さない |
| F05-06 | Aで開始、行削除・同じuserIdで再作成、Bで開始 | versionが同じでも登録ID不一致でAを拒否 |

### 22.2 正常系と競合

- 開始時に方式、seed、ID、期限、versionが一度に更新される。
- 誤コードを複数回送ってもseed、ID、version、期限は変わらない。
- 正しいコードでACTIVE化し、IDと期限を消去してversionを増加させる。
- 正規取消でGraphicalMatrixへ戻し、画像列を維持する。
- 期限直前は許可し、期限と同時刻または期限後は拒否する。
- nullまたは空のkey、CSRF、Bindingを保存先操作前に拒否する。
- verifyとcancelの同時実行では一方だけが成功する。
- 二つのbeginが同じ事前versionを使う場合は一方だけが成功する。
- DB commitまたはLDAP応答喪失時に成功画面を出さず、無条件再更新しない。
- 保存先停止、seed復号失敗で新しいseedをfallback生成しない。

### 22.3 保存先と配布物

- PostgreSQLとH2で新規DDL、既存DDL、開始、確認、取消、管理更新を試験する。
- 実LDAPでAssertion成立、不成立、未対応、ACL不足、schema欠落を試験する。
- Servlet response、HTTP status、Cache-Control、監査ログに秘密がないことを確認する。
- 管理API、CLI、CSV、保存形式移行の全書込経路で旧Bindingが失効することを確認する。
- 既存ACTIVE TOTP、GraphicalMatrix、WebAuthnの通常ログイン回帰を確認する。
- package regressionで新DDL、LDAP schema、設定、文書が配布物へ含まれることを確認する。

**受入条件:** F05-01からF05-06をDBとLDAPの両バックエンドで満たし、正常な開始、再試行、確定、
取消が成立すること。旧IdP、旧Admin Tools、未対応の直接書込経路が残っていないこと。

### 22.4 実装時の検証結果

2026-09時点で次を実施した。

- Pluginの全単体試験: 179件成功、失敗・エラー0件。
- Dashboardの全単体試験: 48件成功、失敗・エラー0件。
- H2を使用したsecurity regression: dry-runの非更新、旧PENDING失効、管理`set-sequence`による

- package regression: Plugin、Admin Tools、Dashboardの配布物、設定、DDL、LDAP mapping、文書の

## 25. 残る制約

- すでに画面表示または認証器アプリへ保存された旧seedを端末から回収することはできない。
- 管理更新と、すでに生成途中のHTTPレスポンス送信を完全に同期させるものではない。
- DBやLDAPへ特権的に直接書き込み、本設計のversion・ID契約を無視する操作は防げない。
- HTTPセッション複製方式とLDAP Assertion Controlの実環境対応は、配備前の結合試験が必要である。
- LDAPの非同期multi-writer構成では、単一の更新順序を保証する構成が別途必要である。

これらの制約を含めても、登録開始時に認可された操作を特定の登録世代へ限定し、管理変更後の旧操作と
別登録seedの取得を拒否することがF-05の完了条件である。
