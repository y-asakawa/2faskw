# 2FAS-KW v1.2.7 Standalone Dashboard 詳細設計・リリースノート

## 1. 文書の位置付け

本書は、2FAS-KW v1.2.7で提供する運用ダッシュボードの詳細設計である。
現行の`graphicalmatrix-audit.log`を唯一の認証イベント入力として利用し、IdPと同居する構成と
別サーバで稼働する構成の両方を対象とする。

公開パッケージ名は次の固定名とする。

```text
2faskw-dashboard.zip
```

本書はv1.2.7実装時の設計判断と受入条件を保存するリリースノートである。導入・運用手順は
`docs/DASHBOARD.md`を正とする。

## 2. 結論

v1.2.7は、Java 21で動作する参照専用の単体Webアプリケーションとして実装する。
Grafana、Loki、外部RDB、MFA保存DB、LDAP、Shibboleth IdPプラグイン本体を実行時依存にしない。

推奨構成は次のとおりである。

```text
IdP server
  /opt/shibboleth-idp/logs/graphicalmatrix-audit.log
            |
            | read-only tail
            v
  2FAS-KW Dashboard Agent
    - parse
    - redact / pseudonymize
    - bounded spool
            |
            | HTTPS + mTLS
            v
Dashboard server
  2FAS-KW Dashboard Service
    - ingest API
    - embedded local index
    - aggregate query
    - read-only Web UI
            |
            v
  Apache HTTP Server + Shibboleth SP
    - administrator authentication
    - role attributes
```

閉じた管理ネットワーク内で簡易閲覧する場合は、Apache HTTP ServerとShibboleth SPを置かず、
Dashboard Serviceの`local`認証modeを使用できる。ただし、`local`は利用者認証ではなく接続元IP制限で
あり、Internet公開、利用者単位の監査、`DASHBOARD_AUDITOR`、`DASHBOARD_ADMIN`には使用しない。
本番の推奨構成は引き続き認証proxyを使用する構成とする。

単体動作とは、次を意味する。

- DashboardサーバではZIPを展開し、Java 21だけで起動できる。
- Grafana、Loki、Node.js、Python、外部PostgreSQLを必須にしない。
- 認証イベントの正本はIdP上の監査ログであり、Dashboardの索引は再構築可能とする。
- DashboardはMFA保存DB、LDAP、IdP管理APIへ接続しない。
- 同じZIPにDashboard Service、Agent、履歴import CLIを含める。

別サーバへリアルタイム転送する場合は、IdP側へAgentを配置する必要がある。Agentを配置できない
環境では、監査ログを管理者が安全にコピーし、Dashboardのimport CLIで取り込む。

## 3. 設計目標

### 3.1 目的

1. 現行監査ログだけでGraphicalMatrix認証、自己管理、登録、変更、管理API操作を可視化する。
2. Dashboard障害を認証成功・失敗・応答時間へ波及させない。
3. IdP同居、別サーバ、オフライン取込のいずれでも利用できる単体パッケージを提供する。
4. 利用者ID、IP、session、challengeを必要以上に中央サーバへ送信しない。
5. 現行ログで観測できない情報を「0件」と誤表示しない。
6. v1.3以降の構造化イベントへ移行できる内部データ契約を用意する。

### 3.2 成功条件

- Dashboardを停止しても2FAS-KW認証が継続する。
- Agentの送信先が停止してもIdPの認証スレッドを待機させない。
- `VERIFY`の成功、失敗、ロック、DBエラーを期間指定で正しく集計できる。
- 自己管理、GraphicalMatrix変更、方式変更、TOTP初回登録、管理API操作を区別できる。
- logrotate、Agent再起動、Dashboard再起動時の重複を抑止できる。
- parser失敗、収集遅延、spool overflowを可視化できる。
- ZIPだけでDashboard Service、Agent、履歴importを導入できる。
- 管理LAN内の接続元CIDRだけを許可する`local`認証modeを選択できる。
- 配布物に秘密情報、実ユーザー、内部ホスト名、実IP、監査ログ実データを含めない。

### 3.3 非目的

v1.2.7では次を実装しない。

- Dashboardからのunlock、RESET、方式変更、CSV投入、利用者無効化。
- MFA保存DB、LDAP、WebAuthn StorageServiceへの照会。
- 通常TOTP認証および通常WebAuthn認証の完全な成功・失敗集計。
- SP entityID別の正確な集計。
- IdP Password認証を含むSAMLログイン全体の処理時間測定。
- リスクベース認証の判定や自動対応。
- HA構成のDashboardクラスタ。
- Internetへ直接公開するDashboard。

## 4. 現行ログ仕様

### 4.1 入力ファイル

標準入力は次のファイルである。

```text
/opt/shibboleth-idp/logs/graphicalmatrix-audit.log
```

現行`GraphicalMatrixAuditLogger`は、イベントごとに`FileWriter`をappend modeで開き、1行を書き、
closeする。書込み例外は認証を失敗させないため握りつぶされる。このためDashboardの値は運用傾向を
確認する観測値であり、欠損が一切ない法的監査証跡とは扱わない。

### 4.2 行形式

固定順序の独自`key=value`形式である。

```text
ts=<UTC ISO-8601> event=<event> user=<user> result=<result> ip=<remote-address> session=<session> challenge=<challenge> detail=<detail>
```

例:

```text
ts=2026-01-01T00:00:00.000Z event=VERIFY user=user001 result=OK ip=192.0.2.10 session=node0abc challenge=token detail=matched
```

値のエスケープ規則は次のとおりである。

- `null`または空文字は`-`。
- 空白は`_`。
- `=`は`\=`。
- バックスラッシュ、二重引用符、改行、復帰、タブ、制御文字はエスケープされる。

標準logfmtではないため、汎用logfmt parserへそのまま渡さない。

### 4.3 parser

8項目を固定順序で抽出し、最後の`detail`は行末までを値とする。

```regex
^ts=(?<ts>[^ ]+) event=(?<event>[^ ]+) user=(?<user>[^ ]+) result=(?<result>[^ ]+) ip=(?<ip>[^ ]+) session=(?<session>[^ ]+) challenge=(?<challenge>[^ ]+) detail=(?<detail>.*)$
```

parserは次を検証する。

- UTF-8として読めること。
- 1行が64 KiB以下であること。
- `ts`がISO-8601として解析できること。
- `event`と`result`がASCIIの安全な文字集合であること。
- 制御文字が復号後も残っていないこと。
- 未来24時間より後、または設定済み保持期間より前の時刻でないこと。

parser失敗行は破棄件数だけを記録する。既定では元のraw行をDashboardへ保存・転送しない。
調査用に元行を保存する場合も、IdP上の隔離ファイルへ限定し、Dashboardサーバへ送信しない。

### 4.4 logrotate

現行例は`copytruncate`を使用する。

```text
daily
rotate 180
copytruncate
compress
delaycompress
```

`copytruncate`にはcopyとtruncateの間の欠損可能性がある。v1.2.7はこの制約を解消できない。
Agentは次を実装する。

- ファイルサイズが保存済みoffsetより小さくなった場合、truncate世代を更新して先頭から読む。
- inode変更時は新規ファイルとして追跡する。
- source ID、世代、offset、行SHA-256から重複排除キーを作る。
- 停止期間中の`.gz`は自動推測せず、明示的なimportコマンドで取り込む。

## 5. 現行ログで扱うイベント

### 5.1 GraphicalMatrix認証

| event | 主なresult | 意味 |
| --- | --- | --- |
| `START` | `FAIL`, `DB_ERROR`, `ENROLL_REQUIRED`, `LOCKED` | GraphicalMatrix開始時の拒否または異常。 |
| `CHALLENGE_CREATED` | `OK` | 画像challengeを作成した。認証成功ではない。 |
| `VERIFY` | `OK`, `FAIL`, `LOCKED`, `ENROLL_REQUIRED`, `DB_ERROR`, `BAD_REQUEST` | 画像sequence検証結果。 |
| `FORCE_SEQUENCE_CHANGE_START` | `OK` | 初回・RESET後の強制変更を開始した。 |
| `FORCE_SEQUENCE_CHANGE_SAVE` | `OK`, `BAD_REQUEST`, `ENROLL_REQUIRED`, `DB_ERROR` | 強制変更の保存結果。 |

### 5.2 TOTP初回登録

| event | 意味 |
| --- | --- |
| `TOTP_REGISTER_START` | TOTP初回登録を開始した。 |
| `TOTP_REGISTER_VERIFY` | 登録用コードを検証した。 |
| `TOTP_REGISTER_CANCEL` | 登録を取り消し、状態を戻した。 |

これらは通常TOTPログインの成功・失敗ではない。画面には必ず「TOTP初回登録」と表示する。

### 5.3 自己管理・変更

| event | 意味 |
| --- | --- |
| `SELF_SERVICE_AUTH` | 自己管理用のPassword+MFA認証結果。 |
| `SELF_SERVICE_HANDOFF` | one-time handoffの消費結果。 |
| `CHANGE_LDAP_AUTH` | 従来LDAPログイン経路の結果。 |
| `CHANGE_START` | 変更フロー開始。 |
| `CHANGE_CHALLENGE_CREATED` | 現在のGraphicalMatrix確認challenge作成。 |
| `CHANGE_VERIFY` | 現在のGraphicalMatrix確認結果。 |
| `CHANGE_CHOOSE_SEQUENCE` | sequence変更メニュー選択。 |
| `CHANGE_CHOOSE_METHOD` | MFA方式変更メニュー選択。 |
| `CHANGE_BACK_MENU` | メニューへ戻った。 |
| `CHANGE_SAVE` | 新しいGraphicalMatrix sequence保存結果。 |
| `CHANGE_METHOD_SAVE` | MFA方式保存結果。 |

操作途中イベントと保存完了イベントを分ける。変更完了件数には`CHANGE_SAVE result=OK`または
`CHANGE_METHOD_SAVE result=OK`だけを使用する。

### 5.4 管理API

主なイベントは次のとおりである。

```text
API_USER_READ
API_USER_UPDATED
API_USER_DELETED
API_METHOD_CHANGED
API_USER_RESET
API_UNLOCKED
API_ENABLED
API_DISABLED
API_TOTP_RESET
API_DENIED
API_BAD_REQUEST
API_REQUEST_REJECTED
API_UNSUPPORTED
API_ERROR
```

管理CLI、CSV import、直接SQL操作は完全には含まれない。画面には「管理API操作のみ」と表示する。

### 5.5 現行ログで取得できない項目

| 項目 | v1.2.7での表示 |
| --- | --- |
| SP entityID | 「現行ログでは取得不可」。SP別グラフを作らない。 |
| 通常TOTP認証結果 | 「取得対象外」。0件と表示しない。 |
| 通常WebAuthn認証結果 | 「取得対象外」。0件と表示しない。 |
| IdPノード名 | Agent設定の`nodeId`を使用する。 |
| 正確なクライアントIP | `getRemoteAddr()`であり、プロキシ環境ではプロキシIPの可能性を注記する。 |
| MFA処理時間 | 安全に対応付けできないため算出しない。 |
| 安定した失敗理由 | event/resultと許可済みdetail mappingだけを使う。 |
| 完全な認証試行数 | `CHALLENGE_CREATED`を認証試行として数えない。 |

## 6. 配置モデル

### 6.1 モデルA: 別サーバ配置（推奨）

```text
IdP node 1 -- Dashboard Agent --\
IdP node 2 -- Dashboard Agent ---- HTTPS/mTLS --> Dashboard server
IdP node N -- Dashboard Agent --/                    |
                                                     +-- local index
                                                     +-- Web UI
```

- AgentからDashboardへの片方向通信だけを許可する。
- DashboardからIdP、DB、LDAP、管理APIへの通信を禁止する。
- Dashboard用FQDNと管理ネットワークを用意する。
- UIはApache HTTP ServerとShibboleth SPで保護する。

### 6.2 モデルB: IdP同居

```text
IdP server
  Shibboleth IdP / 2FAS-KW
  Dashboard Service (別プロセス・別OSユーザー)
```

Dashboardは監査ログを直接tailする。小規模PoCには利用できるが、本番ではCPU、メモリ、disk I/O、
page cacheをIdPと共有するため推奨しない。

同居時も次を必須とする。

- Jettyと同じJVMへ組み込まない。
- Dashboardの保存先を`/opt/shibboleth-idp`配下へ置かない。
- systemdの`MemoryMax`、`CPUQuota`、`TasksMax`を設定する。
- UIのlisten addressはloopbackに限定する。

### 6.3 モデルC: オフライン取込

監査ログを安全な経路でDashboardサーバへコピーし、次のCLIで取り込む。

```bash
/opt/2faskw-dashboard/bin/2faskw-dashboard-import.sh \
  --node-id idp-node-01 \
  --file /secure/import/graphicalmatrix-audit.log
```

`.gz`も明示的に対応する。import後の原本削除は自動実行せず、運用者が保管規程に従って処理する。

## 7. コンポーネント設計

### 7.1 Dashboard Service

1つのJavaプロセスで次を提供する。

- HTTPSまたはloopback HTTPのWebサーバ。
- 正規化済みイベントのingest API。
- ローカル監査ログのtail（同居mode）。
- embedded H2による再構築可能な検索索引。
- 時間単位・日単位の集計。
- read-only REST API。
- 静的Web UI。
- health、収集遅延、parser失敗、spool状態の内部メトリクス。

Web UIの静的ファイルはJARへ内包し、CDNや外部JavaScriptへ依存しない。

### 7.2 Dashboard Agent

同じDashboard JARを`agent` subcommandで実行する。

```bash
java -jar 2faskw-dashboard-1.2.7.jar agent \
  --config /etc/2faskw-dashboard-agent/agent.properties
```

Agentの責務:

- audit logをread-onlyでtailする。
- 行を固定parserで解析する。
- userをprivacy設定に従って保持・仮名化・除去し、IPを除去・prefix化する。
- 許可されたdetailをreason codeへ正規化する。
- 送信単位をローカルspoolへ一時保存する。
- mTLSでDashboardへbatch送信する。
- offset、ファイル世代、送信ackをstate fileへ保存する。

AgentはDashboard停止時に認証処理へ通知せず、IdPを停止・再起動しない。

### 7.3 Import CLI

- `.log`、`.log.<date>`、`.gz`を読める。
- dry-runで行数、期間、parser失敗数、node ID、重複見込みを表示する。
- `--apply`指定時だけ索引へ反映する。
- raw user/IPを標準出力へ表示しない。
- 同じファイルの再importはline digestにより二重計上しない。

## 8. 技術構成

### 8.1 推奨スタック

| 項目 | v1.2.7 |
| --- | --- |
| Runtime | Java 21 |
| Web server | Java 21標準`jdk.httpserver` |
| REST | `HttpHandler` / JSON |
| UI | JAR内静的HTML、CSS、JavaScript |
| 索引 | embedded H2 file database |
| Migration | 起動時のversioned schema migration |
| Build | Maven |
| Service | systemd |
| Production authentication | Apache HTTP Server + Shibboleth SP |
| Closed management network access | source CIDR制限付き`local` mode |

初期実装では、配布依存を増やさずJava 21だけで起動できること、UIをloopback上の認証proxy配下で
運用すること、または閉じた管理ネットワーク内で`local` modeを使用すること、同時閲覧20接続を
目標とすることから、embedded Jetty 12ではなくJava 21標準の
`jdk.httpserver`を採用する。UI listenerとmTLS ingest listenerは別socket、別server instanceとする。
将来、外部公開、高い同時接続数、HTTP/2、詳細なconnector制御が必要になった場合は、REST pathと
設定名を維持したままJetty 12へ置換する。置換前には同じセキュリティヘッダ、request size上限、
mTLS client certificate検証、rate limitを回帰試験する。

H2はMFA保存DBではなく、Dashboard専用のローカル検索索引である。認証イベントの正本は監査ログとし、
索引は削除後に再importできる。H2へのアクセスはDashboardプロセスだけに限定する。

v1.2.7ではDashboardの複数台active-active構成を対象外とする。HAまたは大規模運用で外部PostgreSQLが
必要になった場合は、v1.3以降の別設計とする。

### 8.2 ディレクトリ

Dashboardサーバ:

```text
/opt/2faskw-dashboard/                 application
/etc/2faskw-dashboard/                 configuration
/etc/2faskw-dashboard/credentials/     mTLS and HMAC secrets
/var/lib/2faskw-dashboard/             index and migration state
/var/log/2faskw-dashboard/             service and access audit logs
/var/cache/2faskw-dashboard/import/    bounded temporary import area
```

IdP Agent:

```text
/opt/2faskw-dashboard-agent/           application
/etc/2faskw-dashboard-agent/           configuration
/etc/2faskw-dashboard-agent/credentials/
/var/lib/2faskw-dashboard-agent/       offset state and bounded spool
/var/log/2faskw-dashboard-agent/       agent operational log
```

DashboardとAgentはそれぞれ専用OSユーザーで動かす。Agentを`jetty`ユーザーとして動かさず、
監査ログだけを専用グループまたはACLで読めるようにする。

## 9. パッケージ設計

### 9.1 公開ファイル

固定名:


### 9.3 同梱禁止

- 実監査ログ、サンプルとして加工していない実ログ。
- DBファイル、Agent offset、spool。
- 秘密鍵、client certificate、HMAC鍵、passphrase。
- 内部FQDN、内部IP、実ユーザーID。
- `.DS_Store`、`__MACOSX`、IDE設定、作業用CSV。
- `target/`、Git履歴、テスト結果。

## 10. 設定設計

### 10.1 Dashboard Service

```properties
dashboard.enabled = false
dashboard.mode = server

dashboard.http.bindAddress = 127.0.0.1
dashboard.http.port = 9080
dashboard.http.basePath = /2faskw-dashboard

dashboard.storage.path = /var/lib/2faskw-dashboard/dashboard
dashboard.storage.retentionDays = 30
dashboard.storage.aggregateRetentionDays = 90

dashboard.query.defaultHours = 24
dashboard.query.maxRangeDays = 100
dashboard.query.pageSize = 100
dashboard.query.maxPageSize = 500
dashboard.query.maxExportRows = 10000

dashboard.auth.mode = proxy
dashboard.auth.trustedProxies = 127.0.0.1/32
dashboard.auth.remoteUserHeader = X-Remote-User
dashboard.auth.roleHeader = X-2FASKW-Role
dashboard.auth.rolesFile = /etc/2faskw-dashboard/roles.properties
dashboard.auth.localAllowedCIDRs =
dashboard.auth.localRole = DASHBOARD_VIEWER

dashboard.ingest.enabled = true
dashboard.ingest.requireMtls = true
dashboard.ingest.maxBatchEvents = 500
dashboard.ingest.maxRequestBytes = 1048576
dashboard.ingest.allowedClockSkewSeconds = 300

dashboard.health.staleEventSeconds = 900
dashboard.health.parseFailureWarningCount = 1
```

`dashboard.enabled=false`を配布時既定とし、設定とアクセス制御を確認してから有効化する。
`dashboard.auth.mode`は`none`、`local`、`proxy`のいずれかとし、配布時既定は`proxy`とする。
`localAllowedCIDRs`と`localRole`は`local` modeでだけ使用し、他のmodeでは認可判断に使用しない。

### 10.2 Agent

```properties
agent.enabled = false
agent.nodeId = idp-node-01
agent.source = /opt/shibboleth-idp/logs/graphicalmatrix-audit.log
agent.statePath = /var/lib/2faskw-dashboard-agent/state
agent.spoolPath = /var/lib/2faskw-dashboard-agent/spool
agent.spoolMaxBytes = 268435456
agent.pollMillis = 500
agent.heartbeatSeconds = 60

agent.dashboardUrl = https://dashboard.example.org/2faskw-dashboard/ingest/v1/events
agent.tls.caFile = /etc/2faskw-dashboard-agent/credentials/dashboard-ca.crt
agent.tls.clientCertFile = /etc/2faskw-dashboard-agent/credentials/idp-node-01.crt
agent.tls.clientKeyFile = /etc/2faskw-dashboard-agent/credentials/idp-node-01.key

agent.connectTimeoutMillis = 3000

agent.privacy.userMode = plain

```

`nodeId`は設定で明示し、OS hostnameを自動送信しない。Agentは認証イベントがない場合も
`heartbeatSeconds`間隔でheartbeatを送信し、Dashboardは`last_received_at`を更新する。
heartbeatは認証イベント数、`last_occurred_at`、`last_event_id`を変更しない。

### 10.3 privacy mode

| 項目 | 既定 | 代替設定 |
| --- | --- | --- |
| user | `plain`: 生のユーザーID | `hmac`: HMAC-SHA-256、`drop`: 送信しない |
| IP | `plain`: 生の送信元IPアドレス | `prefix`: IPv4 `/24`、IPv6 `/48`、`drop`: 送信しない |
| session | 常に送信しない | なし |
| challenge | 常に送信しない | なし |
| detail | reason mappingだけを送信 | raw保存はしない |

`plain`は運用者が認証主体を特定するための既定方式である。ユーザーIDは
`[A-Za-z0-9._@-]{1,255}`だけを許可し、mTLSで転送する。DashboardのH2ファイル、backup、CSV、
Web UIを個人情報を含む管理データとして保護する。送信元IPもイベント一覧、検索、TOP集計へ
表示するため、同じ管理データとして保護する。

複数IdPで同じ利用者をHMAC検索する場合は同じHMAC鍵が必要になる。鍵はDashboard用に新規生成し、
sequence、TOTP、DB、API tokenの鍵を再利用しない。鍵ファイルはAgentだけが読める`0400`または
同等の権限にする。

## 11. 正規化イベント

### 11.1 Agentから送る形式

```json
{
  "schemaVersion": 1,
  "eventId": "sha256 based opaque identifier",
  "occurredAt": "2026-01-01T00:00:00Z",
  "receivedAt": "2026-01-01T00:00:01Z",
  "nodeId": "idp-node-01",
  "event": "VERIFY",
  "result": "OK",
  "reason": "matched",
  "userRef": "user001",
  "sourceNetwork": "192.0.2.25",
  "lockedUntil": null,
  "parseStatus": "ok",
  "sourceGeneration": "opaque",
  "sourceOffset": 12345,
  "lineDigest": "sha256"
}
```

生の監査ログ行は送らない。`LOCKED`イベントでは`detail`内の`locked_until`だけを検証済みの
epoch millisecondsとして`lockedUntil`へ保持し、それ以外のraw detailは送信しない。`eventId`は、
node ID、source generation、offset、line digestから決定的に生成し、再送時の重複排除に使う。

### 11.2 reason mapping

`detail`全文を自由検索用に保存せず、eventごとのallowlistでreasonへ変換する。

例:

```text
matched                         -> matched
sequence_mismatch               -> credential_mismatch
missing_enrollment              -> enrollment_missing
inactive_enrollment             -> enrollment_inactive
empty_sequence                  -> sequence_missing
bind_failed                     -> ldap_bind_failed
legacy_ldap_login_disabled      -> legacy_login_disabled
one_time_handoff_consumed       -> handoff_consumed
<Java exception simple name>    -> internal_error
unknown detail                  -> other
```

mappingにない値は`other`とし、元文字列を保存しない。mapping fileの変更はversion管理し、
Dashboardの集計定義を変える変更として扱う。

## 13. 集計定義

### 13.1 GraphicalMatrix成功

```text
event = VERIFY AND result = OK
```

### 13.2 入力不一致

```text
event = VERIFY AND result = FAIL
```

TOPページの上位ユーザーは、選択期間内のこのイベントを`user_ref`別に集計し、件数降順、
同数の場合は`user_ref`昇順で表示する。`user_ref IS NULL`は除外する。表示件数は既定3件とし、
画面または`topMismatchLimit` query parameterで1～100件へ変更できる。

### 13.3 送信元IP上位

```text
event = VERIFY AND result IN (OK, FAIL, LOCKED)
```

上記を「認証試行回数」として、選択期間内のイベントを`source_network`別に集計する。加えて、
次を「入力不一致回数」として別のランキングへ表示する。

```text
event = VERIFY AND result = FAIL
```

どちらも件数降順、同数の場合は`source_network`昇順で表示し、`source_network IS NULL`は除外する。
表示件数は既定3件とし、画面または`topSourceNetworkLimit` query parameterで1～100件へ変更できる。
同じ表示件数を2種類のランキングへ適用する。`ipMode=prefix`の場合は個別IPではなくネットワーク
単位の集計になる。

### 13.4 失敗率

```text
VERIFY result=FAIL / (VERIFY result=OK + VERIFY result=FAIL)
```

`LOCKED`、`BAD_REQUEST`、`DB_ERROR`、`ENROLL_REQUIRED`は分母・分子から除外し、別パネルにする。

### 13.5 ロック

次を別系列で表示する。

- `VERIFY result=LOCKED`: 検証処理でロックへ到達、またはロック結果。
- `START result=LOCKED`: 既にロック中の開始拒否。
- `CHANGE_START result=LOCKED`: 変更画面でのロック拒否。

これらの合算値は「ロック関連イベント数」と表示する。別に、`LOCKED`イベントから抽出した
`locked_until`と、その後の`VERIFY OK`、`CHANGE_VERIFY OK`、管理APIのunlock・RESET・方式変更を
状態遷移として評価し、現在時刻時点の「現在ロック中のユーザー」を最大100件表示する。

現在ロック中の一覧は監査ログからの推定値である。管理CLI、CSV、直接SQL・LDAP変更は完全には
監査ログへ記録されないため、正確な最終状態はMFA保存DBまたはLDAPで確認する。

### 13.6 自己管理

| 指標 | 定義 |
| --- | --- |
| 自己管理認証成功 | `SELF_SERVICE_AUTH result=OK` |
| handoff成功 | `SELF_SERVICE_HANDOFF result=OK` |
| GraphicalMatrix変更完了 | `CHANGE_SAVE result=OK` |
| MFA方式変更完了 | `CHANGE_METHOD_SAVE result=OK` |
| 強制変更完了 | `FORCE_SEQUENCE_CHANGE_SAVE result=OK` |

開始数と完了数の差は離脱の参考値であり、同一transactionを正確に相関できないため厳密なconversion
rateとは呼ばない。

### 13.7 TOTP初回登録

```text
TOTP_REGISTER_VERIFY result=OK
```

通常TOTP認証成功として集計しない。

### 13.8 管理API

`API_*`をevent、result別に集計する。`API_DENIED`、`API_ERROR`、
`API_REQUEST_REJECTED`は運用警告として別表示する。

## 16. 認証・認可

### 16.1 認証mode

| mode | 用途 | 利用者識別 | 接続元制限 | 最大ロール |
| --- | --- | --- | --- | --- |
| `none` | Dashboardサーバ自身またはSSH tunnelによるPoC | 固定値`local` | loopbackのみ | `DASHBOARD_ADMIN` |
| `local` | 閉じた管理LANからの簡易閲覧 | 固定値`local-network` | `localAllowedCIDRs` | `DASHBOARD_OPERATOR` |
| `proxy` | 本番運用 | 認証proxyが渡す利用者ID | `trustedProxies` | `DASHBOARD_ADMIN` |

- Dashboardは`127.0.0.1`でlistenする。
- `auth.mode=none`ではloopback以外へのbindを拒否する。
- `auth.mode=local`ではloopbackまたは具体的なinterface addressへbindし、wildcard address
  `0.0.0.0`と`::`へのbindを拒否する。
- `auth.mode=proxy`の本番構成ではApache HTTP Server + Shibboleth SPを使用し、Dashboardの
  直接portをFirewallで到達不能にする。
- modeごとの不要な認証headerや設定値を認可判断へ混在させない。

### 16.2 `local` mode

`local` modeは、認証proxyを構築しない閉じた管理ネットワーク向けに、DashboardのWeb UIとAPIを
接続元ネットワークで制限する簡易modeである。IPアドレスは利用者本人を証明しないため、本番の
利用者認証を代替するものではない。

設定例:

```properties
dashboard.http.bindAddress = 192.168.10.20
dashboard.http.port = 9080
dashboard.auth.mode = local
dashboard.auth.localAllowedCIDRs = 192.168.10.0/24,10.20.0.0/16
dashboard.auth.localRole = DASHBOARD_VIEWER
```

アクセスURLの例:

```text
http://192.168.10.20:9080/2faskw-dashboard/
```

判定仕様は次のとおりとする。

1. `HttpExchange.getRemoteAddress()`相当のTCP接続元IPを取得する。
2. 接続元IPが`localAllowedCIDRs`のいずれかに含まれる場合だけHTTP要求を許可する。
3. 許可した要求には利用者名`local-network`と`localRole`を割り当てる。
4. 一致しない要求はHTTP 403とし、HTML、JavaScript、CSS、API、health responseを返さない。
5. `health/live`と`health/ready`はロール判定を行わないが、`localAllowedCIDRs`の接続元判定は
   必ず行う。
6. access auditには固定利用者名、固定ロール、実際のTCP接続元IPを記録する。
7. query rate limitは固定利用者名全体ではなく、実際のTCP接続元IPごとに適用する。

`localAllowedCIDRs`は空でないことを必須とし、IPv4とIPv6のCIDR表記だけを受け付ける。hostname、
範囲表記、wildcard、`0.0.0.0/0`、`::/0`は拒否する。単一IPはIPv4では`/32`、IPv6では`/128`で
指定する。構文不正、空設定、全アドレス許可があれば起動時にfail closedとする。

接続元判定では`Forwarded`、`X-Forwarded-For`、`X-Real-IP`を使用しない。また、
`remoteUserHeader`、`roleHeader`、`rolesFile`も無視する。これによりクライアントが送信したheaderで
接続元や権限を変更できないようにする。

`localRole`の既定値は`DASHBOARD_VIEWER`とし、指定可能値を`DASHBOARD_VIEWER`または
`DASHBOARD_OPERATOR`に限定する。利用者単位の識別を行えないため、`DASHBOARD_AUDITOR`と
`DASHBOARD_ADMIN`は設定エラーとして拒否し、管理API履歴、CSV export、管理者向けAPIは
`proxy` modeだけで利用可能とする。

DashboardのCIDR判定だけに依存せず、OS Firewallでも同じ送信元CIDRとportに制限する。
可能な限り専用管理VLANまたはVPNを使用する。v1.2.7のDashboard UI listenerは直接TLSを終端しないため、
平文HTTPを許容できないネットワークでは`local` modeを使用せず、HTTPS認証proxyを使用する。

### 16.3 `proxy` mode

`proxy` modeでは、trusted proxy CIDR内から届いた要求だけについて`remoteUserHeader`と
`roleHeader`を信用する。trusted proxy CIDR外から来た認証headerは、値が正しく見えても拒否する。
認証proxyはクライアントが送信した同名headerを削除し、Shibboleth SPなどの認証結果から設定し直す。
`rolesFile`に利用者が存在する場合は、そのロールを`roleHeader`より優先する。

### 16.4 ロール

| ロール | 権限 |
| --- | --- |
| `DASHBOARD_VIEWER` | 概要、認証、自己管理の集計表示。 |
| `DASHBOARD_OPERATOR` | 収集状態、reason別分析、イベント検索。 |
| `DASHBOARD_AUDITOR` | 管理API履歴、承認済みexport。 |
| `DASHBOARD_ADMIN` | Dashboard設定状態、node登録、role mapping。認証管理操作は不可。 |

フロントエンドの非表示だけで認可しない。各REST endpointでロールを検証する。

### 16.5 セッション

- `proxy` modeではShibboleth SPの認証済みsessionを利用する。
- `local` modeは接続ごとに送信元CIDRを再判定し、Dashboardの認証sessionを発行しない。
- `none` modeもDashboardの認証sessionを発行しない。
- Dashboard独自Passwordを本番の認証方式にしない。
- 認証proxyが発行するCookieは`Secure`、`HttpOnly`、`SameSite=Lax`以上とする。
- logoutは認証proxyとShibboleth SPのsessionに対して行い、Dashboard側にlogout対象の認証sessionは
  保持しない。

## 17. セキュリティ

### 17.1 信頼境界

Dashboardは参照専用であり、次を禁止する。

```text
Dashboard -> MFA DB
Dashboard -> LDAP
Dashboard -> IdP management API
Dashboard -> Admin Tools
Dashboard -> user browser authentication state changes
```

Agentは監査ログと自身のstate/spoolだけを読み書きし、IdP credentialディレクトリを読めないことを
インストール試験で確認する。

### 17.2 Web防御

- CSPを設定し、inline scriptと外部CDNを避ける。
- `X-Content-Type-Options: nosniff`。
- `Referrer-Policy: no-referrer`。
- frame embeddingを拒否する。
- HSTSはTLS終端proxyで設定する。
- query値をHTMLへ直接挿入しない。
- JSON responseへ秘密情報を含めない。
- 認証済みAPIでもrate limitとquery cost limitを設ける。
- `local` modeは管理LANまたはVPNとFirewallで保護し、Internetへ直接公開しない。
- `local` modeでは送信元を示すHTTP headerを信用せず、TCP接続元だけをCIDR判定する。
- `local` modeが平文HTTPになることを導入時に明示し、機密性が必要なら`proxy` modeへ切り替える。

### 17.3 データ保護

- 個別イベントのretentionは既定30日、最大90日。
- 時間単位aggregateのretentionは既定90日、最大180日。
- 詳細90日・aggregate 180日が必要な環境では明示的に設定を変更する。
- index、backup、exportは監査ログと同じ機密区分。
- exportは既定無効。
- H2ファイルとcredentialは別ディレクトリ・別権限。
- Dashboardログへquery parameter、user検索入力、mTLS秘密情報を出さない。
- Java heap dumpとcore dumpを本番では制限する。

### 17.4 mTLS

- 独自CAまたは組織CAでAgent client certificateを発行する。
- nodeごとに別証明書を使用する。
- SANにnode IDを持たせる。
- 失効・期限切れ・unknown CAを拒否する。
- client private keyはAgent hostから持ち出さない。
- Dashboard server certificateのhostnameを検証する。

## 18. 性能・容量

### 18.1 初期対象

v1.2.7の初期対象:

```text
IdP node数: 1-10
平均イベント: 100 events/second以下
瞬間イベント: 500 events/second
保持: raw index既定30日、最大90日
同時Dashboard閲覧: 20
```

この値を保証値にせず、受入負荷試験で確定する。

### 18.2 Service既定

```text
Java heap: 512 MiB
ingest queue: 10,000 events
DB writer: single writer + batch transaction
batch commit: 250 eventsまたは2秒
UI refresh: 60秒
query max range: 100日
event page: 100、最大500
```

H2はsingle service向けである。大量node、長期raw保持、多数同時queryが必要な場合はv1.3の外部
PostgreSQL/Loki構成へ移行する。

### 18.3 Agent

Agentは認証処理と別プロセスで動作する。

```text
heap: 128 MiB
spool既定: 256 MiB
batch: 250 events
flush: 2秒
retry: exponential backoff、最大60秒
```

spool上限到達時は古い未送信batchを無制限に保持しない。drop数をローカルログへ記録し、
Dashboard復旧後にhealthへ送る。認証を止める動作にはしない。

## 19. 障害動作

| 障害 | 認証への影響 | 動作 |
| --- | --- | --- |
| Dashboard停止 | なし | Agentがbounded spoolへ保存しretryする。 |
| Dashboard index破損 | なし | Serviceを停止し、backupまたは監査ログから再構築する。 |
| Agent停止 | なし | 再起動後にoffsetから再開する。 |
| Agent spool満杯 | なし | dropを記録し、認証は継続する。 |
| audit log権限変更 | 認証には原則なし | Agentはread errorを記録する。 |
| parser失敗 | 認証にはなし | failure countを増やし、raw行は中央へ送らない。 |
| mTLS期限切れ | 認証にはなし | ingest停止、spool、警告。 |
| Dashboard disk逼迫 | 認証にはなし | ingestを503で拒否し、Agentがspoolする。 |
| logrotate中の欠損 | 観測値欠損 | copytruncate制約としてhealthと運用記録で扱う。 |

Dashboard障害時にIdPを再起動する手順を作らない。

### 22.4 Web security test

- `proxy` modeの未認証アクセス拒否。
- trusted proxy外の偽装header拒否。
- `local` modeで許可CIDR内のWeb UIとAPIを許可する。
- `local` modeで許可CIDR外のWeb UI、静的asset、APIをHTTP 403にする。
- `Forwarded`、`X-Forwarded-For`、`X-Real-IP`で`local` modeのCIDR制限を回避できない。
- `local` modeで`X-Remote-User`や`X-2FASKW-Role`を送っても利用者名とロールを変更できない。
- `localAllowedCIDRs`の空設定、不正CIDR、hostname、`0.0.0.0/0`、`::/0`を起動時に拒否する。
- `local` modeのwildcard bindを拒否する。
- `localRole`の`DASHBOARD_AUDITOR`と`DASHBOARD_ADMIN`を起動時に拒否する。
- IPv4 `/32`、IPv6 `/128`、複数CIDRを正しく判定する。
- roleごとのAPI拒否。
- query range、page size、export上限。
- XSS、CSV injection、path traversal。
- CSP、cookie、security headers。
- `proxy` modeではdirect service portを外部へ公開しない。
- `local` modeではdirect service portが許可CIDRとFirewall制限の両方を満たす接続だけを受け付ける。
- response/log/browser URLに秘密情報がない。

## 26. 主要リスクと判断事項

### 26.1 現行ログの欠損

監査ログ書込み例外は認証を失敗させず、`copytruncate`にも欠損可能性がある。Dashboardを完全な監査証跡
と表現しない。

### 26.2 user/IPの必要性

利用者別の障害調査と不正試行確認を優先し、userは`plain`を既定とする。一方でユーザーIDを含む
Dashboard索引、backup、CSV、Webアクセスを個人情報として保護し、保持期間と閲覧ロールを定める。
組織方針で生IDを中央保存できない場合は`hmac`または`drop`へ変更する。IPは引き続き`drop`を既定とする。

### 26.3 embedded H2の限界

単体動作には適するが、大規模長期保持やactive-activeには向かない。v1.2.7の対象規模を負荷試験で
超えた場合は、機能追加より先にbackend移行を設計する。

### 26.4 Dashboard認証

単体JARに安易な共有Password認証を実装しない。本番はShibboleth SPまたは組織標準の認証proxyで保護する。
`local` modeは閉じた管理LAN向けの接続元CIDR制限であり、利用者認証ではない。固定利用者名になるため
個人単位のアクセス監査ができず、同一CIDR内の侵害端末も許可される。利用者識別、上位ロール、HTTPSが
必要な環境では`proxy` modeを使用する。

### 26.5 Agent配置

別サーバ構成でもIdP側にはAgentが必要である。「Dashboard ZIPをDashboardサーバへ置くだけで自動的に
IdPログを取得する」と説明しない。DashboardからSSH/SFTPでIdPへpullする構成は採用しない。
