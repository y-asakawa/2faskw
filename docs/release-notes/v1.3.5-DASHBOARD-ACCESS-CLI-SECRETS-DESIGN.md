# 2FAS-KW v1.3.5 Dashboard閲覧制御・CLI秘密情報保護 詳細設計

実装状態: 実装・主要自動回帰試験完了、実環境確認は未実施

## 1. 文書の目的

本書は、2FAS-KW v1.3.5で対応する次のセキュリティ修正について、実装仕様、
運用互換性、試験、配備、切戻しを定義する詳細設計兼リリースノートである。

1. F-03: Dashboardの汎用イベント取得経路にもPrincipal由来の閲覧範囲を適用する。
2. F-04: CSV provisioningで認証画像列をJavaのプロセス引数へ渡さない。

二つの修正は実行経路と配備対象が異なるため、実装、試験、完了判定を分ける。
F-03はDashboard、F-04はAdmin Toolsの`graphicalmatrix-db.sh`とSequence Toolが対象である。

## 2. 対象バージョン

本変更の配布対象はv1.3.5とする。基準実装はv1.3.4であり、既に公開されたtagや
成果物を移動、再作成、置換しない。

設計段階では`version.ini`、Maven version、plugin metadata、成果物名を変更しない。
実装、回帰試験、実環境確認が完了した後に、v1.3.5のrelease変更として一括更新する。

## 3. 修正の区分

| 区分 | 内容 | v1.3.5の必須範囲 |
|---|---|---|
| A: F-03 | DashboardのPrincipalベース閲覧範囲、SQL、集計、UI | v1.3.5で必須 |
| B: F-04 | CSV画像列のJava argvからstdinへの移行 | v1.3.5で必須 |
| C: 関連改善 | TOTP seed、直接入力CLI、SQL本文の安全な受け渡し | 任意の後続対応 |

AとBの両方が受入条件を満たした場合に、F-03・F-04対応済みとする。Bの実装だけで、
管理CLI全体から秘密情報のargv露出が除去されたとは扱わない。

## 4. Security invariant

### 4.1 Dashboard

- 閲覧範囲は認証済みPrincipalからのみ決定する。
- query parameter、event filter、正規表現、cursorで閲覧範囲を拡張できない。
- VIEWERとOPERATORは管理APIイベントおよび未分類イベントを取得できない。
- AUDITORとADMINは監査に必要な全イベントを取得できる。
- 一覧だけでなく、集計、ページング、export、派生状態へ同じ閲覧範囲を適用する。
- 権限外イベントの件数、存在、利用者、送信元ネットワークを間接的にも返さない。
- 未知イベントは明示的に分類されるまでAUDITOR以上に限定する。
- UI上の非表示だけに依存せず、ServerとStoreの両境界で制御する。

### 4.2 CSV画像列

- CSVの認証画像列をJavaのargv、環境変数、Java system propertyへ渡さない。
- Bash組込み`printf`から専用のstdinへ画像列だけを送る。
- dry-runとapplyの双方で同じ保護を適用する。
- エンコード失敗時はDB更新へ進まず、平文保存へfallbackしない。
- hash、keyword、aes-gcm、plaintextの保存意味と認証結果を変更しない。
- エラー、trace、診断ログへ平文画像列を追加しない。

本設計はroot、処理ユーザー自身、JVMメモリを参照できる主体から秘密を保護するものではない。

## 5. 運用互換性

### 5.1 変更しないコマンド

F-03・F-04の必須対応では、次の管理操作を変更しない。

- `graphicalmatrix-db.sh import-csv`のコマンド形式
- CSV provisioningの`A`、`M`、`D` action
- CSVの列名、列順、quoted fieldの扱い
- systemd path unitによるincoming directory監視
- `graphicalmatrix-db.sh`の通常の利用者管理コマンド
- `graphicalmatrix-sp.sh`のSP、属性、access、MFA管理コマンド
- Dashboardの既存URLとquery parameter

既存CSVの書換えや、既存DBデータの再暗号化は不要である。

### 5.2 意図的に変わる表示

F-03により、VIEWER／OPERATORのDashboard表示範囲は次のように変わる。

- 通常認証・自己管理イベントは引き続き閲覧できる。
- 管理APIイベントと未分類イベントは表示されない。
- 管理イベントを用いて再構成する現在ロック状態は表示しない。
- ロック件数を誤って`0`とせず、利用不可として表示する。

AUDITOR／ADMINの監査閲覧範囲は維持する。OPERATOR権限で管理操作履歴を監視していた
環境は、該当する運用者へAUDITORを割り当てる必要がある。

### 5.3 API応答の互換性

VIEWER／OPERATORのsummaryでは、次のようにロック状態を利用不可として返す。

```json
{
  "lockedUserCount": null,
  "lockedUsers": [],
  "lockedUsersAsOf": null,
  "visibility": {
    "scope": "OPERATIONAL",
    "lockedUsersAvailable": false
  }
}
```

独自のDashboard API clientが`lockedUserCount`を常に数値として扱っている場合は、
`null`と`visibility.lockedUsersAvailable`に対応する。権限外イベントを明示指定した
`/api/v1/events`は、存在を開示しないため`200`と空配列を返す。ルート自体の権限が
不足する`/admin-api`と`/export`は従来どおり`403`を返す。

## 6. F-03の問題

Dashboardは`/admin-api`と`/export`をAUDITOR以上へ制限している一方、汎用の
`/events`をOPERATORへ公開している。現行Storeの汎用検索は時刻、event、利用者、
送信元等のfilterを処理するが、Principalのロールによるevent type制限をSQLへ渡さない。

そのため、OPERATORが次のような検索を行うと、AUDITOR向け管理APIイベントを取得できる
可能性がある。

```text
/api/v1/events?event=API_USER_UPDATED
```

filterなし、正規表現、ページング、summaryの集計にも同じ境界を適用する必要がある。

## 7. F-03のイベント分類

新設する`DashboardEventPolicy`へイベント分類を集約する。分類はサーバ側の定義から決定し、
clientから分類値や許可prefixを受け取らない。

| 分類 | 対象 | 閲覧可能ロール |
|---|---|---|
| `AUTHENTICATION` | 認証イベントの明示allowlist | VIEWER以上 |
| `SELF_SERVICE` | 自己管理イベントの明示allowlist | VIEWER以上 |
| `ADMIN_API` | 文字どおり`API_`で始まるイベント | AUDITOR以上 |
| `RESTRICTED_OTHER` | 上記以外の既知・未知イベント | AUDITOR以上 |

認証イベントと自己管理イベントは明示リストで管理する。任意の`CHANGE_`prefix全体を
VIEWERへ公開しない。新しいイベントを追加した場合は、Policyとロール別テストを同じ変更で
更新する。未分類のままでも取込は継続し、閲覧だけをAUDITOR以上へ制限する。

`API_`のSQL判定に`LIKE 'API_%'`を使用しない。SQLのunderscoreは任意の1文字として
解釈されるため、次のように文字列先頭を厳密に比較する。

```sql
LEFT(event_type, 4) = 'API_'
```

`API_X`は`ADMIN_API`、`APIX_X`と`APIUSER`は`RESTRICTED_OTHER`となる。

## 8. F-03の閲覧scope

不変型`DashboardEventScope`を新設し、認証済みPrincipalからだけ生成する。

| Principal role | Scope |
|---|---|
| VIEWER | `OPERATIONAL` |
| OPERATOR | `OPERATIONAL` |
| AUDITOR | `ALL` |
| ADMIN | `ALL` |

Principalまたはroleが欠落・不正な場合は拒否する。scope欠落を`ALL`として扱う
compatibility constructorや無制限overloadを追加しない。

最終的なデータ範囲は次の積集合とする。

```text
Principal scope AND route category AND user filter
```

利用者が指定するevent、regex、user、reason、node、source network、result、cursorは、
scopeの代わりにならず、scopeを広げない。

## 9. F-03のルート仕様

| API | 最低ロール | 返却可能なデータ |
|---|---|---|
| `/summary` | VIEWER | scope内の集計。ロック状態は別制御 |
| `/authentication` | VIEWER | scopeとAUTHENTICATIONの共通部分 |
| `/self-service` | VIEWER | scopeとSELF_SERVICEの共通部分 |
| `/events` | OPERATOR | scope内の全カテゴリ |
| `/admin-api` | AUDITOR | ADMIN_API |
| `/export` | AUDITOR | scope内。既存`exportEnabled`も必要 |
| `/ingest-health` | OPERATOR | 取込サービスの稼働指標のみ |

local認証とproxy認証で同じPolicyを使用する。`authMode=none`は現行どおりADMIN相当だが、
ロール境界の受入試験には使用しない。

## 10. F-03のServer・Store設計

処理順序を次のように統一する。

```text
HTTP request
  -> Principal認証
  -> routeの最低ロール確認
  -> Principalからscope生成
  -> scope AND route category AND user filterをSQLへ適用
  -> regex、page、JSONまたはCSV生成
```

`DashboardServer.handleApi()`でscopeを一度決定し、summary、category events、generic events、
exportへ渡す。`DashboardStore`のイベントを返す全メソッドはscopeを必須引数とする。
HTTP以外の直接呼出しでも無制限検索へ到達できるoverloadを残さない。

新設する`DashboardEventPredicate`は、scopeとroute categoryからSQL断片とbind parameterを
生成する。任意のSQL断片をclientや呼出元から受け取らない。

`OPERATIONAL`では公開対象の明示allowlistを次の条件へ変換する。

```sql
AND event_type IN (?, ?, ...)
```

許可集合が空の場合は`1 = 0`とし、条件を省略しない。`ALL`で条件を省略できるのは、
認証済みPrincipalから生成した`ALL` scopeをStoreが確認した場合だけとする。

scopeはLIMIT、offset、regex候補上限より前にSQLへ適用する。Javaで取得後に権限外行を
削除する方式は、隠れた行が件数、page、cursor、処理時間へ影響するため採用しない。

cursorは位置指定にすぎず権限証明ではない。AUDITORのcursorをOPERATORが再利用しても、
要求時のPrincipalからscopeを再生成して適用する。

## 11. F-03の集計とロック状態

生イベント集計と時間単位集計の両方へ同じscopeを適用する。時刻範囲の端を生データ、中央を
`dashboard_hourly`から取得する既存方式は維持する。

Top user、Top network、failure rateは、既存の固定event条件とscopeの共通部分を対象とする。
この修正によって集計対象eventを広げない。

現在のロック状態は`API_UNLOCKED`、`API_USER_RESET`、`API_METHOD_CHANGED`等を含む履歴から
再構成している。OPERATOR向けにAPI eventを除外した不完全な履歴で再構成すると、既に解除された
利用者をロック中と誤表示する可能性がある。

このため、VIEWER／OPERATORではロック再構成queryを実行しない。AUDITOR／ADMINだけが完全な
履歴から現在状態を取得する。UIは`lockedUsersAvailable=false`の場合に「0人」ではなく、
権限上利用できないことを表示する。

## 12. F-03のUIとcache

- 権限外の管理API tab、export操作、ロック表示をUIから隠す。
- UIの非表示は補助とし、APIとSQLを正式な強制境界とする。
- capability情報が欠落した場合に全権限ありとして表示しない。
- 既存の`Cache-Control: no-store`を維持する。
- 将来cacheを追加する場合はscopeとpolicy versionをcache keyへ含める。
- AUDITOR応答をVIEWER／OPERATORへ再利用しない。
- ingest healthへevent category別履歴や利用者別管理件数を追加しない。

## 13. F-04の問題

CSV provisioningのA／M行では、CSVから取得した画像列を検証・正規化した後、
`sequence_storage_encode()`へ渡す。現行helperは次のように画像列をJavaの位置引数へ含める。

```bash
java -cp "$cp" io.github.yasakawa.faskw.GraphicalMatrixSequenceTool \
  encode "$IDP_HOME" "$sequence" "$ordered" "$duplicates"
```

同一ホストでprocess情報を参照できる別利用者は、実行中に`ps`や`/proc`から画像列を取得できる
可能性がある。CSV fileの`0600`や保存directoryの`0700`は、起動後のargvを保護しない。
現行処理はapply判定前にもencodeするため、dry-runにも同じ問題がある。

## 14. F-04のstdin契約

既存の`GraphicalMatrixSequenceTool encode-stdin`を使用し、helperを次の形式へ変更する。

```bash
builtin printf '%s' "$sequence" |
  java -cp "$cp" io.github.yasakawa.faskw.GraphicalMatrixSequenceTool \
    encode-stdin "$IDP_HOME" "$ordered" "$duplicates"
```

実装要件は次のとおりである。

- `builtin printf`を明示し、画像列を持つ外部printf processを起動しない。
- formatは固定の`%s`とし、画像列をformat stringとして解釈しない。
- 不要な改行を追加しない。
- Javaへは現在処理中の1行から確定した画像列だけを送る。
- JavaがCSV readerのstdinや次のCSV行を直接消費しない。
- shell変数をexportしない。
- `bash -c`のcommand stringへ画像列を埋め込まない。
- orderedとduplicatesの既存設定をそのまま渡す。
- plaintext modeはJavaを起動せず、Bash組込みprintfを使用する。

shell function内部の変数とJavaの外部process argvは異なるため、内部関数呼出し
`sequence_storage_encode "$resolved_sequence"`は維持できる。ただし利用者が直接実行する
親CLIの引数に秘密を渡す別経路は、F-04本対応だけでは解消しない。

## 15. F-04の失敗処理

エンコード結果は、command substitutionとpipeの終了状態を明示的に確認する。

```bash
if stored_sequence="$(sequence_storage_encode "$resolved_sequence")"; then
  [[ -n "$stored_sequence" ]] || die "sequence encoding returned no data"
else
  die "sequence encoding failed"
fi
```

次の場合は処理を失敗させ、applyへ進めない。

- Javaまたは必要なJARが存在しない。
- `encode-stdin`が利用できない旧JARである。
- stdin読取りまたはsequence validationに失敗した。
- storage設定または鍵・pepperの読取りに失敗した。
- Javaが非ゼロ終了した。
- encoderが空の結果を返した。

旧JARとの自動互換のためにargvを使う`encode`へfallbackしてはならない。shellとJARは同じ
配布版へ更新する。失敗時も秘密値をerror messageへ含めない。

## 16. F-04で変更しないデータ

- 認証画像列のvalidationとcanonical representation
- 順序あり／なし、重複許可／不許可
- aliasから画像IDへの解決
- hashのsaltとHMAC、keyword、AES-GCMの保存方式
- DB columnと既存row
- `initial_sequence`の保存仕様
- CSV previewの既存運用上の取扱い

salt付きhashや暗号文は実行ごとに異なるため、旧版と新版の保存文字列の完全一致を試験条件に
しない。保存値を使ったmatch、decode、方式判定、認証結果が同じ意味になることを確認する。

## 17. 関連改善C

次の経路も秘密情報をargvへ含める可能性があるが、F-04の必須範囲とは分けて実装する。

### 17.1 TOTP seed

`GraphicalMatrixTotpSeedTool`へstdin入力を追加し、運用入口として次の形式を追加する案とする。

```bash
sudo /opt/shibboleth-idp/bin/graphicalmatrix-db.sh \
  set-totp-seed-stdin USER < /protected/totp-seed.txt
```

旧`set-totp-seed USER SECRET`は互換性のため直ちに削除しないが、親shellのargvにseedを含むため、
新しい手順では推奨しない。

### 17.2 直接入力する画像列

画像列を親CLIの引数へ直接渡す操作は、内部Javaだけをstdin化しても親processのargvに値が残る。
複数利用者の運用では、保護されたCSV fileを入力にする既存provisioning経路を推奨する。

### 17.3 SQL本文

H2のSQL本文とPostgreSQLの`psql -c "$sql"`もargvへ現れ得る。H2はpassword用stdinとの競合を
避けるため保護されたSQL file、PostgreSQLはtransactionと出力互換性を確認したうえでstdinまたは
`-f`へ移行する。これらはscalar結果、複数SELECT、途中errorのtransaction境界を試験してから行う。

## 19. F-03試験

同じ時刻範囲へ通常認証、自己管理、`API_USER_UPDATED`、`API_UNLOCKED`、未知イベントを
投入する。管理イベントにだけ存在するtest用user referenceとnetworkを用意し、値と件数の
両方が漏えいしないことを確認する。

| ID | 条件 | 合格条件 |
|---|---|---|
| F03-01 | OPERATORで`/admin-api`、`/export` | `403` |
| F03-02 | OPERATORでfilterなしの`/events` | API・未知eventなし、通常eventあり |
| F03-03 | OPERATORでAPI event完全一致 | `200`、空配列、固有情報なし |
| F03-04 | OPERATORでregex `API_.*`、`.*` | scopeを超えない |
| F03-05 | user、reason、node、network等の複合filter | 権限外eventを取得できない |
| F03-06 | 1件単位のpage、同一時刻event | 全pageでscopeを維持 |
| F03-07 | AUDITOR cursorをOPERATORが使用 | OPERATOR scopeを再適用 |
| F03-08 | AUDITOR／ADMINの同一検索 | 従来の監査対象を取得可能 |
| F03-09 | VIEWERで`/events` | `403`。カテゴリ別閲覧は維持 |
| F03-10 | `API_X`、`APIX_X`、unknown | 定義どおり分類 |
| F03-11 | null、不正scope、空allowlist | 拒否または0件。無制限にならない |
| F03-12 | 権限外行が大量に存在 | page、LIMIT、regex候補を消費しない |
| F03-13 | rawとhourlyの境界時刻 | 同じscopeの件数 |
| F03-14 | OPERATOR／VIEWERのsummary | API event件数と固有情報なし |

| F03-16 | role切替とbrowser cache | 上位roleの応答を下位roleへ再表示しない |
| F03-17 | Store直接呼出し | scope必須。無制限overloadなし |

local認証とproxy認証の両方でVIEWER、OPERATOR、AUDITOR、ADMINを試験する。
`authMode=none`だけで権限試験を完了しない。

## 20. F-04試験

本番の画像列やstorage secretを使用せず、保護されたtest directory内のCSVを使用する。
Java wrapperでargvをNUL区切りのまま検査し、stdinは別に取得する。秘密値そのものをCI logへ
出力せず、合否だけを記録する。

| ID | 条件 | 合格条件 |
|---|---|---|
| F04-01 | CSV A／M、hash、dry-run | argvに画像列なし、stdinに正規化済み列あり |
| F04-02 | CSV A／M、hash、apply | 同じ受け渡しでDBへ保護形式を保存 |
| F04-03 | keyword／aes-gcm | argv非露出と認証結果の互換性 |
| F04-04 | plaintext | 不要なJava起動なし、既存保存仕様を維持 |
| F04-05 | 複数行CSV、stdinからCSV入力 | Javaが次のCSV行を消費しない |
| F04-06 | 順序、重複、aliasの各設定 | 旧版と同じ許可・拒否・認証結果 |
| F04-07 | Javaなし、非ゼロ終了、空出力 | applyせず、plaintext fallbackなし |
| F04-08 | storage設定不正、鍵読取り失敗 | 秘密を表示せず失敗を伝播 |
| F04-09 | 実JVMのprocess情報 | Java argvと新設envに画像列なし |
| F04-10 | 中断、SQL生成失敗 | 既存trapと一時fileの後片付けを維持 |

## 21. 配備

### 21.1 F-03

1. Policy、scope、SQL predicateの単体試験を先に追加する。
2. Storeの全読取り入口をscope必須へ変更する。
3. Server、summary、export、UIを接続する。
4. Dashboard JAR、web assets、文書を同じ版で配備する。
5. 旧nodeと新版nodeが同時にrequestを受ける状態を残さない。
6. OPERATORとAUDITORの実アカウントで配備後確認を行う。

Dashboard DBの既存イベント削除や取込停止は不要である。

### 21.2 F-04

1. `encode-stdin`を持つJARを確認する。
2. 修正済み`graphicalmatrix-db.sh`と対応JARを同じ配布版から導入する。
3. dry-run用test CSVでargv非露出とpreviewを確認する。
4. 検証環境でapplyし、保存値の方式と通常認証を確認する。
5. 全Admin Tools hostとCSV runnerで旧shellが残っていないことを確認する。

本番DBへ試験用の実認証情報を不用意に登録しない。

## 22. 切戻し

F-03を旧版へ戻すと汎用eventsとsummaryの情報露出が再発する。切戻しが必要な場合は、先に
`/events`をAUDITOR以上へ制限し、必要に応じて`/summary`も暫定的にAUDITOR以上へ制限する。
UIのtabだけを隠す対応は切戻し時の緩和策として不十分である。

F-04を旧shellへ戻すとCSV処理時のargv露出が再発する。修正版を再配備できるまで、対象hostで
CSV provisioningを停止するか、process情報を参照できる利用者を実効的に制限する。旧JAR対応の
ために修正版shellをargv方式へ自動fallbackさせない。

AとBは独立して切り戻せる。F-04の問題を理由にDashboard DBを変更せず、F-03の問題を理由に
認証DBのsequenceを変換しない。

## 24. リリース概要

v1.3.5では、Dashboardのroute単位認可をデータ行・集計単位の認可へ拡張し、汎用検索を通じた
管理イベントの取得を防止する。また、CSV provisioningの認証画像列をJavaの標準入力へ移し、
同一hostのprocess情報から平文画像列が読み取られる可能性を低減する。

SP管理、MFA管理、利用者管理、CSV provisioningの既存コマンドは変更しない。運用上の主な変更は、
VIEWER／OPERATORのDashboardに管理イベントと現在ロック状態を表示しなくなる点である。
独自Dashboard API clientは、ロック状態の`null`と`visibility`へ対応する必要がある。

実装と自動回帰試験は完了している。リリース判定では、proxy modeのOPERATOR／AUDITOR実アカウントと
実際のCSV runnerを使用した配備後確認を別途実施する。
